## 0. 版本号怎么读

| 写法 | 含义 |
|---|---|
| **alpha 1.0 / 2.0 / 3.0 / 4.0** | **功能模块大版本** —— 一个大版本只装一个模块：**1 = Database（数据库）· 2 = Workspace（工作区）· 3 = Notes（笔记）· 4 = Retro（复盘）** |
| **1.1 / 1.2 / 3.1 / 3.2 …** | **同一模块内的进度子号** —— 一条主线走一段落，就递一个小号；**大号不变**（模块没换就不换大号） |
| **`alpha<大号>.<子号>`**（如 `alpha1.3`） | **出包标签** —— 包标签 = 里程碑号 + 子号，与移动端（DoyahNotes §5）同一命名法；小改动 +1 |
| **Alpha 1~4 / Beta 1** | **跨仓里程碑** —— 与 macOS 侧同一套地图（`Docs/发布计划.md` §2）；**里程碑号就是模块号** |
| **口径来源** | 人类主人原话（派活单 `T-20261002-009`）：「如果有小改动，你可以改子版本号，alpha1.0、1.1、1.2」⇒ **每个里程碑从 `.0` 起、小改 +1**；**跨侧唯一出处 = `Docs/发布计划.md` §5 附注**（2026-10-02 v1.29 掰直，`Docs/发布方案.md` §8 同向）。**一处如实登记**：派活单 `T-20261002-032` 的前门口径写的是「进度号从 1 起」——与人类主人原话不符，本侧**按原话落**（`.0` 起），已在前门回执里登记此差异 |

两条纪律：

1. **里程碑号不由本侧自己编** —— 按总地图走（1 = Database · 2 = Workspace · 3 = Notes · 4 = Retro；全量那一版 = `beta1.0`）。
2. **Windows 的 `alpha<号>` 与 macOS 的同名里程碑不是同一个包** —— 两端各出各的包，**本侧只借用里程碑号**，不改对侧出包节奏、不主张跨端同包（跨端一致的那部分仍按 §8.5.4「一样」清单判）。

### 0.2 数据库测试环境（本机实测，2026-10-02）

**跑 1.x 的「真跑通」这一步，缺一样东西：能连上的 PostgreSQL 口令。** 实测如下：

| 项 | 实测结果 | 对 1.x 的影响 |
|---|---|---|
| **PostgreSQL 18** | 服务在跑（`postgresql-x64-18`）、**端口 5432 通** | **可用** —— 只差口令 |
| 认证方式 | `pg_hba.conf` 本机回环 = **scram-sha-256**（要口令；没有 trust 档） | 无口令就连不上；本机没有 `pgpass` 档 |
| 客户端工具 | `psql` 在 `C:\Program Files\PostgreSQL\18\bin` | 可用（造夹具 / 对照读数） |
| **MySQL** | 有客户端（`D:\Program Files\mysql-8.4.10-winx64`），**服务未起、3306 不通** | 1.8 段的 MySQL 面仍然待老板重新拍板后再排 |
| SQLite | 无 `sqlite3` 命令行；**但 `rusqlite` + `libsqlite3-sys` 已在本机 cargo 缓存里** | 3.x 的笔记本地库**不需要联网取依赖** |
| Docker / Podman | 都没有 | 起不了临时库；只能用本机那台 PG 18 |
| PostgreSQL 驱动 crate | `tokio-postgres` / `sqlx` **不在**本机 cargo 缓存（缓存里只有 `tokio` / `rusqlite`） | 真连库那一片要先联网取 crate |

**因此本侧当前的两条道**：
- **没有口令也能推进的**（现在就能做）：外壳与表示层、连接配置与 URL 解析、对象树 / SQL 编辑面的**行为层**、缩进与自测。
- **必须真库才能算「跑通」的**：真连接、真取数、真对象树、真执行计划 —— 按子号出口判据（§2 第 1 条）**不许拿假数据充「已跑通」**。

**已解（2026-10-02 下午）**：不再需要用户那台 PG 的口令 —— 本侧**自己起了一台专用实验集群**（`initdb -A trust` + 端口 5433 + 数据目录 `_tmp_face2/pglab`），**不动用户现有那台**。夹具 = `app.accounts`（50 行）/ `app.orders`（500 行）。真库端到端判据 = `App/src-tauri/tests/live_lab.rs`（设 `DOYAH_LAB=1` 启用；没设就**跳过并说明为什么**）。**仍缺的一样东西**：那台集群**不会开机自启**（手工 `pg_ctl start` 起），重启机器后要重新起 —— 要不要把它做成服务/脚本，等老板一句话。

**要老板给的一样东西**：本机 PostgreSQL 的连接口令（或一句话授权我在别的端口起一台**专用测试库**，用 trust 认证、不动现有那台）。

## 5.3 ConPTY 攻坚记录（2026-10-03 第 35 轮，**一处真突破 + 一处未解**）

第 17 轮那次失败（症状：子进程起得来、`CreateProcessW` 返回成功、进程还在跑，但
**从不执行命令**）这一轮找到并**证实**了病根：

### 已解决：进程属性表缓冲区**必须按 API 要求的对齐**分配
- 第一版我用 `Vec<u8>` 当属性表缓冲，只保证 **1 字节**对齐；而属性表里有指针。
- 改法：先问 API 要多少字节（`InitializeProcThreadAttributeList(null, …)`），
  再用 `std::alloc::alloc` 按 `align_of::<usize>()` 分配，用完
  `DeleteProcThreadAttributeList` + `dealloc`。
- **判据（决定性）**：让 shell 把结果写文件。改之前四种 shell（`cmd /c` / `cmd /k` /
  `cmd` / `pwsh -Command`）**文件从不出现**；改之后 `cmd /c echo RAN > 文件` 的
  **文件出现、内容 `RAN`**。这一条是本模块的"病根判据" —— **续做实现时它必须是第一条用例**（本轮的实验代码已按纪律撤掉，所以"已写进用例"这句话当时并不成立，这里改为如实的措辞）。

### 未解：子进程的输出**进不了**伪控制台管道
对齐修好之后，新的边界很清楚：
- 伪控制台**建成功**，而且**它自己的 16 字节模式序列能读到**（`?9001h` `?1004h`）
  ⇒ 读出这条路是通的；
- 但子进程自己的输出**读不到**：`cmd /c echo HELLO` 往返读到 0 字节，
  `cmd /q /k` 里敲 `echo …` 也是 0 字节（子进程确实在跑 —— 写文件那条能成）。

**这一轮已排除**（都不是病根）：
1. `bInheritHandles` 为 0 或 1 —— 两种取值现象**完全一样**；
2. 属性表对齐（就是上面那条，已修）；
3. 子进程那两端的继承位（`SetHandleInformation` 两种都试过）；
4. 我们这端的继承位没清（已清）；
5. `CreatePseudoConsole` 之后我们这侧原始句柄没关（已关）；
6. 读端不排空（专用线程一直读，**已排空**）；
7. `STARTUPINFOEXW.cb` 大小（用的就是结构体大小）；
8. `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` 的值与大小（`HPCON` 按值传入、
   `size_of::<HPCON>()`）。

**下一步该查的方向**（写下来免得下次重复）：伪控制台是否真的**挂上了**这一个进程
（在子进程里读它自己的控制台信息来证明，比如让它 `mode con` 或读 `GetConsoleScreenBufferInfo`
把行列写进文件 —— 若行列等于我们请求的 80×24，说明挂上了；否则说明属性没生效）。

### 第 36 轮续查（两个猜想都被实验否掉，但换到了确定的结论）
- **猜想 A（属性没生效）→ 否**：让子进程把它自己的控制台尺寸写进文件，得到
  **`win=80x24 buf=80x24`** —— 正是我们请求的尺寸 ⇒ **伪控制台确实挂上了这一个进程**，
  属性是生效的。这条很值：它把「挂没挂上」这个最大的疑点**永久排除**了。
- **猜想 B（`CreatePseudoConsole` 之后不该关我们那侧的原始句柄）→ 否**：
  保留 / 关闭两种做法**现象完全一样**（都只有 16 字节模式序列）。
- 补充排除：把 `cmd /c echo` 换成「明确刷新的 pwsh 输出」也一样 ⇒ **不是 cmd 的输出缓冲问题**。

**当前边界（已确定）**：伪控制台挂上了、子进程在跑、**读出管道是通的**（模式字节到了我们手里），
但**子进程的屏幕帧没有到达管道** ⇒ 问题在「伪控制台 → 管道」这一段，不在「进程挂没挂上」。

**下一步该查的方向**（写下免得下次重复）：
1. 用**别人的 ConPTY 实现**做对照（同一个 `cmd /c echo` 在别的 ConPTY 客户端下能否到达读端）——
   判定「是我们的用法问题」还是「这台机器 / 这个 Windows 版本的行为差异」；
2. 试 `CreatePseudoConsole` 的 `dwFlags`（我们传的是 0）里的 `PSEUDOCONSOLE_INHERIT_CURSOR`；
3. 把 `output_write` 换成**真实文件句柄**做对照，看屏幕帧是否落进文件 ——
   判定「ConPTY 有没有产出帧」与「管道方向对不对」各占多少。

### 第 37 轮续查（换查法：匿名管道 vs 命名管道）
- **换查法的由头**：官方与常见的 ConPTY 用法都走**命名管道**（`\\.\pipe\…`），
  我前几轮一直用匿名管道（`CreatePipe`）。两者对伪控制台的差别是"能否按名字重新打开"。
- **结果：匿名管道对照组仍然是"只有 16 字节模式序列、标记不到"**（与第 35/36 轮一致，
  这也算把匿名管道这条路**再确认一次**）。
- **命名管道对照组没跑起来**：`CreateNamedPipeW` 调用失败 —— 是我把参数传错了
  （`nMaxInstances` 应给 `PIPE_UNLIMITED_INSTANCES`、打开模式要用能双向的
  `PIPE_ACCESS_DUPLEX` + `PIPE_TYPE_BYTE` 组合，且客户端要用同样的读写权限打开）。
  **这一条是本轮留下的、最具体的下一步**：把命名管道的参数按文档写对再跑一次对照。
- 本轮**不再继续**（连续三轮未通）：按纪律撤净实验代码、如实记录，把决定权交回人类主人。

### 第 41 轮补充：**ConPTY 续做是"可自动验证"的**（这条会影响"要不要继续"的判断）
- 本侧**能启动 GUI 应用**并读到窗口（实测：`doyah-studio.exe` 起来、标题 `Doyah Studio`、
  内存 24.8 MB、无报错）。
- 本机**有 `psr.exe`**（Windows 自带的"问题步骤记录器" = 程序化截图能力），
  再加上 Win32 的 UI Automation，就能写成"**点开终端页签 → 敲一条命令 → 在输出面上找到预期文字**"
  这种**自动判据**。
- 含义：ConPTY 的续做**不是"只能靠人眼点验"**，可以做成机械判据进闭环（与本项目其余部分的
  做法一致）。**这也说明"要不要继续"是个投入选择，不是可行性问题。**
