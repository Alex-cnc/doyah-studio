# 调研：Windows 版 Doyah Studio 的技术栈候选（2026-09-28）

**性质**：调研笔记（**待需求提出者拍板**，未定稿）；落在本侧 `windows/`，属 `[独占:windows]` 面，不改契约层。
**现状（本文的起点）**：`Docs/概要设计.md` §8.5.1 本侧已选**表示层 = WPF（`net8.0-windows`）**、领域层 = C#/.NET 8 类库、`Cli/` 验证入口、xUnit；**WinUI 3 = 备选**（§8.5.6-3）。选 WPF 的原始理由 = 结果网格虚拟化成熟 + 分发面小（不要求目标机预装 Windows App SDK 运行时）。
**本次调研的判据（需求提出者 2026-09-28 提出）**：以**「界面最精致好看」**为第一判据重排前端候选；后台 = **SQLite 离线存储**、**排除 Java**。

**需求提出者 2026-09-28 补充的两条前提**：① Windows 版是**全新实现、不存在迁移问题** ⇒ 「从 WPF 迁移的成本」不作为判据，按实力重排；② **Linux 第三端（公司环境）现用 = Rust 后台 + Electron 前台**。
**关于 ② 的补充（2026-09-28，同一次口径）**：Linux 端用 Electron 是**被迫** —— 那台机器是**公司资产、系统老旧、没有软件源、装不了最新版本** ⇒ 本侧建议契约侧按**平台差异例外**处置（登记进平台差异表那一路），**不必为此放宽总契约、也不必要求 Linux 端改栈**；契约原文（`需求规范书` §1.2-1 / `P6` 的「无 Electron」）**保持不动**。相应地，Windows 端是否允许 Web 外壳**不能拿 Linux 当先例**，仍须独立拍板。

### ⚠️ 先说一条与契约的冲突（本调研最要紧的发现）

- 契约侧**明写禁用 Electron**：`Docs/需求规范书.md` §1.2-1「**原生体验**：使用各平台**原生界面栈**（具体选型属平台实现，登记于 §10.9），随系统深色模式与缩放，**无 JVM / 无 Electron**」；`Docs/产品能力规划说明书.md` P6「**原生轻量** — 无 JVM / 无 Electron；不为功能引入重量级运行时」（另有 `需求规范书.md:357` 的分层图写着「App 层（平台原生界面栈）」）。
- ⇒ **Linux 端现用的 Electron 与这两条直接相抵**；Windows 端若跟 Linux 走 Web 外壳，撞的是同一条。
- ⇒ 另有一条**口径需要澄清**：「各平台**原生**界面栈」按字面 = macOS SwiftUI/AppKit、Windows WinUI/WPF（**系统控件**）；**Avalonia 是 Skia 自绘**（跨平台一致，但不是系统控件）⇒ 严格读法下它也不满足「原生界面栈」，同时它满足 P6 的「无重量级运行时」。**这一句的宽严由契约侧定**，本侧只报不动笔。

## 一、前端（表示层）三个候选

### A. Avalonia 11 / 12（Skia 渲染 + Fluent 主题 + 全量可重样式）—— **本侧推荐**

- **精致度**：控件模板与样式**全部可由应用替换**（WPF 的样式体系 + 选择器），设计令牌能 1:1 复刻 macOS 侧取值 ⇒ **「像自家产品」的上限最高**；Fluent 主题开箱即现代。
- **与现状的耦合**：领域层、`Cli/`、xUnit **一行不用改**，只换表示层；目标框架由 `net8.0-windows` 变 `net8.0`；分发是**普通 .NET publish**（框架依赖或自包含单文件），**无额外 UI 运行时**。
- **附带收益**：本仓 §8.6 的 **Linux 自用第三端**可直接复用同一套视图；开发与 CI 不强绑 Windows。
- **代价 / 风险**：`DataGrid` 在独立包且样式模型与 WPF 不同 ⇒ §8.5.6-3 那份 50 万行基线要**复测**；与 Windows 系统原生材质（Mica / 标题栏 / 任务栏缩略图）要靠 Win32 互操作补，不是「与外壳同款」；生态与第三方控件少于 WPF。
- **来源**：Avalonia 官方对比页（自述：UI 栈随应用发布、不依赖 Windows 子系统；Avalonia 12 渲染器改为 deferred composition + dirty-rect 追踪，其 35 万元素基准**峰值帧率较 11.x 提升 1867%**）；Avalonia《WinUI vs WPF vs UWP》。

### B. WinUI 3（Windows App SDK 2.x）

- **精致度**：**原生 Fluent**（Mica / 亚克力 / 系统动画），合成动画跑在**合成器线程**、UI 线程忙也不卡 ⇒ **「系统级精致」的上限最高**，与 Win11 外壳天然一致。
- **与现状的耦合**：工程要换成 WASDK 形态；**分发新增运行时依赖**（随附 Windows App SDK Runtime 或自包含）；**Visual Studio 无 WinUI 3 的 XAML 设计器**（官方建议热重载 + 运行中检查）；大网格控件靠 CommunityToolkit（虚拟化可用，但非一等公民）。
- **代价 / 风险**：**Windows-only** ⇒ §8.6 Linux 第三端要另写一份视图；长期性需自评（微软自 2019 起在 WinUI/UWP 上反复调整口径，官方文档同时表态「推荐新原生应用用 WinUI 3」）。
- **来源**：`ctco.blog`《WinUI vs WPF in 2026》（对比表：现代 Fluent = 原生一等公民；Win7/8 不支持；微软主投方向 = WinUI 3、WPF 转维护）；Avalonia 对比页（Windows App SDK **2.0 于 2026-04 稳定**；无 VS 设计器；MSIX 默认打包，未打包需随附运行时）。

### C. WebView2 + Web 前端（React / Vue + TS + 设计令牌 CSS），宿主壳可用 .NET 或 Tauri 2

- **精致度**：**理论上限最高** —— 动效、毛玻璃、渐变、图表与自定义排版都不受控件体系限制，且能直接用 CSS 复刻 macOS 侧设计令牌做**像素级还原**；若将来要 Web 端，视图可同源复用。
- **与现状的耦合**：变成**双栈**（前端 TS + 宿主进程），数据层要么走宿主 IPC、要么前端直连（本侧**不推荐**后者）。
- **代价 / 风险**：50 万行网格依赖前端虚拟化（需重测性能，见 §8.5.6-3 口径）；内存与启动开销高于原生；打包链路更长（前端构建 + 宿主）。
- **来源**：Tauri v2 前置条件页（**WebView2 在 Windows 10 1803+ 已预装**，可直接用；开发需 Rust 工具链）；Tauri vs Electron 2026 对比文（体积 / 内存优势）。

### D.（现状保留项，不在三候选内）WPF + 现代控件库（WPF-UI / Fluent 主题）

零迁移成本、DataGrid 现状基线直接沿用、**契约层一字不用改**；精致度上限**中上**（可仿 Fluent，但控件体系较旧、动效能力弱）。

## 二、后台（SQLite 离线存储）三个候选（排除 Java）

### A. C#/.NET 8 + `Microsoft.Data.Sqlite`（+ Dapper 或 EF Core）—— **本侧推荐（与前端 A/B 同栈同进程）**

- **分发与维护**：NuGet 包**自带原生 SQLite**（免单独分发），EF Core 团队维护；需要 ORM 时用 `Microsoft.EntityFrameworkCore.Sqlite`（迁移可用，注意 SQLite 的改列 = 建新表搬数据）。
- **生产口径（照官方与实战文；这几条决定「离线数据不损坏」）**：① **WAL 从第一版就开**（读不阻塞写、写不阻塞读；该设置**存在库文件里**、只设一次；**网络盘上无效**）；② **`busy_timeout` 必须有**（缺了必遇 `database is locked`）；③ 含写的显式事务用 `BeginTransaction(deferred: false)`（即 `BEGIN IMMEDIATE`），避免读改写中途撞 `SQLITE_BUSY`；④ **备份只走 `VACUUM INTO` 或 `BackupDatabase`**，绝不在运行时复制库文件，也别手删 `-wal` / `-shm`；⑤ **连接池会持有文件句柄** ⇒ 删库 / 换库 / 卸载前先清池；⑥ 库文件放**用户数据目录**（`LocalApplicationData`），**不要写进安装目录**。
- **代价**：无（与推荐前端同栈）。

### B. Rust + `rusqlite`（bundled）/ `sqlx`

- **优势**：单二进制、内存安全、性能与并发上限最高；将来若把重排序 / 重聚合下推到数据层，这里最合适。
- **代价**：**第二工具链**（本机未装 Rust）；与 C# 前端之间要 FFI 或子进程边界，跨语言序列化有成本；迁移生态不如 EF Core。
- **来源**：Tauri v2 前置条件（Rust 工具链为 Tauri 前提）；SQLite 实战文（同族口径）。

### C. Go + `modernc.org/sqlite`（纯 Go，无 cgo）

- **优势**：交叉编译与单文件分发最省事；`database/sql` 心智负担小；无原生依赖。
- **代价**：第二工具链；ORM / 迁移生态弱于 EF Core；同样要跨进程边界。
- **来源**：Go 侧同族实践（单文件 + 纯 Go 驱动为常见组合）；桌面嵌入式库对比文（SQLite = 关系型默认，纯托管方案各有取舍）。

### 备选（不在三候选内）TypeScript / Node + `better-sqlite3`

若前端选 C（WebView2）且要求「单栈」，可让主进程持有 SQLite。但本产品是**桌面本地优先**，把数据层放在 Node 侧会引入额外的进程与打包复杂度 ⇒ 本侧不推荐，仅登记。

## 三、推荐组合与「要动的地方」

**前提变了 ⇒ 结论跟着变**：Windows 是全新实现（无迁移包袱）、Linux 端 = Rust + Electron。于是收敛为两条自洽路线，而不是四个并列候选：

**路线 1 · 守契约的原生路线（本侧推荐）**
- 前端 = **WinUI 3**：唯一同时满足「原生界面栈」（系统控件 + Fluent）与「精致好看」上限的原生选择；代价 = 随附 Windows App SDK 运行时、无 VS XAML 设计器（这一点是否触 P6「不为功能引入重量级运行时」，请契约侧一并认定）。
- 后台 = **A .NET 8 + `Microsoft.Data.Sqlite`**（与 C# 前端同栈同进程，最省心）；若接受跨语言边界，也可选 **B Rust**（与 Linux 同语言，为将来共享 core 留门）。
- 代价：Windows 与 Linux 两端**前后都不共享代码**。

**路线 2 · 跨端复用路线**
- 前端 = **Web（与 Linux 的 renderer 同源）**，外壳用 **WebView2**（系统自带、不打包 Chromium ⇒ 不触「无 Electron」字样，但仍触「原生界面栈」的字面）；后台 = **B Rust**（与 Linux 同核）。
- 收益：renderer 层与 Rust core 有**一次写两端用**的可能。
- 代价：① 仍是 Web 视图 ⇒ 必须请契约侧对 §1.2-1「原生界面栈」给宽严；② Linux 的 Electron 外壳 API（Node / Electron IPC）在 WebView2 宿主里**不存在** ⇒ 只能共享 renderer 与 core，**不能共享外壳**；③ 50 万行网格要走前端虚拟化、须复测。

**后端三候选（SQLite、排除 Java）在两条路线下都成立**：A .NET 8 + `Microsoft.Data.Sqlite`〔路线 1 首选〕/ B Rust + `rusqlite`〔路线 2 必选；路线 1 也可选〕/ C Go + `modernc.org/sqlite`〔单二进制最省事，但两端都不沾〕。

**改选要动的地方（重要）**：
- `§8.5.1`（本侧 `[独占:windows]` 节）—— 表示层 WPF → 新选型，**本侧可直接改**；
- **契约层三处** ⇒ **必须走 `Docs/proposals/`**：① `§3` 的 GUI 框架行（现写 Windows = WPF）；② `P-19` / `P-23` / `P-24` 三行里的 WPF 字样；③ **新增**：`需求规范书` §1.2-1 与 P6 的「无 Electron / 原生界面栈」需给定宽严（否则 **Linux 端现用的 Electron 已是无依据的例外**）；
- `§8.5.6-3` 的 50 万行基准是 **WPF 口径**，换前端后**须复测**（旧基线不得当依据）。
