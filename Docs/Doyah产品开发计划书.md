# Doyah 产品开发计划书

> 文档编号 `PC-PLAN-001` · 维护：契约侧 · 上游 = 《Doyah 产品需求分析说明书》
>
> **这本书只回答一件事：哪一条做到哪儿了。** 要什么、验收怎么算 → 需求分析说明书；是什么、边界在哪 → 能力规划说明书；怎么做 → 概要设计说明书。

## 1 定位

### 1.1 四件文档的分工

| 文档 | 回答 | 不写什么 |
|---|---|---|
| 产品能力规划说明书 | **是什么** | 状态、进度、实现 |
| 产品需求分析说明书 | **要什么**（含验收判据） | **状态、进度** —— 一律在本文件 |
| 产品概要设计说明书 | **怎么做** | 不改变「要什么」 |
| **产品开发计划书**（本文件） | **做到哪了** | 不定义需求、不改验收判据 |

**依赖单向**：能力规划 → 需求分析 → 概要设计 → 开发计划。下游可以引用上游的编号，上游不引用下游。

### 1.2 状态口径

| 符号 | 含义 | 谁能改 |
|---|---|---|
| ⬜ | 未开始 | 动手的那一方，提交时同批改 |
| 🟡 | 部分实现（落了一半，或只在某一端落） | 同上 |
| ✅ | 已实现**且**已按验收判据验过 | 同上；只有判据跑过才能翻 |
| ➖ | 评估后不做（写清理由） | 同上 |

**三条纪律**：

1. **状态只有一处**：本文件。需求分析说明书里出现状态符号即为疏漏（门禁 `Scripts/check-doc-tables.py` 现在查这一条）。
2. **翻 ✅ 要有证据**：附判据名或命令读数；判据没跑过就翻 ✅ 视为假绿。
3. **编号是锚**：本文件编号与需求分析说明书 §10.1 索引一一对应，不许自增、不许合并、不许漏。
