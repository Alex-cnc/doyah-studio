## 0. 用法（贴给新助理时先读这一段）

**这份 spec 是两侧共享台账（2026-09-27 撤隔离后）。**

- ✅ **可以**贴给：本机（macOS）的助理、需求提出者自己、任何要接着做 **Doyah Studio** 的助理。
- ✅ **可以贴给**：Windows/Android/鸿蒙 平台侧开发助理（小河马）。**2026-09-27 起信息隔离撤销**，两侧平等、共享三书与本台账（见 §1.3）。

**接手第一天按顺序做四件事**：
1. 读 §1 项目全貌 + §2 铁律（不读铁律会立刻犯低级错误）；
2. 按 §3 跑一次两边的门禁，确认基线是绿的（不绿先修基线，别急着做功能）；
3. 从 §5 任务清单里挑**「不需用户到场」**那一类直接做 —— 这是需求提出者最想要的效果（他原话：「要你做的事情太多太杂需要我一直守在电脑或手机前指挥，太累了」）；
4. 做完一件，按 §8 格式更新这份 spec，并提交。

## 2. 铁律（违反就是返工）

1. **状态只在验证之后改**。代码写完不算完成，跑过脚本/单测拿到 exit 0 才算；SRS 状态位与"已完成"的宣称都要有命令输出支撑。
2. **需求登记要一次性做完**。一条新需求登记会派生 **6 个出口**：正文定义行 / §10.1 索引（含表头计数）/ §10.2 追溯表 / §10.10 平台等价矩阵 / 规划书能力地图 / 变更记录。漏一个，门禁会红。
3. **文档改动必须过门禁** —— 清单与每项口径见《概要设计》§8.3；实跑 `./Scripts/verify-all.sh`，**项数只认它的收尾行 + `Scripts/doc-numbers.json`**（本台账不写死，见 §3.1）。
4. **不要弹窗要授权**；需要授权的项**写进文档记录**（"待授权/待拍板"），不要因为等确认而停工 —— 能做的一律先做，做完登记。
5. **提交信息写清楚**：中文、说明改了什么 + 派生出口 + 验证结果（哪条命令、什么结果）。
6. **不擅自改外部状态**：不在别人的数据库上建库/改 `pg_hba.conf`；不在本机装 MySQL 之类只为跑测试的实例 —— **只给命令，不执行**（口径真值源 = 《需求规范书》§0.9；本台账只作指针）。
7. ~~每台克隆机器各装一次隔离钩子（Notes 仓）~~ **2026-09-27 作废**（隔离撤销）：Notes 仓的 `isolation-check` 层随之下线（队列 L-28）。
8. **Studio 仓是 PUBLIC**：不要把凭据、内网地址、个人内容写进会被推送的文件；敏感/运营类文档放 `Docs/` 下未入库位置（`.gitignore` 默认忽略 `/Docs/*`，只白名单放行三书与 `Docs/design/*.md`）。
9. **删除前确认范围**：需求提出者说"清理掉"可能只指部分文件，不是整个目录。
11. **文档体系只认「四书一单」**（口径见 §11）：四书 = 能力规划 / 需求规格 / 概要设计 / 详细设计-<端>；一单 = 开发计划任务清单。**不许新建第六本书、索引、台账或各类清单**；门禁要的中间产物落 `.build/`。
10. **开工先看工作区**：任何一轮工作开始前先 `git status --short`。**工作区已有未提交改动时，不许直接在上面续改** —— 先判归属（上一轮残work / 另一位助理 / 需求提出者手改）再动手；**永远不要 `git add -A` 一把梭**把不明改动提交进去。原因：循环间隔可能短于一轮工期，两个轮次会叠在同一棵工作区上。

每次收到新的任务清单或拍板确认，**追加**（不要覆盖历史）：


**规矩**：

5. **并发写版本号必须先重读文件**（2026-09-26 教训）：循环在跑时，三书的版本号随时在涨 —— **不要凭记忆或上次的值硬编码新版本号**，一律先正则读出当前最高号再 +1，否则会撞出重复的变更行（表格门禁也会红）。

## 10. 计数方法（可复跑；数字不许靠印象）

## 11. 产品文档体系：四书一单（通用要求，产品无关）

> 本节是**跨产品的通用要求**：任何产品都按这一节组织文档；产品名不进本节。人类主人 2026-10-26 第二次强调原话：
> 「整个项目只有四书一单 … 任何产品的四书都由大河马统一输出 … 这是唯一的口径，不要再给我自行新建乱七八糟的索引和清单出来了」。

### 11.1 五件套（唯一）

| 位置 | 书 | 写什么 |
|---|---|---|
| ① | **《X产品能力规划说明书》** | 能力点（是什么 / 不是什么 / 边界）、能力地图；不引下游编号 |
| ② | **《X产品需求规格说明书》** | 需求条目（六列：编号 / 需求 / 判据 / 优先级 / 状态 / 来源）、验收判据、验收总表 |
| ③ | **《X产品概要设计说明书》** | 组件表、契约 (`P-xx`)、ADR、跨端约束；不写实现细节 |
| ④ | **《X产品详细设计说明书-<端>》** | 七件套契约、追溯矩阵、用例定义、实现约束 |
 - **《X产品开发计划任务清单-<端>》**（一单）—— **只给正在开发的端建，每端一份活件**（人类主人 2026-10-26 令：「清单应该只有 macOS 和小河马的安卓端」）：
   现有两份 = `-macOS端`（本侧开发主体）+ `-Android`（小河马侧，2026-10-26 定为最新且唯一）。其他端（Windows / Linux / HarmonyOS / iOS）**有详设、不建清单**，真开工时再加。
   **每端只许一份**：同一端出现第二份清单即判红（`check-end-sheets` 判据 A2）；旧写法 `-安卓端` 已归档，不许复活。
   **不设产品级总单**（同令：「不应该有一个 Doyah产品开发计划任务清单.md 文件」）。
   单册内：需求状态台账（该端状态唯一来源）+ 版本计划 + 批次 + 变更记录；日报从这里取数。
   跨端视图（平台矩阵 / 按平台清单 / 需求索引）不是书，是派生件 ⇒ 落 `.build/derived/`；`Scripts/check-end-sheets.py` 钉死这三条。
 - **版本纪律（人类主人 2026-10-26 令）**：**任务清单永远只有一份活件，不做版本快照**；
   四书才有版本 —— 目前 v1.0 冻结在 `Docs/frozen/`（四份），**不带版本号的是活书**（持续演进、阶段冻结）；
   活书从冻结件复制而来，漂移积累到该冻结时问人类主人是否冻结新版本，同意才 `Scripts/freeze-books.py`。

- 四书**由大河马统一输出**，端不各写一套；详设按端分册（`-macOS端` / `-Android` 等），端名只出现在详设文件名里。
- 一单**与详设同构、按端分册**：详设有 `-macOS端`，一单就有 `-macOS端`；日报从本端那一份取数。
- 一单是**唯一进度源**：日报、周报、进度表一律从它取；不许另开「里程碑清单」「按平台任务清单」当第二本。
- **各端的一单一律只认同端详设「活书」版**（人类主人 2026-10-26 令）：`任务清单-macOS端` 只认 `详细设计说明书-macOS`，
  `任务清单-Android` 只认 `详细设计说明书-Android`；**不许引别端详设**，**不许把 `Docs/frozen/` 的冻结件当上游**。
  `check-end-sheets.py` 判据 I 钉死：同端活书缺失即红、头部没写同端端名即红、头部出现别端详设即红、头部出现 `-vX.Y-<日期>.md` 冻结件名即红。
- `Docs/` 根目录**只许四书 + 一单**（判据 H，`check-end-sheets.py`）：四书 = 能力 / 需求 / 概要 / 详设-<端>（附 `-变更记录`、`-追溯表`）；一单 = `任务清单-macOS端`、`任务清单-Android`。
  仅额外容忍三件**工程件**：`README.md`、`智能体助手-开发规范.md` / `Doyah项目开发规范.md`（写「怎么做活」，不是产品书）、`模板-详细设计说明书-Studio.md`。
  **其余一律不许待在根上**：发布说明、发布方案/计划、人工点验清单、手工验收手册、功能清单、兼容性矩阵、测试用例、里程碑清单、按平台清单、调研书、项目评审、各类记录/草案/接管记录 —— 过程件全部进 `Docs/archive/`（20261026 根目录清理见 `Docs/archive/root-20261026/INDEX.md`）。

### 11.2 编号形制

- 五段式：`<FR|NFR|AC>-<产品码>-<面>-<域>-<三位序号>`，例 `FR-STD-DB-DRV-005`。
- **面**：`ALL`（所有面）/ `WS` / `DB` / `CLI` 等；**域**：能力域码（`DRV` / `CONN` / `SESS` / `META` / `NAV` / `UI` / `CLI` / `SEC` / `DATA` / `IFACE` …）。
- **`DATA` / `IFACE` 是合法域码**（数据需求 / 接口需求），不是「上一版编号体系」。判一个编号该不该存在，看**冻结件里在不在**，
  不看它「长得像不像章节名」—— 2026-10-26 我把 `FR-STD-ALL-DATA/IFACE-*` 误判成旧号删掉 v1.0 正式条目，是反例。
- 风险不是需求：风险用 `R-001` 形制；`NFR-*-RISK-*` 不许再出现。
- 状态符号（✅ / 🟡 / ⬜）不许进需求定义行；状态只在一单与台账里。

### 11.3 冻结与活书（活书 ← 冻结版）

1. `Docs/frozen/` 存**冻结快照**（四书逐字复制 + 头部两行横幅：`【冻结版 vX】` / `冻结规则`）；
2. **活书 = 从冻结版复制出来的一份**；在活书上干活，差异自然长大；
3. `python3 Scripts/check-frozen-sync.py`：逐本算差异行数，**阈值 40 行** —— ≤ 阈值静默继续；> 阈值即**决策点**，
   去问人类「要不要冻结成新版本」；
4. 他同意才 `python3 Scripts/freeze-books.py --version vX.Y --note "…"`（复制 + 重写 `Docs/frozen/README.md` 清单 + `--strict` 自证）；
5. **禁止**未经同意把活书刷进冻结件 —— 那等于改掉他冻的基线；`--strict` 只在刚冻结完时用。
6. 比对时**必须剥掉横幅**（`**【冻结版` / `**冻结规则**`），否则每本虚报 +2 行。

### 11.4 派生件与中间产物

- 门禁要的对账数据落 `.build/`（生成物、不入库、不进 `Docs/`）：`requirement-index.jsonl` 一类。
- **变更记录属于书自身的版本史**，写在书内（或该书专属的 `-变更记录` 附录），不另开「索引」。
- 「需求索引」「追溯表」「里程碑清单」「按平台任务清单」「各种台账」**都不是书**，不得与四书并排；它们的内容归属见 11.1 表右列。

### 11.5 日报与进度

- 日报三段：**做了什么（对应一单条目号）· 门禁/读数 · 阻塞**；进度数字只从一单取，不复述过程、不引二手清单。
- 一单的状态词只许 `todo / doing / blocked / done`；版本计划写在同一份单的版本计划节里。

### 11.6 门禁（改文档必跑）

`./Scripts/verify-all.sh` 为准；其中与本体系直接相关的：`check-frozen-sync`（冻结基线漂移）· `check-doc-versions`（版本号与头部）
