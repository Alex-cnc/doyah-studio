# 通用开发规范

## 1 铁律（违反就是返工）
1. **第一刀是纵切，不是横切**：从零起的功能，第一轮只许打通一条**最小的端到端路径** —— 数据库能存进去 → 后台能拿出来 → 页面能显示出来，哪怕功能简陋、页面只有一个按钮；**反面**是先花两天把数据库层做完、再花两天把后台做完、最后做页面 —— 那样「这三层接不起来」要等全部写完才暴露，方向错了也来不及。判据：评审（交接说明必须写清本轮走通的那条纵切 + 它的验证命令与输出；只报「某层完成」= 不合格）。
2. **状态只在验证之后改**：代码写完不算完成，跑过脚本/单测拿到 `exit 0` 才算，宣称「已完成」必须附那行输出。判据：`./Scripts/verify-all.sh` 或 `./Scripts/verify-core.sh` 的收尾行。
3. **开工先看工作区，提交只加本片文件**：先 `git status --short`；有未提交改动先判归属（上一轮残work / 另一助理 / 主人手改）再动手。**永远不用 `git add -A` 一把梭** —— 一梭下去会把这四类一起带上：① **本机台账与运行态**（`.agent/`、`Docs/开发记录-*.md`、`Docs/design/`：每轮都在写、含本机路径，靠微云备份）；② **派生件**（`.build/derived/`、`dist/`：可机械重生成，进了库没法 diff）；③ **私物**（`.secrets/`、`.backups/`、`_transfer_*.md`、`.DS_Store`、`*.xcuserstate`）；④ **别人的未提交改动**。另注：`Docs/` 下**默认不入库**（`.gitignore` 的 `/Docs/*`），只有白名单里的四书一单 + 工程件 + 规范 + `frozen/` 才进 —— **新增文档要入库得同时改白名单**，否则它只活在本机（`git status` 里看不见它，clone 出来也没有）。判据：评审 + 提交前 `git status --short` 逐条说明；`git diff --cached --name-only` 必须与本片文件清单一致。
4. **提交信息中文写清三件**：改了什么 + 派生出口 + 验证命令与结果。判据：评审（`git log -1`）。
5. **不弹窗要授权**：需要授权/拍板的写进队列「待授权/待拍板」，能做的一律先做，**不许因等确认停工**。判据：`Scripts/check-queue-needs-user.py` + 评审。
6. **不擅自改外部状态**：不在别人的库上建库、不改 `pg_hba.conf`、不为跑测试在本机装 MySQL —— **只给命令，不执行**。判据：评审（口径真值源 = 《产品需求规格说明书》§0.9）。
7. **删除前确认范围**：「清理掉」可能只指部分文件，不是整个目录。判据：评审。
8. **Studio 仓是 PUBLIC**：凭据、内网地址、个人内容不进会被推送的文件。判据：`git check-ignore -v <文件>` + 评审。
9. **文档改动必过门禁**（清单见 §4）。判据：`./Scripts/verify-all.sh`。
10. **不擅自扩大文档体系**：只认 §2 的四书一单，不许新建第六本书 / 索引 / 台账 / 清单，门禁要的中间产物落 `.build/`。判据：`Scripts/check-doc-invariants.py`、`Scripts/check-end-sheets.py`。
11. **报数报「还剩多少」**：不许只报扫描覆盖面，「已登记」≠「已修完」，数字不许靠印象。判据：`Scripts/check-doc-numbers.py` + 评审。
12. **一条拍板只落一处结论**：同一状态散在多本册子只改一处必留矛盾 ⇒ 状态唯一源 = 一单。判据：`Scripts/check-status-consistency.py`。

13. **判据必须声明覆盖范围**：任何「报缺失 / 报异常」的判据，先说清它扫了哪些目标源、哪些没扫；**覆盖不全时只许报「未知」，不许报「发现」**。原因不是洁癖：主人自己做过四次「悬空引用」检测，四次都因覆盖不全出假阳性（48 → 29 → 作废 → 23），**坏判据比没有判据更危险** —— 没有判据时人会去核对，假阳性会让人把真的当成假的、把假的当成真的。判据：脚本 `--json` 输出里必须有 `sources`（已覆盖）/ `uncovered`（未覆盖）两段；`uncovered` 非空而结论报「发现」即红；评审时看交接说明有没有写这两段。
14. **每条判据配一条「必须判红」的负例**：正例只证明它能通过，负例才证明它真会拦。新写或改写的门禁，必须同时交一个**故意违规的样本**（临时文件 / 单测用例），证明它确实红；这条不是新习惯 —— 已有的「0-token 门控」（同一触发连来两次 ⇒ 第二次 0 请求）就是同一条纪律，现在推广到全部判据。判据：`Scripts/test-verify-all-gate.py` 以及各门禁自己的自测用例；新增门禁若无负例用例即红（评审 + 自测计数行）。
15. **独立验收层：判「对」的依据不许由被判方提供**：生成 spec / 代码 / 测试的同一个模型，不能同时判定自己生成的东西「对」。判「对」只认三样 —— **人类主人原话** / **契约条文**（四书里的判据行）/ **外部权威系统**（编译器、测试框架、真实设备）。这是 #2「状态只在验证之后改」的加强版：不但要附验证输出，**验证的判据本身也不能由被验者写**。判据：评审 —— 交接说明里每条「已完成」要指名依据属于以上哪一类（口径编号 / 主人原话 / 命令输出），只写「我验过了」= 不合格。

## 2 四书一单（唯一文档体系，产品无关）
| 位置 | 书 | 写什么 |
|---|---|---|
| ① | 《X产品能力规划说明书》 | 能力点（是什么 / 不是什么 / 边界）、能力地图；不引下游编号 |
| ② | 《X产品需求规格说明书》 | 需求条目（编号 / 需求 / 判据 / 优先级 / 状态 / 来源）、验收判据 |
| ③ | 《X产品概要设计说明书》 | 组件表、契约 `P-xx`、ADR、跨端约束；不写实现细节 |
| ④ | 《X产品详细设计说明书-<端>》 | 七件套契约、追溯矩阵、用例定义、实现约束 |
| 单 | 《X产品开发计划任务清单-<端>》 | 该端需求状态台账 + 版本计划 + 批次；日报从这里取数 |

- **PC 一体化：Agent / Studio / Notes / Retro 四个功能写在**同一份**全量四书里**（人类主人 2026-11-01 重申）：PC 三端是同一产品的四个功能面，不是四个产品 ⇒ 能力 / 需求 / 概设 / 详设各只有一本全量书，不许按功能各立一套。判据：`Docs/` 根只认这四个功能合写的书（`check-doc-invariants.py` 白名单）。
- **Notes / Retro 是独立产品，独立仓里的四书是「分册」**（同 Tuner 的形态）：分册**来自全量四书，只裁剪不增删** ⇒ 分册出现的每个编号都必须能在全量四书里找到（`分册 ⊆ 全量`）；**唯一例外是任务清单** —— Notes / Retro 各记各的，全量 Studio 仓也有自己那份（`-macOS`）。违规分两种：分册有、全量无 ⇒ **全量漏登**；分册改条文 ⇒ 越权。判据：`Scripts/check-book-subset.py`（负例：分册塞一条全量没有的编号 ⇒ 必须判红）。
- **四书由大河马统一输出**，端不各写一套；详设按端分册，端名只出现在详设文件名里（2026-10-26 定）。判据：评审（谁落笔看 git 作者）。
- **一单只给正在开发的端建、每端一份活件**（现 = `-macOS` / `-Android`）；其他端有详设、不建单，真开工时再加；**不设产品级总单**；旧写法 `-安卓端` 不许复活。判据：`Scripts/check-end-sheets.py`（判据 A2）。
- **一单永远只有一份活件，不做版本快照**；只有四书有版本。判据：同上。
- **一单与详设同构、按端分册，只认同端详设活书**：不许引别端详设、不许把 `Docs/frozen/` 冻结件当上游。判据：同上（判据 I）。
- **一单是唯一进度源**：日报 / 周报 / 进度表一律从它取，不许另开「里程碑清单」「按平台任务清单」当第二本。判据：`Scripts/check-plan-coverage.py` + 评审。
- **`Docs/` 根只许四书 + 一单**（+3 工程件：`README.md`、本件与《项目管理规范》、详设模板）；发布说明 / 点验清单 / 功能清单 / 调研书 / 各类记录等过程件一律进 `Docs/archive/`。判据：同上（判据 H）+ `Scripts/check-doc-invariants.py`（17 份白名单）。
- **跨端视图不是书**：平台矩阵 / 按平台清单 / 需求索引 / 追溯表 / 各种台账都是派生件 ⇒ 落 `.build/derived/`，不得与四书并排。判据：同上（判据 H）。
- **平台详设以 macOS 为基准派生，不各写一本**（2026-11-05 人类主人定法：「有了 macOS 的详细设计并验证通过了绝大多数条目，其他平台端的详细设计就好做了 —— 参考 macOS 版本的设计，根据平台差异进行调整即可」）：每本《X产品详细设计说明书-<端>》(macOS 除外) 必须 ① 头部写「派生自 `Docs/Doyah产品详细设计说明书-macOS.md` vX」；② 有一节差异登记，对着**本族基准**详设 §3 的每一节表态 —— 基准按族定：**PC 族（Windows / Linux）= macOS；移动族（iOS / 鸿蒙）= Android**（安卓已开发完，是移动族基准本体，不再回头补它自己的详设；iOS 按主人 2026-11-05 令「参考安卓来做详设」）； —— `沿用` / `差异` / `不适用`，后两者必须给依据或本端落点；③ 每有 macOS 详设新增一节（如 §3.29 / §3.30 这类真机缺陷补登记），各端差异登记同批补行，不是等排期。本条判的是「有没有逐节表态」，判不了「表得对不对」——后半由各端测试与骨架判据负责。判据：`Scripts/check-platform-derivation.py`（红=还有端没表过态）。
- **编号形制五段式**：`<FR|NFR|AC>-<产品码>-<面>-<域>-<三位序号>`（例 `FR-STD-DB-DRV-005`），`DATA` / `IFACE` 是合法域码。判据：`Scripts/check-req-ids.py`。
- **风险不是需求**：风险用 `R-001` 形制，`NFR-*-RISK-*` 不许再出现；状态符号不许进需求定义行。判据：`Scripts/check-req-ids.py` + `Scripts/check-plan-coverage.py`。
- **新需求登记一次性落齐派生出口**：正文定义行 → 需求索引 → 追溯表 → 平台等价矩阵 → 能力地图，漏一个门禁红。判据：`Scripts/check-req-index.py`、`Scripts/check-req-ids.py`、`Scripts/gen-platform-parity.py --check`、`Scripts/check-plan-coverage.py`。

## 3 版本与计数
- **版本只写头部**：活书 `v<冻结段>.NNN`，第三段 = 自冻结起第几次改动，**上限 999**；改正文就 +1。判据：`Scripts/check-doc-versions.py`。
- **冻结 = 升一段**：`v1.0.NNN` 定稿冻结 ⇒ 冻结件 `v1.1`（`-v1.1-YYYYMMDD.md`），活书继续 `v1.1.NNN`；历史两段式旧号原样留作追溯，门禁只跟三段式比。判据：同上。
- **自动冻结（2026-11-01 人类主人令）**：`v1.0.NNN` 的流水段到 **999 就不再自增** —— 该段必须先冻结**这一版**（逐字一致：`python3 Scripts/freeze-books.py --version v1.0`），活书随即转下一段 `v1.1.0` 继续；**这两个动作都不等人发话**，是版本号本身触发的。判据：`Scripts/check-doc-versions.py`（流水 = 999 且没有该段冻结件 ⇒ 红；> 999 ⇒ 红）；取号：`Scripts/next-doc-version.py`（读到 999 自动给出 `vA.(B+1).0`，不会给 1000）。
- **并发写版本号先重读文件**取当前最高号再 +1，不许凭记忆或上次的值硬编码。判据：`Scripts/next-doc-version.py`。
- **不许有「变更记录」文件，书里也不写变更历史**：逐轮改了什么看 git 提交。判据：`Scripts/check-doc-versions.py`（出现变更记录节、或引用旧变更记录件即红）。
- **冻结件只能冻结、不许手改**：漂移 40 行 = 决策点，问主人是否冻结，同意才 `Scripts/freeze-books.py --version vX.Y`。判据：`Scripts/check-frozen-sync.py`。
- **数字与路径都不写死**：项数 / 例数唯一来源 = `verify-all.sh` 收尾行 + `Scripts/doc-numbers.json` + `Scripts/self-test-counts.json`，需求计数 = `Scripts/report-requirements.py`；计数在仓根调仓内脚本、别仓走各自入口，文档里不写本机绝对路径。判据：`Scripts/check-doc-numbers.py` + `grep -rn '/Users/' Docs --include=*.md` 为空。

## 4 门禁
- **唯一入口**：Studio `./Scripts/verify-all.sh`（只验 Core 用 `./Scripts/verify-core.sh`）｜ Notes `bash tools/logic-check/run.sh` ｜ Retro `bash tools/verify-all.sh`。判据：跑它本身，`exit 0` 才叫门禁绿。
- **首红即退** ⇒「只剩一处红」是伪读数；要一次跑完用 `--keep-going`。判据：`Scripts/test-verify-all-gate.py`。
- **每轮交接三件**：`check-doc-numbers.py` + `check-release-version.py` + `check-self-test-counts.py`，三条都跑（各 `exit 0`）才算交接。判据：这三条本身。
- **文档体系相关**（清单与每项口径的唯一来源 = 《产品概要设计说明书》§8.3）：`check-frozen-sync` · `check-doc-versions` · `check-doc-tables` · `check-doc-invariants` · `check-end-sheets` · `check-plan-coverage` · `check-req-index` · `check-req-ids` · `check-p-parity` · `check-exclusive-sections`。判据：`./Scripts/verify-all.sh`（已接线）。
- **契约层锁定**：无 `[独占:*]` 标记的节 = 契约层，只有大河马可改；他侧走提案或注 `contract-change：理由`；台账类节标 `[开放]`。判据：`Scripts/check-exclusive-sections.py`。
- **提案通道**：动契约层先提 `Docs/proposals/NNNN-短标题.md`（状态 / 提出方 / 影响面 / 关联提交 SHA），采纳后由 macOS 侧落笔。判据：`Scripts/check-exclusive-sections.py` + 评审。

## 5 交接
- **接手第一天四步**：① 读 §1 → ② 跑门禁确认基线绿（不绿先修基线，别做功能）→ ③ 从一单挑「不需用户到场」的直接做 → ④ 做完更新文档并提交。判据：评审。
- **换环境 / 换助理**：本件 + 《项目管理规范》整份贴过去即可接手；拍板原话与逐笔记录在 `Docs/archive/过程记录-20261026/`，只在追溯时查。判据：评审。
- **日报三段**：做了什么（对应一单条目号）· 门禁/读数 · 阻塞；数字只从一单取；一单状态词只许 `todo / doing / blocked / done`。判据：评审。
- **引用他的话与数字必须逐字**，不许润色；每条结论都要能指到出处（四书条文 / 派单单号 / 提交）。判据：评审。
