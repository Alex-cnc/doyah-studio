# 通用开发规范

## 1 铁律（违反就是返工）
1. **第一刀是纵切，不是横切**：从零起的功能，第一轮只许打通一条最小的端到端路径（存进去 → 拿出来 → 显示出来），哪怕只有一个按钮。
- **归属环节**：全局
- **不是什么**：不是「先做完数据库层再做后台再做页面」；也不是「每层都完成一点」—— 三层接不起来要等全部写完才暴露。
- **判据**：【人判】交接说明写清本轮走通的那条纵切 + 它的验证命令与原始输出，由接收方核对这份输出；只报「某层完成」= 判错。 **覆盖范围**：只看「本轮是否有一条端到端路径被真跑通」，看不到广度够不够（广度由需求条数与一单批次回答）。
- **负例**：【人判】交接写「数据库层已完成、后台待接入」而没有任何一条端到端命令输出 ⇒ 接收方必须退回。
- **读数口径**：报「本轮纵切：命令 + 输出行数」，不报各层完成度。
- **归属**：本节；判据形态（人判）改机判需另立脚本。

2. **状态只在验证之后改**：代码写完不算完成，跑过脚本/单测拿到 `exit 0` 才算，宣称「已完成」必须附那行输出。
- **归属环节**：全局
- **不是什么**：不是「写完代码就算完成」，也不是「跑了一条命令就算」—— 必须是本条要求的那个验收入口。
- **判据**：【机判】〈落点 #01〉（或只验 Core 的 〈落点 #02〉）收尾行 + 〈落点 #03〉 的 `Executed N tests`。
- **覆盖范围**：只判收尾行存在且 0 失败，判不了这次跑是不是在干净树上（脏树读数不算，见 §4.1），也判不了你报的状态对应的是不是这次改动（2026-11-18 补：铁律 13 落地）
- **负例**：改完代码没跑 〈落点 #100〉 就写「已完成」⇒ 交接时无收尾行，接收方判错。
- **读数口径**：报「入口 / 收尾行原文 / 失败数」三件。
- **归属**：本节。

3. **开工先看工作区，提交只加本片文件**：先 `git status --short`，判清归属再动手；提交只 `git add` 本片文件。
- **归属环节**：全局
- **不是什么**：不是「工作区干净才允许开工」；`git add -A` 一律禁止 —— 它会同时带上本机记录、派生件、私物、别人的未提交改动四类。
- **判据**：【机判】`git status --short` 逐字判归属 + 提交里出现 待办流水文件、构建产物目录、`dist/`、`.secrets/`、`_transfer_*`、`*.xcuserstate` 任一即红【脚本：〈落点 #04〉】；【人判】归属判断由本人在提交信息里写明（残余 / 另一助理 / 主人手改）。
- **覆盖范围**：机判只判「提交里出现了禁用路径」，判不了哪些算本片文件（归属由本人在提交信息里写明，属人判）（2026-11-18 补：铁律 13 落地）
- **负例**：改**对侧子树**（对侧端独有的目录）⇒ 路径归属判据判红「对侧子树」（2026-11-10 实测）；改共享面（文档目录 / 脚本目录）而新增行不注 `shared-surface：理由` ⇒ 判红「共享面未登记」。
  **补正**：原文负例写「`git add -A` 后带上 `派生件区/x.md`」—— 提交动作不在文件层，构建产物目录 又在忽略清单里，`git diff` 根本看不到它；这条判据真正能拦的是「路径归属」，不是「`git add` 的写法」。
- **读数口径**：报「本片文件数 / 未提交残余数」。
- **归属**：本节；白名单另见 `.gitignore`。

4. **提交信息中文写清三件**：改了什么 + 派生出口 + 验证命令与结果，三件缺一即不合格。
- **归属环节**：全局
- **不是什么**：不是「写了标题就算」；也不是「验证结果是『已跑』」—— 必须贴命令与输出行。
- **判据**：【人判】接收方读 `git log -1`，三件缺一即判错（提交信息是本条唯一被验对象）。 **覆盖范围**：只看 `git log -1` 的三件是否齐，不判三件内容是否正确（内容由对应判据判）。
- **负例**：【人判】提交信息只有「修 bug」四个字 ⇒ 判错退回。
- **读数口径**：报「三件：齐/缺哪件」。
- **归属**：本节。

5. **不弹窗要授权**：需要授权或拍板的进队列，能做的一律先做，不许因等确认停工。
- **归属环节**：全局
- **不是什么**：不是「等主人回话才继续」；也不是「把要授权的事自己做了」—— 前者停工，后者越权。
- **判据**：【机判】〈落点 #05〉（队列行**状态词**在词表内 + `needs-user` 行**点名**到仍待拍的号）；【人判】「这件事该不该问主人」「有没有绕过队列直接做了」由本人判。
- **覆盖范围**：机判只判队列状态词与 `needs-user` 点名，判不了「这件事该不该问主人」和「有没有绕过队列先做了」（2026-11-18 补：铁律 13 落地）
  **曾经的错指向**（2026-11-10 实测）：原文写「待拍板项**必须在队列里**」。该脚本只做点名 / 仍未决 / 挂起理由 / 查无此号四件事，**没有第二份来源可比「是否都在队列里」**；队列文件还在 `.gitignore` 内（干净克隆整段跳过）。已按实改口径。
- **负例**：需要主人授权的动作没进队列而直接在提交里做了 ⇒ 判错（人判：〈落点 #05〉 判不了「该不该问主人」，它只判队列行的状态词与点名）。
- **读数口径**：报「队列新增 N 条 / 已自行完成 M 条」。
- **归属**：本节（要拍板的事进项目规范的队列，不进本册）。

6. **不擅自改外部状态**：不在别人的数据库上建库建号、不改数据库服务的**认证配置**、不为跑测试在本机装服务 —— 只给命令，不执行。
- **归属环节**：全局
- **不是什么**：不是「只读操作也要问」（查连接、看报错、跑只读查询都不用授权）；也不是「本地环境随便装」—— 装服务同样算改外部状态。
- **判据**：【人判】执行记录里有没有对他人库 / 系统配置的写操作，由本人自查 + 交接说明注明；判定口径与**具体对象**（哪台机、哪份配置文件）属项目事实，本册不写，也不指节号。 **覆盖范围**：只看交接说明里有没有「已执行」的外部写动作及其授权来源，看不到命令是否真被执行。
- **负例**：【人判】为跑测试在自己机器上装一个数据库服务，并写进交接当「已就绪」⇒ 判错。
- **读数口径**：报「给出命令 N 条 / 已执行 0 条」。
- **归属**：本节。

7. **删除前确认范围**：「清理掉」先确认是部分文件还是整个目录，范围写进命令再执行。
- **归属环节**：全局
- **不是什么**：不是「先删再问」；也不是「备份了就能删」—— 备份不是授权。
- **判据**：【人判】删除命令必须带明确路径通配并在此前贴出 `ls` 结果，由本人核对。 **覆盖范围**：只看删除前是否贴出范围清单，不判清单是否完整（完整性靠事中复核）。
- **负例**：【人判】收到「清理掉旧包」直接 `rm -rf dist/` ⇒ 判错（只该删过期的单个文件）。
- **读数口径**：报「待删 N 个 / 实删 N 个 / 保留 N 个」。
- **归属**：本节。

8. **公开仓不留凭据 / 内网地址 / 个人内容**：会随提交进入公开仓的文件里不许有密钥、内网地址、他人的个人内容。
- **归属环节**：全局
- **不是什么**：不是「删了提交历史就干净」（历史不重写，污染了就得换密钥）；也不是「私有仓可以放」—— 按每个仓自己的公开性判；**哪些仓是公开的属项目事实**，本册不写。
- **判据**：【机判】〈落点 #06〉（扫待推送文件的凭据/内网地址模式）；〈落点 #07〉 确认忽略规则命中。
- **覆盖范围**：只判待推送文件里有没有凭据 / 内网地址模式，判不了没有固定模式的个人内容（那要读内容，人判）（2026-11-18 补：铁律 13 落地）
- **负例**：把 `sk-` + 32 位随机串（示例值不写全，否则自己被判红） 写进**已跟踪**的 已跟踪的契约文档 ⇒ 〈落点 #50〉 必须判红（2026-11-10 实测）。内网地址在该脚本里只到**提示级**，不判红；是否脱敏由人判定夺。
- **读数口径**：报「扫描文件 N / 命中 0」。
- **归属**：本节（铁律 #8）。

9. **文档改动必过门禁**：〈落点 #01〉。
- **归属环节**：全局
- **不是什么**：不是「审一遍读起来顺就行」—— 门禁清单见本文 §4，不是可选项。
- **判据**：【机判】〈落点 #01〉 文档项（含 〈落点 #08〉）；**入场判据 = 〈落点 #09〉** —— 按改动推断动作、把该动作的必跑判据全跑一遍（2026-11-10 修过一个洞：原来只看暂存区，暂存两个脚本就再也不看工作区，文档那套判据一条没跑，注入重复 `Q37` 仍 rc=0）。
- **覆盖范围**：只判动作对应的判据跑过、门禁输出在，判不了「该改的文档这次到底改没改」（那由 〈落点 #34〉 报告 + 人判）（2026-11-18 补：铁律 13 落地）
- **负例**：删掉需求书某个 § 标题导致表格列数变化而不跑门禁 ⇒ 〈落点 #32〉 必须判红；把 `| **Q37**` 那一行复制一份（同号两行）再跑 `action-router --changed --check --fast` ⇒ 必须 rc=1（2026-11-10 实测）。
- **读数口径**：报「文档项：绿/红 + 失败脚本名」。
- **归属**：本节。

10. **不擅自扩大文档体系**：只认 §2 的三书一单，不许新建第六本书 / 索引 / 派生表 / 清单，门禁要的中间产物落 构建产物目录。
- **归属环节**：全局
- **不是什么**：不是「有用就可以新建一本」；也不是「索引不算书」—— 索引 / 派生表一律进 派生件区。
- **判据**：【机判】〈落点 #10〉（文档根白名单）、〈落点 #11〉、〈落点 #12〉。
- **覆盖范围**：只判文档根白名单与放置规则，判不了「这本书该不该存在」（那是决策）（2026-11-18 补：铁律 13 落地）
- **负例**：在文档根新建《Doyah产品测试登记.md》⇒ 〈落点 #22〉 必须判红。
- **读数口径**：报「文档根 N 份 / 越界 M 份」。
- **归属**：本节。

11. **报数报「还剩多少」**：报数报「还剩多少 / 缺在哪」，不报「扫了多少」。
- **归属环节**：全局
- **不是什么**：不是「已登记 = 已修完」；也不是「覆盖率 96% 可以当结论」。
- **判据**：【人判】结论句里有没有「还剩/缺在哪」，由接收方读（**本条主体是人判**）；【机判】〈落点 #13〉 只兜「写死的数字必须与实测一致」。
- **覆盖范围**：机判只兜「写死的数字与实测一致」，判不了结论句里有没有报剩余（那是读句子，人判）（2026-11-18 补：铁律 13 落地）
  **曾经的错指向**（2026-11-10 实测）：原文把 〈落点 #36〉 当主判据。它只对 〈落点 #106〉 做一单 ↔ 实测 ↔ 文档三向对账，**不解析结论句** —— 往一单写「还剩 1 条未闭环」它照样绿。
- **负例**：报告写「已完成 391 条中的 379 条」而不说剩 6 条未闭 ⇒ 〈落点 #36〉 判不出，接收方判错（故本条保留人判）。
- **读数口径**：报「总数 / 已闭 / **未闭**」三值，未闭必须点名。
- **归属**：本节（铁律 #11）。

12. **一条拍板只落一处结论**：同一状态散在多本册子只改一处必留矛盾 ⇒ 状态唯一源 = 一单。
- **归属环节**：全局
- **不是什么**：不是「多写几处更保险」—— 同一状态写两处必然只改一处，留下矛盾。
- **判据**：【机判】〈落点 #14〉（跨册状态比对）。
- **覆盖范围**：只判跨册的状态字面一致，判不了这条拍板该不该存在、有没有被后来的决定取代（2026-11-18 补：铁律 13 落地）
- **负例**：在概设正文给已 ✅ 的编号 `FR-STD-ALL-BLD-001` 紧贴一个 ⬜ 括注（编号与全角括号之间不留字、不加反引号）⇒ 〈落点 #19〉 判红「括注 ⬜，而一单为 ✅」（2026-11-10 实测）。
  **口径边界**：编号与括号之间夹字、括注里带说明的都不在它判据面（脚本自登记的 ④ 条边界）；需求书索引已不带状态列，原文负例里的「索引标 doing」已不存在。
- **读数口径**：报「状态项 N / 矛盾 M」。
- **归属**：本节。

13. **判据必须声明覆盖范围**：任何「报缺失/报异常」的判据，先说清扫了哪些目标源、哪些没扫。
- **归属环节**：全局
- **不是什么**：不是「加了 `--json` 就算声明」；覆盖不全时**只许报「未知」，不许报「发现」**。
- **判据**：【人判】脚本 `--json` 输出有没有 `sources` / `uncovered` 两段、交接说明写没写，由评审人核；`uncovered` 非空而结论报「发现」即判错。 **覆盖范围**：本条只判「有没有写覆盖范围」，不判声明是否真实——真实性由铁律 15 独立验收层兜。
  **曾经的错指向**（2026-11-10 实测）：原文标的是**机判**（「`--json` 输出必须含 `sources`/`uncovered` 两段」）。全仓只有 3 个脚本输出 `uncovered`（〈落点 #99〉 / 〈落点 #115〉 / 〈落点 #116〉），**没有任何门禁核这条**，也没有 `--json` 契约检查 —— 机判是我自己写上去的声称，已降为人判。
- **负例**：悬空引用检测扫了 48 个源报「23 处异常」，实际漏扫分仓 ⇒ 必须报「未知」而不是「23 处」。
- **读数口径**：报「覆盖 N 源 / 未覆盖 M 源 / 结论：发现｜未知」。
- **归属**：本节（铁律 #13）。

14. **每条判据配一条「必须判红」的负例**：正例只证明能通过，负例才证明真会拦；新写或改写的门禁必须同时交一个故意违规的样本。执行器：〈落点 #103〉（造不出文件层负例的必须登记在 〈落点 #104〉 并写清原因，未登记即红）。
- **归属环节**：全局
- **不是什么**：不是「有单测就算」—— 必须有一条**故意违规**的用例，且它必须判红。
- **判据**：【机判】〈落点 #15〉（各门禁自测计数与登记一致）+ 〈落点 #16〉；新增门禁无负例用例即红。
- **覆盖范围**：只判「登记的自测例数与实跑一致」和「新增门禁有没有负例」，判不了那条负例是否真能覆盖会发生失效形态（2026-11-18 补：铁律 13 落地）

- **读数口径**：报「负例数 / 断言数」两个数，不报「自检通过」。
- **归属**：本节（铁律 #14）。

15. **独立验收层：判「对」的依据不许由被判方提供**：判「对」只认三样：人类主人原话 / 契约条文（三书判据行）/ 外部权威系统（编译器、测试框架、真机）。
- **归属环节**：全局
- **不是什么**：不是「自己跑通了就算对」；生成 spec/代码/测试的同一个模型不能同时判定它对。
- **判据**：【人判】交接说明里每条「已完成」必须指名依据属于哪一类（口径编号 / 主人原话 / 命令输出）；只写「我验过了」= 判错。 **覆盖范围**：只看依据是否指向三类之一，判不了依据本身是否站得住。
- **负例**：【人判】交接写「已按我最新的理解实现并自测通过」而不指名契约条文号 ⇒ 判错。
- **读数口径**：报「已完成条目数 / 其中指明依据的条数」。
- **归属**：本节（铁律 #15）。

## 1.7 归约：没见过的东西先归到已有的格子里

- **归约：没见过的东西先归到已有的格子里**（2026-11-18 定；人类主人：「有没有可能在开发之前，把所有可能的阶段、流程、环节都以规范的形式覆盖到」）；
  **三句话**：① 任何新事物（新需求、新故障、新工具、新平台）动手前，先归约到「6 个动作 × 27 个环节」里的某一格；② 归不进去的，**停下来加环节**，且新环节必须同时给出「出口」—— 拿到什么算完；没有出口的环节不许建；③ 归进去了就按那一类的出口走，不许临场发明流程。
- **是什么**：把「无限的新场景」压成「有限的格子」的那一步。规范能跟着场景扩张，靠的不是写更多条，而是不认识的先归类。
- **不是什么**：不是「凡事都要新立环节」—— 能归进现有格子的一律不许新建；也不是「归约表填完就能开工」—— 表填完还要过该动作的必读与必跑。
- **判据**：【机判】〈落点 #105〉 每个环节必须有非空「出口」，缺一个即红；【人判】**归约演练**：拿一个从没做过的场景，只给这份规范，填下面的表；填不出来即为规范缺口。
- **负例**：给某个环节删掉「出口」⇒ 必须判红（2026-11-18 实测：删掉 `B2` 的出口 ⇒ 点名「走到这一步怎么算做完没说」）；建一个没有出口的新环节 ⇒ 必须判红；没填归约表就开工 ⇒ 人判退回重填。
- **覆盖范围**：判得了「每个环节都有出口」；判不了「这次归约归得对不对」，也判不了「某个新场景是否真的属于这一类」—— 那是人判。
- **归属环节**：A3

**归约演练表（每个新场景填一次，填完贴在需求条目下）**

| 要填的格 | 填法 |
|---|---|
| 属于哪个动作 | 从 6 个动作里选一个：改文档 / 改判据脚本 / 改代码 / 改前端 / 动凭据或用户数据 / 推送 |
| 走过哪些环节 | 列环节 ID，如 `A1 → A2 → B1 → C1 → C3 → D1` |
| 每环节的出口 | 照抄该环节「出口」的原话；抄不出来 = 这次归约没成，先回去补环节定义 |

## 2 三书一单（唯一文档体系）
| 位置 | 书 | 写什么 |
|---|---|---|
| ② | 《X产品需求规格说明书》 | 需求条目（编号 / 需求 / 判据 / 优先级 / 状态 / 来源）、验收判据 |
| ③ | 《X产品概要设计说明书》 | 组件表、契约 `P-xx`、ADR、跨端约束；不写实现细节 |
| ④ | 《X产品详细设计说明书-<端>》 | 七件套契约、追溯矩阵、用例定义、实现约束 |
| 单 | 《X产品开发计划任务清单-<端>》 | 该端需求状态一单 + 版本计划 + 批次；日报从这里取数 |

### 2.1 一单：活件、唯一进度源、与详设同构

- **一单只给正在开发的端建、每端一份活件**：〈落点 #17〉（判据 A2）。
- **归属环节**：A3
- **不是什么**：不是「每端都先建一份备着」—— 只给正在开发的端建，未开发端不建。
- **判据**：【机判】〈落点 #17〉（判据 A2）。
- **覆盖范围**：只判「一单的端白名单都是正在开发的端、每端恰一份」，判不了这个端是否真的在开发（端清单本身由需求书判） (2026-11-18 补：铁律 13 落地)
- **负例**：给不在允许端清单里的端建一单（`任务清单-Web端.md`）⇒ 端清单判据判红「不属于允许的端」（允许端清单见落点表；2026-11-10 实测）。
  **补正**：`ALLOWED_SHEETS` 现含六端 ⇒ 原文「给尚未开发的某端建一单」**不拦**（该端有详设与清单）；能拦的是清单外的端。
- **读数口径**：报「一单份数 / 对应端」。
- **归属**：本节。

- **一单永远只有一份活件，不做版本快照**：一单是活件，任何时点只有一份，历史差异看 git，不拍快照。同上。
- **归属环节**：A3
- **不是什么**：不是「每版留一份做对照」—— 历史看 git，快照只会漂移。
- **判据**：【机判】〈落点 #17〉（判据 A2）。
- **覆盖范围**：只判「同端没有第二份一单 / 没有版本快照文件」，判不了历史版本是否被藏到别的目录或别的文件名 (2026-11-18 补：铁律 13 落地)
- **负例**：在 冻结区 留一份一单快照 ⇒ 必须判红（v1.3 起已删两份历史快照）。
- **读数口径**：报「活件份数（应 1）/ 快照份数（应 0）」。
- **归属**：本节。

- **一单与详设同构、按端分册，只认同端详设活书**：不许引别端详设、不许把 冻结区 冻结件当上游。
- **归属环节**：A3
- **不是什么**：不是「可以引别端详设」；也不是「冻结件能当上游」。
- **判据**：【机判】〈落点 #17〉（判据 I）。
- **覆盖范围**：只判「章节结构与同端详设同构、引用的上游是活书」，判不了章节内容是否与详设实质一致（那由 〈落点 #34〉 报「碰了代码没碰文档」） (2026-11-18 补：铁律 13 落地)
- **负例**：A 端一单引用 B 端详设的某一节作为落点 ⇒ 必须判红。
- **读数口径**：报「引别端 N 处 / 引冻结件 M 处（应 0）」。
- **归属**：本节。

- **一单是唯一进度源**：日报 / 周报 / 进度表一律从它取，不许另开「里程碑清单」「按平台任务清单」当第二本。
- **归属环节**：A3
- **不是什么**：不是「日报里另记一份进度」；也不许另开「里程碑清单」当第二本。
- **判据**：【机判】〈落点 #18〉 + 〈落点 #19〉；【人判】日报数字是否只从一单取。
- **覆盖范围**：机判只判「一单与需求索引逐行对得上」，判不了别处（日报、聊天、提交信息）有没有另立一套状态口径 —— 那半只能人判 (2026-11-18 补：铁律 13 落地)
- **负例**：在进度活件（一单）里加一条需求书索引没有的编号（`FR-STD-DB-DRV-014`）⇒ 〈落点 #30〉 判红「一单多 1 条」（2026-11-10 实测）；另在别处另写一份进度（周报写「本版进度 80%」）⇒ 脚本判不了，接收方判错。
- **读数口径**：报「未闭条数（只从一单取）」。
- **归属**：本节。

### 2.2 分册只有「截取」，不许按端拆

- **分册的需求书与概设不许按端拆**：分册来自全量书、**只裁剪不增删**（`分册 ⊆ 全量`：分册出现的每个编号都必须能在全量书里找到）；一个产品各一本需求规格 + 一本概要设计，端差异不写进这两本；详设按端一本、从本族基准派生，只改落点与读数口径，不许另起契约正文。
- **归属环节**：A2
- **不是什么**：不是「各端可以有自己的需求书」—— 需求与概设一个产品各一本，端差异只进详设；也不是「分册可以自己加条文」—— 只能裁，不能增。
- **判据**：【机判】〈落点 #20〉（分册 ⊆ 全量）、〈落点 #21〉（详设逐节表态）。
- **覆盖范围**：只判「分册内容 ⊆ 全量」「详设逐节表态过」，判不了分册里有没有偷偷写全量没有的新契约 (2026-11-18 补：铁律 13 落地)
- **负例**：在分册里写一条全量书没有的正文行 ⇒ 〈落点 #20〉 判红（2026-11-10 实测）；另建一本《需求规格说明书-<端>》⇒ 判红。
- **读数口径**：报「分册 N 本 / 按端拆 M 本（应 0）/ 全量书里找不到的编号 X（应 0）」。
- **归属**：本节；**哪个产品分几本、哪端归哪个仓属项目事实**，本册不写。

### 2.3 目录与派生件

- **文档根只许三书 + 一单**：文档根只放四件活书 —— README、本册、项目规范、详设模板，别的不许并排；发布说明 / 点验清单 / 功能清单 / 调研书 / 各类记录等过程件一律进归档区。
- **归属环节**：A2
- **不是什么**：不是「发布说明也是书」—— 过程件一律进归档区。
- **判据**：【机判】〈落点 #10〉（判据 H，白名单份数由项目定）。
- **覆盖范围**：只判文档根白名单，判不了白名单里的内容是否合规 (2026-11-18 补：铁律 13 落地)
- **负例**：把《发布方案.md》放回文档根 ⇒ 必须判红。
- **读数口径**：报「根目录 N 份 / 白名单外 M 份」。
- **归属**：本节。

- **跨端视图不是书**：平台矩阵 / 按平台清单 / 需求索引 / 追溯表 / 各种派生表都是派生件 ⇒ 落派生件区，不得与三书并排。
- **归属环节**：A2
- **不是什么**：不是「矩阵也算文档」—— 派生件落派生件区。
- **判据**：【机判】〈落点 #22〉（文档根白名单，多一份即红）。
- **覆盖范围**：只判根目录不出现跨端视图（它只许在派生件区），判不了派生出来的那份是否过期 (2026-11-18 补：铁律 13 落地)
  **曾经的错指向**：本条原写的是一个管「书里内容归位」的判据，2026-11-10 实测——它在文档根建一个派生件表格 **照样绿**，那个脚本管的是「书里的内容归位」（详设不许写轮次/版本/日期），不判根目录新建；错指门 = 规矩形同没有。
- **负例**：在文档根建 `平台矩阵.md` ⇒ 〈落点 #22〉 输出「文档根不是白名单：多 ['平台矩阵.md']」（实测原文见该落点）。
- **读数口径**：报「派生件 N / 误置 M / 白名单外新增 X」。
- **归属**：本节。

### 2.4 端详设从本族基准派生

- **端详设从本族基准派生，不各写一本**：每本《X产品详细设计说明书-<端>》（本族基准端除外）必须 ① 头部写「派生自 <基准端详设> vX」；② 有一节差异登记，对着**本族基准**详设的每一节表态 —— `沿用` / `差异` / `不适用`，后两者必须给依据或本端落点；③ 基准详设每新增一节，各端差异登记同批补行，不是等排期。本条判的是「有没有逐节表态」，判不了「表得对不对」——后半由各端测试与骨架判据负责。
- **归属环节**：A2
- **不是什么**：不是「各端独立写详设」—— 同族其余端从本族基准派生，只改落点与读数口径。
- **判据**：【机判】〈落点 #23〉（逐节表态：派生自 / 差异 / 无差异）· 〈落点 #24〉（拿基准书逐节比对另一端，缺节即红）· 〈落点 #25〉（详设写的「本端落点」必须对得上仓里真实目录）。
- **覆盖范围**：只判「逐节表态 + 缺节即红 + 落点对得上真实目录」，判不了差异写得对不对（那是人判） (2026-11-18 补：铁律 13 落地)
- **负例**：派生端详设自写一套契约正文而非派生自基准 ⇒ 〈落点 #23〉 判红（逐节表态缺行；2026-11-10 实测）。
- **读数口径**：报「逐节表态 N/M」。
- **归属**：本节。**哪一端是本族基准属项目事实**，本册不指定。

- **判据**：【机判】〈落点 #26〉 + 〈落点 #27〉。

### 2.6 规划环节规则（A1–A4）

> 这一节补的是「规划」里原先空着的六个方面：验收口径、非功能需求、契约同步、估时、并行边界、决策记录。
> 它们的共同点：**都是人判**为主 —— 这些事没有判据物，只有人能不能说清。所以每条都写明「谁判、判错什么样、看不到什么」。

- **每条需求必须带可判验收口径**：需求条目里「判据」一栏不许空、不许写「实现后验证」这类同义反复；能机械判的写命令，判不了的写【人判】并点明「谁判 + 判错时他说什么」。口径写不出来，说明这条需求还没想清楚，不许进书。
- **归属环节**：A1
- **不是什么**：不是「先登记，判据以后再补」—— 补不上来的判据会变成永久的「待验证」；也不是「有测试就算有口径」，测试判行为，口径判「凭什么说达标」。
- **判据**：【机判】〈落点 #32〉（需求书判据列存在、列数与表头一致）。【人判】逐条读口径：是否可判、判不了有没有标人判并写清谁判。 **覆盖范围**：判据只保证列存在与列数对，判不了口径本身够不够硬 —— 那必须人读。
- **负例**：`FR-XXX` 行判据列写「功能正常」⇒ 人判退回（不可判）；判据列留空 ⇒ 表格判据报列数异常 / 人判退回。
- **读数口径**：报「需求 N / 有可判口径 N / 口径为空或同义反复 N（应 0）」
- **归属**：本节（A1 验收口径）。

- **非功能需求单独登记，阈值与测量条件同处**：性能、兼容、安全三类非功能承诺各自成处登记（不许散在正文段里当形容词）；每条必须带阈值、测量条件（机器 / 数据量 / 平台）与当前读数来源。没有测量条件的阈值等于没写。
- **归属环节**：A1
- **不是什么**：不是「性能很好、兼容性没问题」这类定语；也不是「阈值先写个目标值，回头再说怎么量」。
- **判据**：【人判】接收方核三件：三类是否各有一处、每条是否带阈值与测量条件、读数能否指向一次真实测量。 **覆盖范围**：只看登记与条件是否写全，判不了阈值定得合不合理。
- **负例**：正文里写「启动要快」 ⇒ 判错（无阈值无条件）；写下「≤2 s」却不说在哪台机器、什么数据量下量 ⇒ 判「未定义」。
- **读数口径**：报「非功能条 N / 带阈值 N / 带测量条件 N / 无来源读数 N」
- **归属**：本节（A1 非功能）。

- **改契约必须同批改下游**：改需求 / 概设里的契约面，必须在**同一批**里改到下游四处 —— 详设（各端）、测试、一单、派生件；漏一处即视为未完成。下游来不及改的，先改契约前的「不改」结论，不许先改上游再补下游。
- **归属环节**：A2
- **不是什么**：不是「代码改完顺手补文档」；也不是「文档回头一起改」—— 回头往往就是永远。
- **判据**：【机判】〈落点 #33〉 报出的「碰了代码没碰文档」的提交必须被回应（该脚本只报告不拦截）。【人判】接收方核这一批的改动集里，契约与下游是否同批出现。 **覆盖范围**：〈落点 #34〉 只看「代码动了文档没动」，看不到「契约动了但改的是无关文档」—— 后者靠人判。
- **负例**：改了概设里的契约条文，同一批里详设与测试都没动 ⇒ 人判退回；把 〈落点 #34〉 的读数直接忽略 ⇒ 视为未回应。
- **读数口径**：报「契约改动 N / 下游同批 N / 未回应 `doc-sync` 读数 N（应 0）」
- **归属**：本节（A2 契约同步）。

- **估时按「可交付单元」算，并给依据；超估 50% 停下报读数**：估时必须说明单位（改动文件数 / 条文条数 / 命令条数 / 串行步骤数），不许用「人天 / 几天」这类没有定义的单位；估完要写一句依据；实际超过估算 50% 时**停下来报当前读数**，不许默默延期假装正常。交给别人做与自己做要分开估 —— 打字速度与判断耗时不是一回事。
- **归属环节**：A3
- **不是什么**：不是「估个大概好交差」；也不是「超了就说需求变复杂了」。
- **判据**：【人判】接收方核三件：单位是否可数、依据是否写了一句、超估时是否有停下来报的读数。 **覆盖范围**：估时合理性判不了 —— 只能判「有没有把单位和依据写出来」。
- **负例**：报「这个要 2–3 天」而说不出单位与依据 ⇒ 判错；超时后直接报「已完成」而不报差值 ⇒ 退回。
- **读数口径**：报「任务 N / 有单位 N / 有依据 N / 超估 50% 未报 N（应 0）」
- **归属**：本节（A3 估时）。

- **并行与串行的边界必须显式声明**：动**同一文件、同一契约面、同一份一单、同一队列**的工作必须串行；只读调研、看不同文件的文档、跑互不影响的判据可以并行；并行开工前先写一句「谁做哪块、产出落在哪个文件」，否则一律按串行做。
- **归属环节**：A3
- **不是什么**：不是「人多就应该并行」—— 并行的收益常常小于合并冲突的代价；也不是「并行就是分头干」，没有分工声明不算并行。
- **判据**：【人判】接收方核：并行部分是否有分工声明、是否触碰了同一文件或同一份一单。 **覆盖范围**：只看声明与文件面重叠，判不了并行后合并质量。
- **负例**：两个助理同时改一单同一节 ⇒ 判错（应串行）；并行写同一个派生文件 ⇒ 判错。
- **读数口径**：报「并行批次 N / 有分工声明 N / 触碰同一文件 N（应 0）」
- **归属**：本节（A3 并行边界）。

- **三类决定必须留 ADR：不可逆 / 否决过其他方案 / 跨端跨仓契约**：每条 ADR 只写三件 —— **决定是什么、否决了什么（及为什么）、代价是什么**；写在概设的 ADR 节（`ADR-<序号>`），一决定一条，不许事后补写成「我们一贯如此」。改判时**追加**一条新 ADR 并注明推翻哪条，不许改旧条。
- **归属环节**：A4
- **不是什么**：不是「所有决定都要写」—— 可逆的小决定不写，写多了没人读；也不是「写了 ADR 就等于决定对了」。
- **判据**：【人判】接收方核三件：是否属三类之一、三要素是否齐、改判是否追加而非改写。 **覆盖范围**：判不了「这个决定该不该做」，只判「有没有留下可追溯的取舍记录」。
- **负例**：把已经上线两周的取舍补写成 ADR 并标当日 ⇒ 判错（时间线造假）；改判时直接改旧 ADR 正文 ⇒ 退回（应追加）。
- **读数口径**：报「三类决定 N / 有 ADR N / 三要素齐 N / 改写旧 ADR N（应 0）」
- **归属**：本节（A4 决策记录）。

## 4 门禁与条文写作格式

### 4.1 门禁清单（唯一源 = 〈落点 #109〉）

**清单不抄在文档里**：项名、顺序、项数都从脚本自身取 —— 〈落点 #110〉（现 **19 项**）。抄一份到文档里就必然与脚本漂（这与「数字与路径都不写死」是同一条道理）。

| 组 | 判什么 | 何时必须跑 |
|---|---|---|
| 单测与平台中立 | Core 与平台适配层单测 · 平台中立性棘轮 · 本地化棘轮 | 改代码 / 改文案 |
| 文档 | 表格与派生计数 · 口径对账（状态括注 / 版本范围 / 一单覆盖 / §4.2 条数） | 改三书一单或规范 |
| 判据自身 | 负例族真跑一遍并逐条判红 · 自检例数与登记表一致 · 条文六字段 · 归属环节 | 改任何判据或条文 |
| 交付 | 打包安装件（沙箱）· 版本号三处对账 · 生成物与构建描述不漂移 | 出包 / 发版 |
| 越界与归属 | 三书独占节 + 路径归属（改动不许落在对侧节或对侧子树） | 跨端 / 跨仓改动 |
| 一单 | 实现列 ↔ 判据列一致 · 卡点表与一单同源 · 派生队列与 next_try | 改一单 |

- **覆盖范围**：本节只回答「有哪些门禁、什么时候跑」，**不判这些门禁本身对不对** —— 后者靠两样：每条门禁自己的 `--self-test`（含必须判红的负例）+ 〈落点 #01〉 第 16 项越界检查。
- **不是什么**：不是「跑一次全绿就永久有效」—— 门禁是**当次树**的快照；工作区脏着跑出来的读数不算（实测踩过：边跑边往索引里塞文件，`build-app` 直接拒包、`rule-negatives` 5 条基线本红）。


### 4.2 判据不写落点：通用册只写形态，落点用编号指过去

**规矩**：本册每条的「判据」字段只写两样 —— **形态**（【机判】/【人判】）与**判什么**；具体脚本、命令、测试文件、路径一律不写，改写成 `〈落点 #NN〉`，由本仓的**落点表**给出实现（项目事实，住在项目册）。

**为什么**：本册写给「所有项目」——换一个项目、换一套技术栈、换一个仓，条文必须照抄仍然成立。把某个工具链的具体命令、某个平台或生态的专有名写进来，等于把某一端的实现细节冒充成通用规矩：别的端照做既跑不起来，也判不了。落点变了（换脚本、换命令）也不该动本册一个字。

- **判据**：【机判】〈落点 #45〉 —— 四样一起判：① 本册条文正文与判据字段里出现「具体脚本路径 / 具体命令 / 平台或生态专有名」即判红；② 本册出现的每个 `〈落点 #NN〉` 必须在本仓落点表内、表内每行必须被至少一条条文引用（双向对账，不许悬空）；③ **术语闭环**：术语表里的每个词在本册正文必须真的用到（防止术语表变成空词柜）；④ 术语表里的每个词在项目册的「术语对应」段必须有对应（防止只清一边）。
- **负例**：往本册任一判据字段写回某个具体脚本路径或命令 ⇒ 必须判红；写「在某个平台上跑」这类平台专有名 ⇒ 必须判红；落点表里留一行没人引用 ⇒ 必须判红。
- **覆盖范围**：判 ①–④ 四样；**判不了两件**：其一「这条规矩本身是否对所有项目成立」，其二「本册正文里自造的词有没有定义」—— 自造词不可枚举，机器认不出哪个词是自造的，只能人判并写进未覆盖面（2026-11-18 补）。
- **归属环节**：A1（规范与契约先行）

**条文写作格式（本节总则，2026-11-10 人类主人：「规范本身其实不规范，没写人判还是机判，没写负例判红」）**

规范是行为规格书，条文不写清验收方式就不算规则。每条条文必须带六字段，缺一即不合规：

| 字段 | 写什么 | 省掉的后果 |
|---|---|---|
| **是什么** | 要求一句话，可引用 | 判据无处挂靠 |
| **不是什么** | 边界与常见误读 | 同一句话被两种解读执行 |
| **判据** | 【机判】命令 + `exit 0` ／【人判】谁判 + 判错的表现 | 条文变口号，或人判伪装成机判 |
| **负例** | 故意违规时哪条必须变红 | 判据假绿而无人知 |
| **读数口径** | 报什么、什么算通过 | 报「全绿」而书里三个版本号 |
| **归属** | 规则正文落在哪本哪节、谁有权改 | 两本规范各写一套 |

- **判据两种，必须点名**：【机判】给命令；【人判】写清「谁判 + 判错时他说什么」。只写「评审」不算判据 —— 它既不说谁判，也不说判错什么样。
- **覆盖范围**：只判「判据字段里有没有点名【机判】或【人判】」，判不了标了机判的命令跑不跑得起来（那由负例族判）(2026-11-18 补：铁律 13 落地)
- **模板的元规范在代码里，不在文档里**：〈落点 #111〉（六字段定义）+ 〈落点 #45〉（执行者）。**不另立《模板规范》文档** —— 再套一层就会丢（人类主人：「随着项目深入推进，这些模板的模板也会丢失」）。
- **覆盖范围**：只判「没有另立模板类文档」（根目录白名单），判不了 schema 定义本身是否完备(2026-11-18 补：铁律 13 落地)
- **存量条文允许暂缺字段**：数量记 〈落点 #112〉，**只许降不许升**；新条文一律不许裸奔。
- **归属环节**：全局
- **不是什么**：不是「新条文也可以先裸奔」—— 只许降不许升。
- **判据**：【机判】〈落点 #39〉（棘轮：缺字段数不得升、完整数不得降；**单向引用**：本册条文正文出现项目规范的书名或节号即红 —— 只许项目规范引用本册，不许本册指回去）。
- **覆盖范围**：只判棘轮方向（缺字段不许升、完整不许降），判不了缺的字段什么时候补上 (2026-11-18 补：铁律 13 落地)
- **负例**：新写一条只有「判据：评审」的条文 ⇒ 缺字段数 +1，必须判红。
- **读数口径**：报「条文 N / 完整 M / 缺字段 K」。
- **归属**：本节。

- **负例（本条自己也要有）**：新写一条缺 **负例** 字段的条文 ⇒ 本册的写法判据必须判红（该例已固化在它的 `--self-test` 里）；在本册任一 条文里写「见项目规范的 §5」这类指回 ⇒ 同样判红（2026-11-10 实测，自检含这条正反例）。

## 6 实现环节规则（B1–B6）

> 本节补的是「实现层」六个环节。此前这六格全是空白 —— 规则书只长了文档与交付的条文，代码怎么写、依赖怎么管、数据怎么迁、接口怎么兼容，一条都没有。
> **写这一节的纪律**：能用真实判据的就写【机判】并点名脚本；没有真实判据的**只写【人判】**，不编一个「看起来像判据」的脚本名（指错门比没有判据更坏）。

- **代码写法：局部改动优先，一次只动与任务相关的最小范围**：不顺手重排、不顺手改名、不顺手改格式；删除前确认范围（铁律 #7 的代码侧落点）；不许留「看起来能跑」的空实现（`TODO` 占位、假返回、`fatalError("not implemented")` 当交付）。
- **归属环节**：B1
- **不是什么**：不是「代码不许重构」—— 重构要**单独提交**并写清动机；也不是「风格统一可以顺手改两百行」。
- **判据**：【机判】〈落点 #47〉 + 〈落点 #03〉（行为不许破）；〈落点 #04〉（改到别人负责的文件即红）。【人判】diff 里出现与任务无关的整段重排 ⇒ 退回。
- **覆盖范围**：只判「构建与测试不破」「改到别人负责的文件即红」，判不了 diff 是不是「与任务无关的整段重排」（那要读 diff，人判） (2026-11-18 补：铁律 13 落地)
- **负例**：为了改一个按钮颜色重排整个文件 ⇒ 人判退回；提交里留 `fatalError("TODO")` 假实现 ⇒ 编译能过，但对应行为用例必须红。
- **读数口径**：报「本片改动文件数 / 其中与任务无关的文件数（应 0）/ 空实现残留数（应 0）」。
- **归属**：本节（实现层 B1）。

- **代码评审与提交：一个提交只做一件事，且必须自证**：提交信息写清「改了什么 / 派生出口 / 验证命令与结果」（铁律 #4）；改**契约或判据**的提交必须附自审清单 —— 改了哪条条文号、跑了哪条判据、反证做没做。
- **归属环节**：B2
- **不是什么**：不是「提交越细越好」—— 一个提交里塞三个无关修复同样不合格；也不是「自审＝自己说没问题」。
- 边界（2026-11-18 实测补）：**派生出口的连带改动算同一件事** —— 改代码导致单测数变化时，同批更新 〈落点 #106〉、门禁索引文件 的门禁行与例数，属于「让这次改动站得住」，不是第二件事；反过来，把「数字跟版」拆成单独提交反而会让门禁在中间状态红。
- **判据**：【机判】〈落点 #48〉（动作对应判据必跑）；`git log -1 --format=%B` 必须能读到验证命令与结果。【人判】自审清单缺条文号或缺反证 ⇒ 退回。
- **覆盖范围**：只判「动作对应判据跑过」「提交信息里能读到验证命令与结果」，判不了「一个提交只做一件事」的边界（那由人判看 diff） (2026-11-18 补：铁律 13 落地)
- **负例**：提交信息只写「修 bug」、无任何验证输出 ⇒ 判错；改了一条判据却没跑它的负例 ⇒ 退回。
- **读数口径**：报「提交数 / 带验证输出的提交数 / 带自审清单的契约提交数」。
- **归属**：本节（实现层 B2）。

- **依赖与工具链：只用本机已装，新增必须登记**：解释器与工具链只许用本机**已装**版本；新增依赖必须同批写明**版本与理由**并登记；脚本必须跨平台 —— 禁 shell 专有语法、禁 GNU / BSD 专有参数。
- **归属环节**：B3
- **不是什么**：不是「能装上就能用」（安装动作要人授权，铁律 #6）；也不是「只在本机跑得过就算跨平台」。
- **判据**：【人判】由接收方核两件：新增依赖是否有版本与理由登记；脚本是否存在平台专有写法（例：`sed -i ''`、`readlink -f`）。**覆盖范围如实声明**：本环节**没有**机判脚本，〈落点 #49〉 管的是测试连接环境，**不是**本环节 —— 不许拿它冒充。
- **负例**：脚本用了只有本机能跑的写法（如命令参数各平台不兼容）⇒ 人判退回；缺依赖时自动安装 ⇒ 违反「不擅自改外部状态」。
- **读数口径**：报「新增依赖 N 个 / 有版本与理由登记 N 个 / 有平台专有写法的脚本 N 个」。
- **归属**：本节（实现层 B3）。

- **配置与凭据：默认值、可回退、不进日志**：密钥只从 stdin 或 0600 文件进，回复只说「已配置 / 长度 / 尾 4 位」；每个配置项有默认值、可回退、改动可追溯；凭据不许进仓库、日志、审计正文。
- **归属环节**：B4
- **不是什么**：不是「本地跑得通就能提交」；也不是「测试用假密钥可以随便写」—— 假密钥必须运行时拼接，源码里不许出现完整形态。
- **判据**：【机判】〈落点 #50〉（公开仓不含凭据 / 内网地址 / 他人个人内容）。【人判】配置项缺默认值或没有回退路径 ⇒ 退回。
- **覆盖范围**：机判只判公开仓文件里没有凭据 / 内网地址 / 他人个人内容，判不了配置项有没有默认值与回退路径（人判） (2026-11-18 补：铁律 13 落地)
- **负例**：把 key 写进 `.env` 一并提交 ⇒ 〈落点 #50〉 判红；日志里打印完整 token ⇒ 人判退回。
- **读数口径**：报「配置项 N / 有默认值 N / 可回退 N / 凭据外泄判红次数（应 0）」。
- **归属**：本节（实现层 B4）。

- **数据与迁移：变更必须同时给 up、down 与兼容说明**：任何 schema / 数据结构变更必须同批给出迁移脚本、回滚脚本、向前兼容说明（旧版本能否读新数据）；破坏性变更拆两步（先加后删），不许一步到位。
- **归属环节**：B5
- **不是什么**：不是「改完能跑就算完」—— **没有回滚路径的迁移不许发布**；也不是「写了 down 就算有回滚」—— 从未执行过的 down 视为不存在。
- **判据**：【人判】接收方核三件：迁移目录有 up / down 两份、down 被本次验证实际执行过、有前后兼容说明。**覆盖范围**：本环节无机判脚本（迁移用例存在则归 〈落点 #03〉，但它判行为不判「有没有回滚」）。
- **负例**：直接 `DROP COLUMN` 且无回滚 ⇒ 判错；只写 down 从未执行 ⇒ 判「未验证」，不算通过。
- **读数口径**：报「迁移 N 个 / 有 up N / 有 down N / 实际执行过 N / 有兼容说明 N」。
- **归属**：本节（实现层 B5）。

- **接口与兼容：改语义就升版本，错误码稳定**：对外接口（CLI 参数 / MCP 工具 / IM 通道 / 跨模块契约）的行为改动必须**向后兼容**，或**升版本并写迁移说明**；错误码与失败形态保持稳定，不许静默改语义。
- **归属环节**：B6
- **不是什么**：不是「改完同步改调用方就算兼容」—— 外部调用方不在本仓，改不到；也不是「加个参数就等于兼容」（默认值变了同样是破坏）。
- **判据**：【人判】接口改动必须附「兼容说明」或「新版本号 + 迁移说明」二选一。**覆盖范围**：本环节无机判脚本；〈落点 #51〉 判的是平台矩阵配置面，**不是**接口兼容 —— 不许拿它冒充。
- **负例**：把 `--open` 的语义从「打开报告」改成「打开目录」而不升版本 ⇒ 判错；错误码从 2 改成 1 且无说明 ⇒ 退回。
- **读数口径**：报「接口改动 N 处 / 有兼容说明 N / 需升版本 N」。
- **归属**：本节（实现层 B6）。


### 6.6 实现层补记：错误处理、并发、评审门槛、依赖升级、迁移幂等、超时重试

> 反查（2026-11-16）：实现层四件事全文零命中 —— `错误处理` 0 · `并发`/`线程` 0 · `幂等` 0 · `重试`/`限流` 0。
> 这四件恰好是「代码写完看着能跑、上线才出事」的那一类。六条都以【人判】为主，逐条声明看不到什么。

- **不许吞异常：失败要么留证、要么明确降级**：`catch` 之后必须做三件事之一 —— 记录一条可检索的失败（含操作、对象、原因）、明确降级并告知调用方、或向上抛；空 `catch`、`catch { return nil }`、`catch { }` 一律退回。调试输出（`print` / `NSLog` / `dump`）与断点不许进提交。
- **归属环节**：B1
- **不是什么**：不是「有 try/catch 就算处理了」—— 吞掉比崩掉更难查；也不是「日志打得越多越好」，无结构、不可检索的输出不算留证。
- **判据**：【人判】接收方读改动：每个新增 `catch` 是否有留证或降级；提交 diff 里有没有调试输出。 **覆盖范围**：只看代码文本，判不了「这条失败在运行时是不是真的会发生」。
- **负例**：`do { … } catch { }` ⇒ 退回；`catch { print("err") }` 只打一行无上下文 ⇒ 判「未留证」；提交里留 `print("here")` ⇒ 退回。
- **读数口径**：报「新增 catch N / 有留证或降级 N / 空 catch N（应 0）/ 调试残留 N（应 0）」
- **归属**：本节（B1 错误处理）。

- **并发与线程边界必须显式：共享状态单一所有者，UI 只在主线程改**：可变共享状态必须有唯一所有者（一个锁 / 一个串行队列 / 一个所有者对象），跨所有者访问必须显式（显式加锁或跳队列）；UI 状态只在 UI 线程改；不许假定「反正跑得快、不会同时进来」。
- **归属环节**：B1
- **不是什么**：不是「有锁就安全」—— 锁住了一半状态、另一半裸改，照样是竞态；也不是「单线程就不会有问题」，异步回调会换线程。
- **判据**：【人判】接收方核：新增或改动的共享状态有没有声明所有者、跨边界访问是否显式、UI 更新是否在主线程。**机判兜底**：〈落点 #47〉 的 actor isolation / sendability 告警不许新增。 **覆盖范围**：文本与告警只能提示，判不了真实竞态 —— 那要靠压测或真机复现。
- **负例**：在后台任务里直接改 `@Published` 属性 ⇒ 退回；两个类各持一份同一份缓存且各自写 ⇒ 判「无单一所有者」。
- **读数口径**：报「共享状态 N / 有单一所有者 N / 跨边界显式 N / 新增并发告警 N（应 0）」
- **归属**：本节（B1 并发）。

- **评审门槛要写明：谁审、什么算过、审不过说什么**：「自审即可开工」不是默认通行 —— 只有**改动面单一、无契约变更、无外部写入**的三类才允许自审；其余必须有第二人（或另一个助理）审，且审的人要给出「过 / 不过 + 理由」。审不过时必须指出具体条文号或判据名，不许写「感觉不行」。
- **归属环节**：B2
- **不是什么**：不是「走过形式」—— 没有具体理由的「过了」等于没审；也不是「什么都要审」，那会让所有人都绕过流程。
- **判据**：【人判】接收方核：本批是否属自审三类之一；不属则是否有第二人结论与理由。 **覆盖范围**：判不了审的人看得够不够细，只判有没有留下可追溯的结论。
- **负例**：改了概设契约条文却只有自审 ⇒ 退回；审核结论写「OK」无条文号 ⇒ 判「未审」。
- **读数口径**：报「批次 N / 可自审 N / 需二审 N / 二审有理由 N」
- **归属**：本节（B2 评审门槛）。

- **依赖升级四件套：从哪版到哪版 / 为什么升 / 怎么验 / 怎么退回**：升级任何依赖（含 vendored 第三方、工具链、SDK）必须同批写这四件；只写「升级到最新」视为未升级 —— 没有验证与回退路径的升级，等于把不确定性丢给下一个版本。
- **归属环节**：B3
- **不是什么**：不是「新版本总是更好」—— 升级的收益要能说出场景；也不是「跟着 lockfile 自动前进」。
- **判据**：【人判】接收方核四件是否齐；〈落点 #52〉 只兜 vendored 第三方的登记表一致（其余依赖无机判）。 **覆盖范围**：只看四件在不在，判不了新版是否引入行为变化。
- **负例**：把某个包从 1.2 升到 1.5 只写「升级依赖」⇒ 退回；升级后没跑对应判据 ⇒ 判「未验」。
- **读数口径**：报「升级 N 个 / 四件齐 N / 无回退路径 N（应 0）」
- **归属**：本节（B3 升级）。

- **迁移必须幂等可重入：重复执行不许产生重复数据**：迁移脚本重复跑一次必须与跑一次结果相同；不可幂等的情形（需要外部系统配合）必须把前置条件写在脚本头部，并在执行说明里写明「只能跑一次」。副作用（建表、建索引、回填）都要能被第二次执行识别为「已完成」。
- **归属环节**：B5
- **不是什么**：不是「跑过一次没出事就行」—— 回滚后再升级就是第二次跑；也不是「加个 IF NOT EXISTS 就算幂等」，回填类操作同样要判。
- **判据**：【人判】接收方核：脚本是否可重入、不可幂等的有没有写前置条件；【机判】〈落点 #03〉 里与迁移相关的用例必须绿。 **覆盖范围**：判不了在真实数据量与线上锁情况下的行为。
- **负例**：`INSERT` 回填数据而无去重 ⇒ 判错；脚本头没写前置条件却要求人工配合 ⇒ 退回。
- **读数口径**：报「迁移 N / 可重入 N / 明写只能跑一次 N / 有迁移用例 N」
- **归属**：本节（B5 幂等）。

- **超时与重试语义必须显式：有上限、有退避、写操作带幂等键**：每个外部调用（库、模型、IM、HTTP）必须显式设超时；重试必须有次数上限与退避（指数或固定 + 抖动），不许无限重试；**写操作重试必须带幂等键**，否则第一次成功、第二次重复执行就是脏数据；限流/配额要写明触发后的行为（排队、拒绝、降级）。
- **归属环节**：B6
- **不是什么**：不是「框架默认会超时」—— 默认值往往是没有；也不是「重试能提高成功率」而不设上限，一次故障会被放大成雪崩。
- **判据**：【人判】接收方核：每个新增外部调用是否显式超时、重试是否带上限与退避、写操作是否有幂等键。 **覆盖范围**：判不了真实网络下的重试风暴，只能判语义是否写清。
- **负例**：网络出口不设超时 ⇒ 退回；`while true { try? retry() }` 式重试 ⇒ 判错；写请求重试而无幂等键 ⇒ 判错。
- **读数口径**：报「外部调用 N / 显式超时 N / 有上限重试 N / 写操作幂等键 N」
- **归属**：本节（B6 超时重试）。

## 7 验证、交付、运行环节规则（C、D4/D5、F）

> 本节补完最后九格。与 §6 同一条纪律：有真判据才写【机判】，没有就写【人判】并声明覆盖范围。
> 一句话区别：**§6 管「写的时候」，本节管「交出去之后」** —— 测试、性能、安全、发布、回滚、运行、告警、故障、用户支持。

- **测试：每条新行为配一条能红的用例，删断言不许仍然绿**：新行为与新判据必须同批带用例；用例要能在**不修代码**的前提下因行为退化而变红；不许用「跑通即通过」的空用例凑数；测试与实现分开写，不许互相调用内部私有符号来「保证一致」。
- **归属环节**：C1
- **不是什么**：不是「覆盖率越高越好」—— 覆盖率不判语义；也不是「手工点一遍就算测过」（那是 C2 真机点验）。
- **判据**：【机判】〈落点 #03〉 收尾必须出现 `Executed N tests, 0 failures`。【人判】新用例是否真能红：临时改坏被测行为，用例应变红（反证一次）。
- **覆盖范围**：只判测试收尾行 0 失败，判不了「新行为有没有配用例」（覆盖率不在其内；能不能红靠人判反证一次） (2026-11-18 补：铁律 13 落地)
- **负例**：把断言删掉、用例仍绿 ⇒ 视为无用例；新行为只有实现没有用例 ⇒ 退回。
- **读数口径**：报「新增行为 N / 配用例 N / 反证能红 N」。
- **归属**：本节（验证层 C1）。

- **性能与资源：给出预算，超了就报数，不许「感觉还行」**：每个会随数据量或文件量增长的路径必须有明确预算（时间 / 内存 / 文件句柄 / 单次输出字节）；实测超预算必须报读数并说明取舍，不许用「本机挺快」代替。
- **归属环节**：C4
- **不是什么**：不是「做压测」才叫性能；也不是「优化到最快」—— 目标是**知道边界在哪**。
- **判据**：【人判】接收方核两件：预算写在哪、超预算时的实测读数。**覆盖范围**：本环节无机判脚本（〈落点 #03〉 只看行为正确性，不判耗时与内存）。
- **负例**：读大文件按全文一次性加载，实测内存翻十倍而无声 ⇒ 判错；只说「性能没问题」不给数 ⇒ 退回。
- **读数口径**：报「有预算的路径 N / 实测超预算 N / 有取舍说明 N」。
- **归属**：本节（验证层 C4）。

- **安全与隐私：默认最小权限，凭据与个人内容不出本机**：新增能力默认**最小权限**（能只读就不写、能局部就不全量）；用户数据、他人个人内容、内网地址不进公开仓、不进日志、不进审计正文；涉及外部写入的动作必须可回退。
- **归属环节**：C5
- **不是什么**：不是「加密了就安全」；也不是「内部工具不用管隐私」。
- **判据**：【机判】〈落点 #50〉（公开仓扫描）。【人判】权限面是否比需求更大、外部写入是否有回退路径。
- **覆盖范围**：机判只扫公开仓的凭据 / 地址 / 个人内容，判不了权限面是否最小、外部写入有没有回退路径（人判） (2026-11-18 补：铁律 13 落地)
- **负例**：为了省事给工具开全盘写权限 ⇒ 退回；把用户对话原文写进示例文档 ⇒ 判红。
- **读数口径**：报「新增能力 N / 权限最小化 N / 外部写入有回退 N」。
- **归属**：本节（验证层 C5）。

- **发布与分发：先定渠道与受众，再谈「发了」**：发布必须写明**渠道**（内部自用 / 指定人试用 / 公开）与**受众**；发布说明只写这一版真实变化，不写愿景；未验证的渠道不许对外。
- **归属环节**：D4
- **不是什么**：不是「打包出去就算发布」—— 打包是 D3；也不是「发到群里就算发布」，受众与渠道要显式写。
- **判据**：【机判】〈落点 #53〉（包标签与版本号一致）。【人判】发布说明是否有渠道与受众两行。
- **覆盖范围**：只判包标签与版本号一致，判不了发布说明里有没有写渠道与受众（人判） (2026-11-18 补：铁律 13 落地)
- **负例**：把内部自用包直接发给外部用户 ⇒ 判错；发布说明写「大幅优化体验」而无一条具体变化 ⇒ 退回。
- **读数口径**：报「发布 N 次 / 写明渠道 N / 写明受众 N」。
- **归属**：本节（交付层 D4）。

- **升级与回滚：每条升级路径都要有一条退回去的路**：升级必须给回滚路径（旧包 / 旧配置 / 旧数据可恢复）；不兼容变更必须在升级说明里**明写不可回滚**并给出人工步骤；升级后首次启动要能自证版本与数据格式。
- **归属环节**：D5
- **不是什么**：不是「重装一遍就算回滚」—— 数据格式变了重装也回不去；也不是「回滚脚本写了就行」，要实际走过一次。
- **判据**：【人判】接收方核三件：回滚路径是否存在且走过、不兼容点是否明写、首启能否自证版本。 **覆盖范围**：只看回滚路径是否存在且走过一次，判不了极端数据量下的回滚耗时。
- **负例**：改了数据格式却宣称「随时可回退」⇒ 判错；升级后启动无版本读数 ⇒ 退回。
- **读数口径**：报「升级路径 N / 有回滚 N / 实际走过回滚 N / 明写不可回滚 N」。
- **归属**：本节（交付层 D5）。

- **运行时与审计：每个自动动作留下「谁、何时、依据哪条」**：一切自动或半自动动作必须留下可检索记录（触发者、时间、依据条文或判据号、结果）；审计记录**只追加不改写**；日志里不写凭据与用户原文。
- **归属环节**：F1
- **不是什么**：不是「打个 print 就算审计」—— 无结构、不可检索、可被改写的日志不算审计。
- **判据**：【人判】接收方抽一条动作，要求当场在记录里找到这四项。**覆盖范围**：本环节无机判脚本。
- **负例**：动作执行完只留一句「已处理」⇒ 判错；日志被覆盖写导致历史丢失 ⇒ 退回。
- **读数口径**：报「自动动作 N / 四项齐全 N / 可改写的记录 N（应 0）」。
- **归属**：本节（运行层 F1）。

- **可观测与告警：先能看见，再谈告警**：运行态至少能回答三件事 —— 是否在跑、最近一次成功/失败在何时、失败原因是什么；告警要有阈值与去向，**没有去向的告警等于没有告警**。
- **归属环节**：F2
- **不是什么**：不是「有日志就等于可观测」；也不是「告警越多越好」—— 无去处的告警会把人练成不看。
- **判据**：【人判】接收方现场问这三件事，看能否当场答出。**覆盖范围**：本环节无机判脚本。
- **负例**：进程挂了三天没人知道 ⇒ 判错；告警发到一个没人看的分组 ⇒ 视为无告警。
- **读数口径**：报「三件事可答 N/3 / 有阈值与去向的告警 N」。
- **归属**：本节（运行层 F2）。

- **故障处置与复盘：先止血、再定性、后改规矩，三件事不许混在一轮做**：出事时第一步是**止血**（回滚 / 关闸 / 只读），第二步定性（改了什么、影响面、为何判据没拦住），第三步才动规矩（补条文或补判据）。**同一条故障第二次出现，不许再靠新增脚本解决** —— 说明上次定性错了。
- **归属环节**：F3
- **不是什么**：不是「写完复盘就结束」—— 复盘要落到**一条**具体改动（条文 / 判据 / 流程），不落就是故事。
- **判据**：【人判】复盘必须回答「为什么原有判据没拦住」；答不出即复盘无效。**覆盖范围**：本环节无机判脚本。
- **负例**：同类问题第二次出现、处置仍是「再加一个脚本」⇒ 判错；复盘只写时间线不写判据缺口 ⇒ 退回。
- **读数口径**：报「故障 N / 有止血动作 N / 回答判据缺口 N / 同类二次出现 N（应 0）」。
- **归属**：本节（运行层 F3）。

- **用户支持与文案：文案是交付物，随功能同批验收，不留「敬请期待」**：界面与提示文案随功能同批交付与验收；不许出现未实现功能的预告、占位文案、机器翻译腔；文案语言只许在册面上已声明的语言里，不许混入第三种。
- **归属环节**：F4
- **不是什么**：不是「文案以后再补」—— 空文案与错文案同属缺陷；也不是「原文照搬英文就是国际化」。
- **判据**：【人判】接收方按语言清单逐项看：有无第三种语言、有无未实现预告、有无占位符残留。**覆盖范围**：本环节无机判脚本（本仓的语言清单口径见项目册）。
- **负例**：菜单里出现三种语言 ⇒ 判错；「即将上线」写在已发布版本里 ⇒ 退回。
- **读数口径**：报「新增文案 N / 与功能同批 N / 第三种语言 0 / 占位残留 0」。
- **归属**：本节（运行层 F4）。


### 7.5 验证层补记：输入校验、依赖漏洞、测试分层、夹具、证据有效期

> 反查（2026-11-16）：`校验` 全文 **0 命中**、`回归` 0、`参数化` 0。
> 这个产品能执行 SQL、能跑 shell、能读写任意路径 —— **输入校验这条最大的口子此前一条规则都没有**。

- **一切外部输入必须参数化或白名单：字符串拼接进 SQL / 命令一律退回**：SQL 只许参数化绑定（`?` / 占位符），不许把值拼进语句；命令只许走白名单可执行文件并逐参数传数组，不许经 shell 拼字符串；文件路径必须规范化（解析 `..` 与符号链接）后校验前缀是否落在允许目录；URL / 主机名必须校验 scheme 与域名白名单。
- **归属环节**：C5
- **不是什么**：不是「转义了就行」—— 转义规则随驱动与编码变化，参数化才是结构上安全；也不是「内部工具不用管」，内部工具常常权限更大。
- **判据**：【人判】接收方读每一个新增的 SQL / 命令 / 路径 / URL 构造点：是参数化或白名单，还是字符串拼接。**覆盖范围**：本环节**无机判脚本**（〈落点 #54〉 判的是出口面，不判注入）；这条只能人读 diff。
- **负例**：`"SELECT * FROM t WHERE id = \(id)"` ⇒ 退回；`sh -c "grep \(pattern) file"` ⇒ 退回；`path = base + userInput` 未经规范化 ⇒ 退回。
- **读数口径**：报「构造点 N / 参数化或白名单 N / 字符串拼接 N（应 0）」。
- **归属**：本节（C5 输入校验）。

- **引入或升级依赖必须查已知漏洞并留结论**：新增依赖、升级版本、往仓里 vendored 第三方源码时，必须查一次已知漏洞（CVE / 安全公告），并在提交信息或依赖登记表里留一句结论：**无已知问题 / 有问题但为什么接受 / 已绕开的点**。查不了（无网 / 无数据源）就如实写「未查」。
- **归属环节**：C5
- **不是什么**：不是「版本越新越安全」；也不是「查过一次就永久有效」，漏洞是后来才公布的。
- **判据**：【人判】接收方核：本次依赖改动有没有那一句结论；写「未查」的有没有说明原因。**机判兜底**：〈落点 #52〉 只兜 vendored 件的登记表一致（版本 / 来源 / 许可），不判漏洞。
- **负例**：升级第三方库只写「升级到 2.3.1」而无漏洞结论 ⇒ 退回；写了「无已知漏洞」但给不出依据 ⇒ 判「未查」。
- **读数口径**：报「依赖改动 N / 有结论 N / 写未查 N / 无结论 N（应 0）」· **覆盖范围**：只判有没有留结论，判不了结论真假。
- **归属**：本节（C5 漏洞面）。

- **测试分层：日常跑相关层，提交前与推送前必须全量**：用例按三层归位 —— **单测**判行为与分支、**集成**判边界（真实编码 / 真实库 / 真实文件系统）、**端到端**只判最小纵切（一条主路径）。日常改动用「单测（可按类过滤）+ 相关集成」；但**提交前与推送前必须跑一次全量** —— 提交钩子对重判据是**跳过**（只跑轻判据），指望钩子等于没跑。跳过的项必须在汇报里写「未跑」。
- **归属环节**：C1
- **不是什么**：不是「全量跑得越多越安全」—— 每次都全量会让真失败的信号淹没在噪声里；也不是「单测绿了就算完」。
- **判据**：【人判】接收方核：本批改动属于哪层、跑的项与跳过的项是否都报出来。**机判兜底**：〈落点 #03〉 收尾行（`Executed N tests, 0 failures`）只证明跑过。
- **负例**：改了 Core 的解析逻辑却只报「全量绿」而不说跑了哪些 ⇒ 退回；把没跑的项算成通过 ⇒ 判错。
- **读数口径**：报「本批改动层：单测/集成/端到端 · 跑了 N 项 · 未跑 M 项（须点名）」· **覆盖范围**：判不了「该跑哪些」这类判断，只判「有没有如实报」。
- **归属**：本节（C1 测试分层）。

- **夹具必须可重建，且不许用真实用户数据**：测试夹具（样例文件、假响应、样例库）必须能由脚本重建（仓里有一条生成/还原路径）；不许把真实用户数据、真实凭据、真实内网地址写进夹具；外部依赖（网络、时钟、随机数）必须可替换，否则用例不可重复。
- **归属环节**：C1
- **不是什么**：不是「拷一份真数据最省事」—— 那份数据会一直躺在仓里；也不是「夹具随便手改就行」，改了两台机器跑出两种结果。
- **判据**：【人判】接收方核：夹具是否有重建脚本、是否含真数据、外部依赖是否可替换。**机判兜底**：〈落点 #50〉（公开仓扫描，凭据 / 内网地址 / 他人个人内容）。
- **负例**：把客户的一行数据写进测试夹具 ⇒ 判红（用户数据扫描判据）；夹具靠手工放进目录、无生成脚本 ⇒ 判「不可重建」。
- **读数口径**：报「夹具 N / 可重建 N / 含真数据 N（应 0）/ 外部依赖不可替换 N（应 0）」· **覆盖范围**：机判只扫公开仓文本，仓外副本与私有仓覆盖不到。
- **归属**：本节（C1 夹具）。

- **证据有效期与留存：能复现才算证据，跨版本即失效**：任何「已完成 / 已达标」的证据必须同时给出三件 —— **命令、环境（机器 / 版本 / 数据量）、时间**；缺一件即视为不可复现。证据跟着版本走：版本号变了，旧读数自动失效，必须在汇报里写「读数来自 vX，本版未复测」。
- **归属环节**：C3
- **不是什么**：不是「贴一段输出就是证据」—— 没命令没法复现；也不是「上周跑过，现在还行」。
- **判据**：【人判】接收方核三件是否齐、版本是否与本次一致。**机判兜底**：〈落点 #55〉 只兜性能读数表的阈值与新鲜度，通用证据无脚本。
- **负例**：贴一段测试输出但不说在哪个提交上跑的 ⇒ 判「不可复现」；用 v1.0.27 的读数证明 v1.0.29 通过 ⇒ 判错。
- **读数口径**：报「证据 N / 三件齐 N / 跨版本沿用 N（应 0）」· **覆盖范围**：只判证据的形状与版本对齐，判不了证据是否被挑选过（只贴绿的那一条）。
- **归属**：本节（C3 证据有效期）。


### 7.6 交付层补记：签名与分发认证、版本语义、解冻、三级投放、发布回执

> 反查（2026-11-16）：这五件事（签名 / 分发认证 / 解冻 / 灰度分批 / 发布回执）在原通用册 **0 命中**。
> 出的是桌面安装件，而「签名后要验证、给别人前要做分发认证」一条规则都没有 —— 没这两步，包在别人机器上会被系统直接拦掉。

- **出包必须签名并验证；分发到他人机器前必须完成该平台的分发认证**：出包后先验签（签名完整 + 分发链认可都必须过，本仓两条命令见〈落点 #56〉〈落点 #57〉）；包要交给别人用时必须完成该平台要求的分发认证与装订（具体认证流程见〈落点 #57〉），未认证的包只许自己用，并在交付说明里明写「未认证，需手动放行」。签名身份与凭据存储条目的名称要登记，换机器时照单重建。
- **归属环节**：D3
- **不是什么**：不是「能双击打开就算签好了」—— 本机能开常常是因为本机信任；也不是「认证一次永久有效」，证书过期后重签要重新认证。
- **判据**：【机判】〈落点 #56〉 与 〈落点 #57〉 两条命令输出必须为 accepted。【人判】分发说明里是否写了认证状态（已认证 / 未认证需手动放行）。
- **负例**：出包后不验签直接发给别人 ⇒ 判错；证书过期仍沿用旧包 ⇒ 判红（验签报 rejected）；交付说明不写认证状态 ⇒ 退回。
- **读数口径**：报「出包 N / 验签通过 N / 已认证 N / 未认证但明写 N」· **覆盖范围**：命令只判本机当前包的签名状态，判不了证书链在别人机器上的信任情况。
- **归属**：本节（D3 签名与分发认证）。

- **版本语义要写明：三段各代表什么，破坏性变更升中段**：三段式 `v主.次.补` 的含义必须写在该书的版本说明里 —— **主**：书的结构或契约面重写；**次**：契约面有增删（含破坏性变更，必须同时写迁移说明）；**补**：措辞、判据、数字修正。破坏性变更只升补位 = 判错。书版本与软件版本的对应关系按「冻结号 = 软件号」那条走。
- **归属环节**：D1
- 只写一处（2026-11-18 主人令补）：书的当前版本 **只**记在**版本表首行**，不许在头部另写一行「当前版本 vX」、也不许在正文另写「文档版本：vX」。同一个事实写两处必然漂 —— 实测概设头部 v1.3.26、版本表顶行停在 v1.3.12，差 12 版，谁对谁错没人能一眼说清。正文任何改动 = **在版本表加一行**；判据取表首（〈落点 #35〉）。
- **不是什么**：不是「改了就加一」—— 加在哪一位必须与改动性质一致；也不是「破坏性变更靠口头通知」。
- **判据**：【人判】接收方核：本次改动的性质与所升的位是否匹配；破坏性变更有没有迁移说明。**机判兜底**：〈落点 #35〉 只兜三段式形状与「当前版本 = 版本表首行」，不判位与改动是否匹配。
- **负例**：删掉一条契约条文却只升补位 ⇒ 判错；升中段但不写迁移说明 ⇒ 退回。
- **读数口径**：报「版本步进 N / 位与性质匹配 N / 破坏性有迁移说明 N」· **覆盖范围**：判不了「这次改动算不算破坏性」—— 那是判断，不是格式。
- **归属**：本节（D1 版本语义）。

- **解冻走「作废 + 重冻」：冻结件不许改，必须改就先作废**：冻结件只能读。冻结之后发现必须改内容时，做法是：① 记录作废原因与影响面；② 把当前冻结标记为「已作废（被 vX 取代）」；③ 从活书重新冻结一次，产出**新的**冻结件与新的软件号。直接改冻结件的任何一个字，都按「伪造冻结件」处理。
- **归属环节**：D2
- **不是什么**：不是「小改一下没事」—— 冻结件的价值就在于「事后可对账」，改一个字就废了；也不是「作废了旧的就不用留」，作废件必须留档。
- **判据**：【人判】接收方核：作废原因是否记、新冻结件是否为新文件、旧件是否仍在。**机判兜底**：〈落点 #44〉 与 〈落点 #58〉 兜冻结件与活书/软件号的一致。
- **负例**：直接在冻结件里改一句 ⇒ 判错；覆盖写同一个冻结文件名 ⇒ 判「无留档」。
- **读数口径**：报「解冻 N 次 / 有作废记录 N / 旧件留存 N / 覆盖写 N（应 0）」· **覆盖范围**：判不了「这次改动是否值得解冻」。
- **归属**：本节（D2 解冻）。

- **三级投放：自己用 → 小范围 → 全量，每级都要能退回**：任何新包不许一步全量投放。第一级只给自己用（至少一个完整工作日，覆盖一次真实任务）；第二级给指定的一两个人；第三级才全量。每一级必须写明「退回上一版」的动作（换回哪个包、数据是否需要回退），并确认退回动作真的能走通一次。
- **归属环节**：D5
- **不是什么**：不是「自己是第一个用户就算灰度」—— 要跑过真实任务；也不是「退回就是重装」—— 数据格式变了重装也回不去。
- **判据**：【人判】接收方核：三级是否逐级走过、每级的退回动作是否写明并走过一次。
- **负例**：新包直接全量替换 ⇒ 判错；写明「可回退」但从没走过 ⇒ 判「未验证」。
- **读数口径**：报「投放 N 次 / 分级走过 N / 退回动作验证过 N」· **覆盖范围**：判不了小范围用户是否真用了新功能。
- **归属**：本节（D5 三级投放）。

- **发布要有回执：谁、何时、能否正常启动**：发布之后必须收到接收方的回执 —— 谁装的、什么时间、是否正常启动（能打开主界面并完成一次最小动作）。没有回执的发布只能记「已投递」，不许记「已发布」；回执缺失超过一轮，必须主动追一次。
- **归属环节**：D4
- **不是什么**：不是「发了文件就算发布」—— 投递与可用是两件事；也不是「对方没说不就等于行」。
- **判据**：【人判】接收方核：发布记录里是否有回执三要素；没有的是否记成「已投递」。
- **负例**：把包放进共享目录就写「已发布」⇒ 判错；回执只写「收到了」而不说能否启动 ⇒ 判「不完整」。
- **读数口径**：报「发布 N / 有回执 N / 记为已投递 N / 回执缺三要素 N」· **覆盖范围**：判不了对方是否长期使用，只判「启动可用」这一件事。
- **归属**：本节（D4 回执）。


### 7.7 复检补记：许可分发、成本配额、备份演练

> 复检（2026-11-16，65 个方面 × 131 条交叉）剩下的最后三个真缺口 —— 其余 18 个「零命中」是词汇差异，不是缺口。
> 三件都有实物为证：`许可` 只作为登记字段存在、仓里有两个花费探针却无成本条文、「恢复备份」讲的是别覆盖记忆目录而不是演练。

- **分发必须附第三方许可与声明，有义务的必须履行**：包交给别人之前，必须能找到一份「本包内含哪些第三方件 / 各是什么许可 / 声明放在哪」；带署名或开源义务的许可（如 MIT 署名、Apache NOTICE、MPL 修改声明）必须履行，不许只留一行登记了事。声明位置写在交付说明里（包内文件或关于页二者其一）。
- **归属环节**：D3
- **不是什么**：不是「登记表里记了许可就算合规」—— 登记表是给自己看的，声明是给用户看的；也不是「自己用就不用附」以外的自由，一旦分发就要附。
- **判据**：【人判】接收方核：包内 / 关于页能否找到第三方许可声明，登记表里的许可义务是否逐条履行。**机判兜底**：〈落点 #52〉 只兜「登记表里有许可行」，不判声明是否随包。
- **负例**：把含 MIT 第三方件的包直接发给别人而不附声明 ⇒ 判错；登记表写「MIT」但关于页没有任何第三方页 ⇒ 判「未履行」。
- **读数口径**：报「第三方件 N / 有许可声明 N / 有义务已履行 N / 声明位置写明 N」· **覆盖范围**：判不了许可义务的法律判断（例如「这样算不算衍生作品」），只能判声明在不在、义务有没有落到实物。
- **归属**：本节（D3 许可）。

- **成本要有预算与配额，超了要停或降级并报数**：任何会花钱的路径（模型调用、外部 API、长时间构建 / 渲染）必须有预算：**每轮 / 每任务的上限**（调用次数、token、时长）、**超预算时的行为**（停、降级到便宜档、转人工）、**读数从哪来**（探针或读数表）。只说「注意成本」不算预算 —— 那既不告诉谁停，也不告诉停在哪。
- **归属环节**：C4
- **不是什么**：不是「花不了几个钱」—— 单价低乘上次数就是账单；也不是「超了就超了，下次注意」。
- **判据**：【人判】接收方核三件：上限有没有具体数值、超限行为是否明确、读数能否指到一次真实测量（仓里已有花费探针：〈落点 #59〉、〈落点 #60〉）。**覆盖范围**：本环节无机判脚本 —— 判不了「这个上限值合不合理」，只能判有没有上限与超限行为。
- **负例**：写了「控制调用次数」却不给数字 ⇒ 判错；超预算后没有任何自动动作、只在事后说一句 ⇒ 判「未定义行为」。
- **读数口径**：报「花钱路径 N / 有数值上限 N / 有超限行为 N / 有读数来源 N」。
- **归属**：本节（C4 成本）。

- **备份必须演练过恢复：没恢复过的备份等于没有**：任何声称「有备份」的数据面，必须至少演练过一次**完整恢复**，并记录三件：**恢复耗时、丢失范围（最多丢多少）、恢复后自检怎么证明是好的**。备份只写「已配置自动备份」不算——那只能证明文件存在，不能证明能回来。
- **归属环节**：D5
- **不是什么**：不是「备份文件在就算安全」；也不是「演练一次永久有效」—— 数据面变了（换库、换机器、改格式）要重新演练。
- **判据**：【人判】接收方核：恢复演练的记录三件是否齐、数据面变化后是否重演。**覆盖范围**：本环节无机判脚本 —— 判不了「备份件里数据是否完整」，只能判「演练有没有做过、记录是否可核」。
- **负例**：说「有每日备份」但从未恢复过 ⇒ 判错；演练记录只写「恢复成功」而不写耗时与丢失范围 ⇒ 判「不完整」。
- **读数口径**：报「数据面 N / 演练过 N / 三件齐 N / 数据面变化后未重演 N（应 0）」。
- **归属**：本节（D5 备份演练）。

## 7.8 运行层补记：审计留存、指标与阈值、事故分级、面向用户的话

> 由来（人类主人 2026-11-18「补」）：F1–F4 原先各只有 1 条，等于整个运行阶段只写了「要留痕 / 要能看见 / 要止血 / 文案别乱」四句口号。
> 本节按「出事那天真的会问的问题」补到每个环节 4 条。**判据诚实度优先**：本仓没有运行期判据物的，一律写【人判】并说明覆盖范围，不挂名字相近的脚本冒充。

- **审计记录必须有留存期与检索入口**：审计记录写明保存多久、按什么维度能检索（动作 / 设备 / 条目号 / 时间窗）；过期删除本身要有记录，不许悄悄清空。
- **归属环节**：F1
- **不是什么**：不是「日志文件在那就算有」—— 没人知道存多久、按什么查，等于查不到。
- **判据**：【人判】接收方随机给一个条目号，要求当场从审计里查出该条目最近三次动作及其时间。
- **覆盖范围**：本仓无运行期审计留存判据物；只判「能不能按条目号查到」，判不了留存期是否合规、也判不了删除记录是否完整。
- **负例**：问「这条记录存到什么时候」答不出 ⇒ 判错；审计目录被清空且无删除记录 ⇒ 退回。
- **读数口径**：报「条目能查到 N / 留存期已写明 N / 删除有记录 N」。
- **归属**：本节（运行层 F1）。

- **审计字段必须结构化落盘，不是拼一句话**：触发者、时间、依据（条文号或判据号）、结果四件各自成字段；同一动作若被闸门跳过或强制，跳过与强制必须成对出现，不许只留一半。
- **归属环节**：F1
- **不是什么**：不是「拼成一行中文就够了」—— 拼字符串无法按字段检索、也无法证明跳过与强制成对。
- **判据**：【机判】〈落点 #61〉（闸门跳过记成 notice、强制与跳过成对、通知双出口都落记录、静默决策不留记录，四条用例必须绿）。
- **覆盖范围**：只判 Agent 决策与通知这一面的审计字段；其它模块（笔记、连接、插件）的审计无判据。
- **负例**：只记「已跳过」而不记被谁强制 ⇒ `testGateForceIsPairedWithTheSkip` 判红。
- **读数口径**：报「审计面 N / 有结构化字段 N / 跳过强制成对 N」。
- **归属**：本节（运行层 F1）。

- **敏感面必须进审计：出站请求、写外部状态、跨仓推送**：这三类动作即使成功也要留记录；失败更要留，且要能看出「试过几次、最后一次错在哪」。
- **归属环节**：F1
- **不是什么**：不是「只在失败时记」—— 成功但无人知的动作正是出事时最难查的那类。
- **判据**：【人判】接收方抽一次出站请求 / 一次外部写 / 一次推送，要求各自在审计里找到记录与重试次数。
- **覆盖范围**：本仓无运行期出站审计判据物（出口清单判据判的是**代码里的清单**，不判运行时有没有留记录）。
- **负例**：能证明某个写操作发生过，但审计里查不到 ⇒ 判错。
- **读数口径**：报「敏感面三类 / 有审计 N / 带重试次数 N」。
- **归属**：本节（运行层 F1）。

- **关键指标只许一个读数来源**：每个指标（延迟、失败率、队列长度、花费）写清由谁算、在哪读；同一指标不许两处各算一套，两套必然吵架。
- **归属环节**：F2
- **不是什么**：不是「多算几处取平均」—— 多来源不是冗余，是两套口径。
- **判据**：【人判】接收方指着任一指标问「这个数谁算的」，必须能答出唯一来源；答出两个即判错。
- **覆盖范围**：本仓无运行期指标采集判据物；只判「有没有唯一来源」，判不了这个来源算得对不对。
- **负例**：界面显示 12%、日志算出 30% ⇒ 判错。
- **读数口径**：报「指标 N / 有唯一来源 N / 两套口径 N（应 0）」。
- **归属**：本节（运行层 F2）。

- **告警三件套：阈值、责任人、静音与升级规则**：每条告警写明阈值是多少、发给谁、什么条件下静音、多久没响应就升级；三件缺一即视为没有告警。
- **归属环节**：F2
- **不是什么**：不是「告警越多越安全」—— 没有责任人和升级规则的告警，只会把人训练成不看。
- **判据**：【人判】接收方逐条问某条告警：阈值多少、谁收、静音条件、几小时升级；四问答不全即判错。
- **覆盖范围**：本仓无运行期告警配置物（无告警服务、无通知渠道配置），只能人判；判不了告警是否真的送达。
- **负例**：告警配了阈值但没写责任人 ⇒ 判错；静音没有期限 ⇒ 退回。
- **读数口径**：报「告警 N / 四问齐 N / 无责任人 N（应 0）」。
- **归属**：本节（运行层 F2）。

- **性能读数必须落读数表，阈值变化要留痕**：每次测量的读数、机器、场景写进读数表；阈值只许按记录调，不许凭感觉改。
- **归属环节**：F2
- **不是什么**：不是「测完贴聊天里就算记录」—— 读数表之外的口头读数下次没法比对。
- **判据**：【机判】〈落点 #62〉（读数条目带阈值与新鲜度，超期即红）。
- **覆盖范围**：只判读数表形状与新鲜度；不判阈值定得合不合理（那是 F3 复盘时要回答的）。
- **负例**：把阈值从 800ms 改成 1200ms 却不写理由 ⇒ 读数表无留痕，判红。
- **读数口径**：报「读数条目 N / 带阈值 N / 超期 N（应 0）」。
- **归属**：本节（运行层 F2）。

- **事故先分级：影响面决定时限，不许所有事故同优先级**：按「影响多少使用者 / 是否丢数据 / 能否绕开」分三级，每级写明响应时限与谁拍板；分级动作在止血之前完成，一句话即可。
- **归属环节**：F3
- **不是什么**：不是「事后再补分级」—— 分级决定先救谁，事后再定等于没定。
- **判据**：【人判】接收方看事故记录第一行：有没有级别、有没有影响面、有没有响应时限；三样缺一即判错。
- **覆盖范围**：本仓无事故记录判据物；只判记录里有没有分级三样，判不了时限是否被遵守。
- **负例**：两个事故一个丢数据一个只影响自己，处置顺序却按发生时间 ⇒ 判错。
- **读数口径**：报「事故 N / 有级别与时限 N / 分级在止血之前 N」。
- **归属**：本节（运行层 F3）。

- **复盘五项齐全：时间线、影响面、根因、为何判据没拦、改哪一条**：五项缺一即复盘无效；「改哪一条」必须指到具体条文号或判据文件名，不许写「加强测试」。
- **归属环节**：F3
- **不是什么**：不是「写清时间线就是复盘」—— 时间线只是第一项，缺后四项等于只讲发生了什么。
- **判据**：【人判】接收方按五项逐条核；第五项指不到具体条文号或判据文件即判错。
- **覆盖范围**：本仓无复盘模板判据物；只判五项在不在、第五项是否指名，判不了根因判断对不对。
- **负例**：复盘写「今后加强测试」⇒ 第五项未指名，退回。
- **读数口径**：报「复盘 N / 五项齐 N / 第五项指名 N」。
- **归属**：本节（运行层 F3）。

- **止血动作必须事前演练过，不许现场发明**：每条回滚 / 关闸 / 只读路径，在出事之前至少走通一次并记下耗时；现场第一次执行的止损不算止血，算第二次事故。
- **归属环节**：F3
- **不是什么**：不是「文档里写了回滚步骤就算演练过」—— 没跑过的步骤，真出事时总有一句命令是错的。
- **判据**：【人判】接收方要求指出该路径最近一次演练的时间与耗时；只有文档没有演练记录即判错。
- **覆盖范围**：本仓无演练记录判据物；只判演练是否发生过，判不了演练时数据量是否与真实一致。
- **负例**：回滚脚本第一次被执行是在事故现场 ⇒ 判错。
- **读数口径**：报「止血路径 N / 演练过 N / 有耗时记录 N」。

- **不是什么**：不是「先写死以后再抽」—— 基线只降不升，写死一条就欠一条。

## 9 协作层补记：沉淀、分支、外部协作者

> 反查（2026-11-16）：`技能` 全文 **0 命中**、`rebase` 通用册 0、`协作者`/`外部助理` 0。
> 这三件是「多个人（或多个助理）在同一仓干活」的底座：不沉淀就会重复踩坑，不约定分支就会互相覆盖，不声明就会双写。

- **非显然的做法必须在 24 小时内沉淀成可复用件**：一次做完、但下次还会遇到的做法（判据怎么设计、某类门禁怎么写、某个坑怎么绕），必须落成 **skill**（触发条件 + 步骤 + 判据 + 反例）或脚本 + 说明；没沉淀的，这件事算没做完。沉淀件要能被另一个助理在**新会话**里直接使用 —— 有触发条件、有步骤、有验证方式，不靠口头补充。
- **归属环节**：E3
- **不是什么**：不是「记在对话里就行」—— 会话会丢；也不是「写成一篇长文」，没有触发条件的长文等于没有。
- **判据**：【人判】接收方核：本批有没有产生「下次还会遇到」的做法；有的话沉淀件在哪、能否按它独立复现。**覆盖范围**：本环节无机判脚本 —— 判不了「这个做法值不值得沉淀」，只能判「有没有产出可用的沉淀件」。
- **负例**：同一个坑第二次出现仍靠现场回忆解决 ⇒ 判错（应已沉淀）；沉淀件只写结论不写触发条件 ⇒ 判「不可用」。
- **读数口径**：报「非显然做法 N / 已沉淀 N / 新会话可用 N / 重复踩坑 N（应 0）」。
- **归属**：本节（E3 沉淀）。

- **一处在途改动一条分支；合并前 rebase 到最新并重跑门禁；冲突不许猜着解**：每个在途改动占用一条分支（或一个明确的独占文件集），不许两个人同时改同一条分支；合并前必须 rebase 到最新基线并**重跑门禁**；合并冲突里涉及**别人的行**时必须问原主，不许「看起来能过就这样解」。
- **归属环节**：E2
- **不是什么**：不是「本地能跑就能合」—— 冲突解决后的代码没人验过；也不是「谁的改动多听谁的」。
- **判据**：【人判】接收方核：分支是否独占、合并前是否 rebase 过且门禁重跑、冲突中别人的行是否问过。**覆盖范围**：判不了分支命名与团队习惯是否一致，只判这三件在不在。
- **负例**：把别人分支上的改动直接覆盖 ⇒ 判错；冲突解完不跑门禁就合并 ⇒ 退回；冲突行是自己改别人的代码且没问 ⇒ 判错。
- **读数口径**：报「在途分支 N / 独占 N / 合并前重跑门禁 N / 涉他冲突问过 N」。
- **归属**：本节（E2 分支）。

- **外部协作者动工前先声明：动哪些文件、哪条分支、预期产出**：另一个助理、另一个 AI、或任何自动化工具在**同一个仓**动手之前，必须先写一句声明（动哪些路径 / 哪条分支 / 预期产出 / 预计时长），并在产出后回执一句「实际改了哪些」。没有声明的，按双写风险处理 —— 先停，先问。
- **归属环节**：E1
- **不是什么**：不是「反正每次提交会看到」—— 等看到时冲突已经发生了；也不是「同一个 AI 就不用声明」，换会话就是换人。
- **判据**：【人判】接收方核：动手前有没有声明、产出后有没有回执；`git status --short` 里是否出现了声明之外的文件。
- **负例**：直接开干且改了三个文件，事后才说「顺手改的」⇒ 判错；两个助理同时改同一节 ⇒ 判错（应先声明再串行）。
- **读数口径**：报「外部协作者 N / 有前置声明 N / 有产出回执 N / 声明外改动 N（应 0）」· **覆盖范围**：判不了声明之后是否按声明执行，只能靠回执与 `git status` 对照。
- **归属**：本节（E1 协作者）。
