## 序言

这本规范不是设计出来的，是被返工逼出来的。

它最早是一页「注意事项」，后来是十五条款式的铁律，再后来分成了两册、长到了十二个章节。每一次增补都对应一次真实的踩坑：把项目专名写进通用册，换个项目就整本失效；把规矩只写在散文里，检查脚本一年都看不见它；章节随手加，最后连「这条该放哪」都没人说得清。

它替接手的人解决的问题是：不必把同一批坑再踩一遍。哪些事情做了会返工、做完什么样才算真做完、怎么验证才算不是自欺，这些都有明文，不需要重新商量。

它不解决的问题是：它不替你判断这个需求该不该做，不替你选技术栈，也不保证守着条文就一定能做出好东西 —— 它只管「怎么做才算合格」，不管「做什么」。

它分两册：这一册写形态（任何项目都成立），另一册写事实（这个项目的参数与落点）。


## 第一章 总纲

第一条【本规范的效力与范围】
（一）**是什么**：本规范只规定「任何项目、任何技术栈都成立的开发形态」：文档怎么写、条文怎么立、判据怎么设、交接怎么交、证据怎么留。违反即返工，没有例外。
（二）**为什么**：此前通用册混进过某一端的实现细节，换一个项目整本失效；反过来，项目事实混进通用册，任何项目照抄都会错。
（三）**不是什么**：不管具体项目的技术选型、目录路径、发布参数、平台专有名 —— 那些属项目规范。也不是建议，是硬约束。
（四）**判据**：【机判】通用册正文出现项目专名 / 具体脚本路径 / 具体命令 / 指回项目的编号 ⇒ 判红（判据物：check-rule-schema · landing_purity / section_refs）。【人判】新增条文对「所有项目」是否成立。
（五）**能力前提**：动手前能同时读到项目规范，才判得出「这是形态还是事实」；只能读到一册时，只许写形态。
（六）**负例**：往本书写某个平台的具体构建命令 ⇒ 必须判红；写某个平台的专有名 ⇒ 必须判红。
（七）**读数口径**：报「专名命中数 / 条文总数」。覆盖范围：判得了可枚举的专名与路径，判不了「这条形态在实践中是否真成立」。
（八）**归属环节**：全局

第二条【规则分两册：通用册写形态，项目册写事实】
（一）**是什么**：本册只写「对所有项目都成立的规矩」—— 换一个项目、换一套技术栈、换一个仓，整份照抄仍然成立；具体工具、端名、路径、参数、产品口径一律写进项目册。两件**不合并**：合并成一本，换项目就得重写整本。
（二）**为什么**：合订成一本时，某一端的实现细节（平台专名、脚本路径）会冒充通用规则；换项目整本失效，等于把「规范」降级成「某个项目的笔记」。
（三）**不是什么**：不是「通用册可以顺带举点本项目例子」—— 举了例子就该照抄得改；也不是「合并成一本更省事」—— 省的是第一次写的时间，赔的是每一次换项目；也不是「项目册可以反过来规定通用规矩」—— 项目册只能写本项目怎么落地。
（四）**判据**：【机判】〈判据物〉 两判：① 本册出现项目事实（工具名 / 端名 / 目录与文件名 / 具体编号）即红；② 本册出现指回项目册的指针（书名 / 节号 / 落点编号）即红 —— 方向只有项目册 → 本册。【人判】新项目若要采用本册：**整份照抄不改一个字**，抄完发现「这句话得改」的地方 ⇒ 分册失败，那句话本该写进项目册。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：往本册写「用某个平台的打包工具出包」⇒ 必须判红；写「详见另一册的某一节」⇒ 必须判红；把两册并成一本 ⇒ 换项目时那个项目的事实就得跟着改（人判：抄完要改 = 分册失败）。
（七）**读数口径**：报「本册条文数 / 含项目事实的条数（应为 0）/ 指回项目册的指针数（应为 0）」，不报「已经通用了」。 覆盖范围：机判只认可枚举的形态（项目事实词表 + 六种指针写法），换个说法认不出，只报人判；「这条规矩是否真对所有项目成立」判不了 —— 那要靠第二个项目照抄一遍才算验过（本册至今没有第二个项目验过，如实记）。
（八）**归属环节**：全局

第三条【本书的结构】
（一）**是什么**：全书 = 序言 + 九章 + 条。序言是叙述层（不编号、不判）；第一章总纲管规范自身；第二章管 Agent 的权利与义务；第三至第八章一章一个开发阶段；第九章附则管版本、废止、术语。条号从第一条起全书连续，永不重排、永不复用。
（二）**为什么**：此前两套骨架硬拼：27 个环节的条文全覆盖，却只有 2 章按环节写，其余进了「补记」；63 条躺在不含其归属环节的章里，谁也不敢搬 —— 因为引用按章号，搬一章断一片。
（三）**不是什么**：不按问题域分章（文档 / 代码 / 判据），那会让同一条在两个域里都说得通，于是又长出「补记」；章内不设「节」，除非单章超过十条。
（四）**判据**：【机判】① 章必须在九章闭集内，新开章即红；② 条号从第一条起连续、不跳号不重号（判据物：check-rule-schema · numbering）；③ 条文所在的章必须与它「归属环节」的所属阶段一致。【人判】序言与总纲是否真的只讲规范自身。
（五）**能力前提**：改结构前能跑一遍条号判据；跑不了时不许改结构。
（六）**负例**：新开一章「其他规则」⇒ 必须判红；把第 42 条挪到别章却没改归属环节 ⇒ 必须判红；条号从第 40 条跳到第 42 条 ⇒ 必须判红。
（七）**读数口径**：报「章数 / 条数 / 条号最大序号 / 错位条数」。覆盖范围：判得了章名、条号、阶段归属；判不了「章的先后顺序是否合理」。
（八）**归属环节**：全局

第四条【条文体裁：一条条文要回答七问（5W1H1W）】
（一）**是什么**：本册条文按法条的体裁写 —— 法条之所以最规范，是因为它强制回答七问：**为什么有这一条**（Why）/ **它长什么样**（What）/ **判什么、能做什么**（What）/ **要什么才守得住、判得了**（Capability / How）/ **判错什么样**（How）/ **谁看、谁判**（Who）/ **什么时候必须回来读**（When）。缺哪一问，这一条就在那个场合失效。
（二）**为什么**：这本书本身就是从「没规定条文该回答什么」里长歪的 —— 章节随手加、分册理由只写在散文里、格式只停在对话里。只有「是什么 + 怎么判」时，条文读起来像检查表；一遇到「这条为什么存在」「拿不到那个能力怎么办」就没人答得上来。
（三）**不是什么**：不是「七问都要写满字」—— 每问有其字段即可；也不是「存量条文已经合规」—— 存量缺「为什么」「能力前提」两问，按欠账基线只许降；也不是「法条的样子就是编号」—— 编号只为引用不断，七问才是目的。
（四）**判据**：【机判】〈判据物〉 两判：① 缺「为什么」的条文条数不得升过欠账基线；② 缺「能力前提」的条数不得升过基线。**七问是否真回答到位**（答非所问、抄一句套话）判不了，属人判。
（五）**能力前提**：要真守住七问，需要三样同时在手 —— ① 每条的出处（哪件事、哪次事故、哪个决定）在写的时候查得到；② 判据要的那个能力（脚本 / 权限 / 真机 / 外部系统）在判的场合拿得到；③ 「谁看、什么时候看」有落点（判据里的人判机判 + 归属环节）。三样缺一样，那一问只许写「未知」，**不许编**。
（六）**负例**：新写一条条文不写「为什么」⇒ 计数 +1 超过基线，判红；补了一条存量却没同批降基线 ⇒ 判红（读数是强断言，不是参考值）。
（七）**读数口径**：报「七问欠账：缺为什么 N/M 条、缺能力前提 N/M 条」，不报「体裁统一」这种话。 覆盖范围：机判只判两个字段在不在、计数有没有超基线；判不了内容是否敷衍，也判不了 Who / When 是否填对（Who 靠判据里的【机判】/【人判】点名，When 靠归属环节，两者的正确性由别的条文判）。
（八）**归属环节**：全局

第五条【给谁看、什么时候看】
（一）**是什么**：两类读者：接手这个仓的 Agent，和接手这个仓的人。时机有四个：开工前读本阶段那一章；改文档前读第二章与第三章；提交前读第四章；出包或发布前读第六章与第九章。总纲与第二章任何一次动手前都要读。
（二）**为什么**：此前只有一张集中索引，它要维护全书，一改就漂；章首自述只维护本章。读错章的原因通常是不知道「什么时候该读哪一章」。
（三）**不是什么**：不是「全文读一遍就够」：条文只在对应时机才用得上，其余时候记住存在即可。也不是「只读铁律就够」。
（四）**判据**：【人判】每章章首是否写明「进这一章前必读哪几条」与「本章有几条机判几条人判」。【机判】章首缺「必读」块 ⇒ 报缺失读数（不判红，属体例债）。
（五）**能力前提**：章首要能自动算出「本章机判 / 人判条数」，否则只能手写、必然漂。
（六）**负例**：章首不写必读条、只写一句「请通读全章」⇒ 人判不合格。
（七）**读数口径**：报「有必读块的章数 / 总章数」。覆盖范围：判不了「必读那几条是否选对」。
（八）**归属环节**：全局

第六条【谁能改、怎么改】
（一）**是什么**：改这本规范是分权动作。人：可直接改条文、可新增、可废止（废止只标状态，不删字）、可改结构。Agent：条文与结构只许提案（写清归属环节、七问八款、判据、负例），由人批准后才落笔；项目册与判据脚本可直接改，但必须同批交负例。
（二）**为什么**：此前无此规定，Agent 可以随手加条文、随手给全书去项目化、随手改名，代价是每次都要人肉复查全书 —— 权限不清等于把审查成本转嫁给读的人。
（三）**不是什么**：不是「Agent 不能改规范」：提案与落笔是两个动作，提案是义务，落笔要授权。也不是「人不受约束」：人改也要走版本与留痕。
（四）**判据**：【机判】条文的增删改必须在提交信息里写明「第N条：新增 / 修改 / 废止 + 理由」，缺则红；废止条必须指向替代条号且替代条必须存在；已被废止的条不许再被引用。【人判】Agent 的提案是否真被批准过。
（五）**能力前提**：提交信息能机读（约定固定前缀）；否则只能人判。
（六）**负例**：Agent 直接改写第三条正文且提交信息不写「第3条：修改」⇒ 必须判红；标「已废止」却不写被哪条替代 ⇒ 必须判红。
（七）**读数口径**：报「本轮条文增 / 删 / 改 / 废止各几条」。覆盖范围：判得了留痕与废止指向，判不了「这次改动该不该做」。
（八）**归属环节**：全局

第七条【判据必须声明覆盖范围】
（一）**是什么**：任何「报缺失/报异常」的判据，先说清扫了哪些目标源、哪些没扫。
（二）**为什么**：没声明覆盖范围的判据会把「没扫」说成「没有」，坏判据比没有判据更危险。
（三）**不是什么**：不是「加了 `--json` 就算声明」；覆盖不全时**只许报「未知」，不许报「发现」**。
（四）**判据**：【人判】脚本 `--json` 输出有没有 `sources` / `uncovered` 两段、交接说明写没写，由评审人核；`uncovered` 非空而结论报「发现」即判错。 **覆盖范围**：本条只判「有没有写覆盖范围」，不判声明是否真实——真实性由铁律 15 独立验收层兜。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：悬空引用检测扫了 48 个源报「23 处异常」，实际漏扫分仓 ⇒ 必须报「未知」而不是「23 处」。
（七）**读数口径**：报「覆盖 N 源 / 未覆盖 M 源 / 结论：发现｜未知」。
（八）**归属环节**：全局

第八条【每条判据配一条「必须判红」的负例】
（一）**是什么**：正例只证明能通过，负例才证明真会拦；新写或改写的门禁必须同时交一个故意违规的样本。执行器：〈判据物〉（造不出文件层负例的必须登记在 〈判据物〉 并写清原因，未登记即红）。
（二）**为什么**：正例只证明能通过，负例才证明真会拦；没有负例的判据往往永远绿。
（三）**不是什么**：不是「有单测就算」—— 必须有一条**故意违规**的用例，且它必须判红。
（四）**判据**：【机判】〈判据物〉（各门禁自测计数与登记一致）+ 〈判据物〉；新增门禁无负例用例即红。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把 〈判据物〉 里 `doc-versions` 族的 `cases` 改大 1（`--no-run` 只做例数与锚点对账）⇒ 〈判据物〉 判红「写的是 8、登记值是 9」（2026-11-10 实测）；新门禁只写「合规输入 ⇒ 绿」同样被发现负例数 0 即红。
（七）**读数口径**：报「负例数 / 断言数」两个数，不报「自检通过」。 覆盖范围：只判「登记的自测例数与实跑一致」和「新增门禁有没有负例」，判不了那条负例是否真能覆盖会发生失效形态（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：全局

第九条【独立验收层：判「对」的依据不许由被判方提供】
（一）**是什么**：判「对」只认三样：人类主人原话 / 契约条文（三书判据行）/ 外部权威系统（编译器、测试框架、真机）。
（二）**为什么**：自己写的代码自己说对、自己生成的 spec 自己引用，是「看起来完成了」的主要来源。
（三）**不是什么**：不是「自己跑通了就算对」；生成 spec/代码/测试的同一个模型不能同时判定它对。
（四）**判据**：【人判】交接说明里每条「已完成」必须指名依据属于哪一类（口径编号 / 主人原话 / 命令输出）；只写「我验过了」= 判错。 **覆盖范围**：只看依据是否指向三类之一，判不了依据本身是否站得住。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：【人判】交接写「已按我最新的理解实现并自测通过」而不指名契约条文号 ⇒ 判错。
（七）**读数口径**：报「已完成条目数 / 其中指明依据的条数」。
（八）**归属环节**：全局


## 第二章 Agent 的权利与义务

第十条【不弹窗要授权】
（一）**是什么**：需要授权或拍板的进队列，能做的一律先做，不许因等确认停工。
（二）**为什么**：因等一个确认而停工，交付时间被拖在等待上；而有的事根本不需要确认。
（三）**不是什么**：不是「等主人回话才继续」；也不是「把要授权的事自己做了」—— 前者停工，后者越权。
（四）**判据**：【机判】〈判据物〉（队列行**状态词**在词表内 + `needs-user` 行**点名**到仍待拍的号）；【人判】「这件事该不该问主人」「有没有绕过队列直接做了」由本人判。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：需要主人授权的动作没进队列而直接在提交里做了 ⇒ 判错（人判：〈判据物〉 判不了「该不该问主人」，它只判队列行的状态词与点名）。
（七）**读数口径**：报「队列新增 N 条 / 已自行完成 M 条」。 覆盖范围：机判只判队列状态词与 `needs-user` 点名，判不了「这件事该不该问主人」和「有没有绕过队列先做了」（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：全局

第十一条【不擅自改外部状态】
（一）**是什么**：不在别人的数据库上建库建号、不改数据库服务的**认证配置**、不为跑测试在本机装服务 —— 只给命令，不执行。
（二）**为什么**：在别人的库建库建号、改数据库认证配置、为跑测试在本机装服务 —— 影响面在别人的环境里，事后无法自证干净。
（三）**不是什么**：不是「只读操作也要问」（查连接、看报错、跑只读查询都不用授权）；也不是「本地环境随便装」—— 装服务同样算改外部状态。
（四）**判据**：【人判】执行记录里有没有对他人库 / 系统配置的写操作，由本人自查 + 交接说明注明；判定口径与**具体对象**（哪台机、哪份配置文件）属项目事实，本册不写，也不指节号。 **覆盖范围**：只看交接说明里有没有「已执行」的外部写动作及其授权来源，看不到命令是否真被执行。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：【人判】为跑测试在自己机器上装一个数据库服务，并写进交接当「已就绪」⇒ 判错。
（七）**读数口径**：报「给出命令 N 条 / 已执行 0 条」。
（八）**归属环节**：全局

第十二条【删除前确认范围】
（一）**是什么**：「清理掉」先确认是部分文件还是整个目录，范围写进命令再执行。
（二）**为什么**：「清理掉」被理解成整个目录而不是部分文件，删掉的东西不可恢复。
（三）**不是什么**：不是「先删再问」；也不是「备份了就能删」—— 备份不是授权。
（四）**判据**：【人判】删除命令必须带明确路径通配并在此前贴出 `ls` 结果，由本人核对。 **覆盖范围**：只看删除前是否贴出范围清单，不判清单是否完整（完整性靠事中复核）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：【人判】收到「清理掉旧包」直接 `rm -rf dist/` ⇒ 判错（只该删过期的单个文件）。
（七）**读数口径**：报「待删 N 个 / 实删 N 个 / 保留 N 个」。
（八）**归属环节**：全局

第十三条【报数报「还剩多少」】
（一）**是什么**：报数报「还剩多少 / 缺在哪」，不报「扫了多少」。
（二）**为什么**：报「扫了多少 / 已登记」会让人误以为已经修完；「已登记」≠「已修完」。
（三）**不是什么**：不是「已登记 = 已修完」；也不是「覆盖率 96% 可以当结论」。
（四）**判据**：【人判】结论句里有没有「还剩/缺在哪」，由接收方读（**本条主体是人判**）；【机判】〈判据物〉 只兜「写死的数字必须与实测一致」。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：报告写「已完成 391 条中的 379 条」而不说剩 6 条未闭 ⇒ 〈判据物〉 判不出，接收方判错（故本条保留人判）。
（七）**读数口径**：报「总数 / 已闭 / **未闭**」三值，未闭必须点名。 覆盖范围：机判只兜「写死的数字与实测一致」，判不了结论句里有没有报剩余（那是读句子，人判）（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：全局


## 第三章 规划

第十四条【文档改动必过门禁】
（一）**是什么**：改完文档不是「读一遍顺就行」，必须把该动作对应的门禁整套跑一遍、拿到 `exit 0`；门禁清单由项目册列出，跑不完就等于没改完。
（二）**为什么**：改完文档读一遍「顺了」不算改完；门禁跑不完时，文档与判据、与代码的真值已经分叉。
（三）**不是什么**：不是「审一遍读起来顺就行」—— 门禁入口由项目册列出，不是可选项。
（四）**判据**：【机判】〈判据物〉 文档项（含 〈判据物〉）；**入场判据 = 〈判据物〉** —— 按改动推断动作、把该动作的必跑判据全跑一遍（2026-11-10 修过一个洞：原来只看暂存区，暂存两个脚本就再也不看工作区，文档那套判据一条没跑，注入重复 `Q37` 仍 rc=0）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：删掉某个标题导致表格列数变化而不跑门禁 ⇒ 〈判据物〉 必须判红；把 `| **Q37**` 那一行复制一份（同号两行）再跑 `action-router --changed --check --fast` ⇒ 必须 rc=1（2026-11-10 实测）。
（七）**读数口径**：报「文档项：绿/红 + 失败脚本名」。 覆盖范围：只判动作对应的判据跑过、门禁输出在，判不了「该改的文档这次到底改没改」（那由 〈判据物〉 报告 + 人判）（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：A2

第十五条【不擅自扩大文档体系】
（一）**是什么**：两层都不许扩 —— ① **不多一本书**：只认三书 + 进度清单，不许新建第六本书 / 索引 / 派生表 / 清单，门禁要的中间产物落 构建产物目录；② **不多一个杂项章**：规范正文的章 = 开发环节（A1…F4），新章必须是环节章，条文必须落在它「归属环节」那一章里，跨环节的元规则只能进已有的元规则章。
（二）**为什么**：文档一多就没人读完；每加一本书就多一份会漂的副本。实测：同一状态散在多本册子里只改一处，必留矛盾。
（三）**不是什么**：不是「有用就可以新建一本」；也不是「索引不算书」—— 索引 / 派生表一律进 派生件区。同样不是「有心得就新开一章」—— 「补记 / 杂项 / 临时 / 其它」不是章节名，是结构失控的痕迹；也不是「索引能查到就算归位」，索引是补丁，不是结构。
（四）**判据**：【机判】〈判据物〉（文档根白名单）、〈判据物〉、〈判据物〉；**章节结构**由〈判据物〉三判 + 一读：① 每章要么标题点名环节编号，要么在「非环节章」白名单里，不在即红；② 白名单里的章正文已不存在即红（白名单只减不增，删章必须同批划掉）；③ 新章标题带「补记 / 杂项 / 临时 / 其它」即红；④ 读数：条文躺在不点它归属环节的章里的**错位条数**，只许下降。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：在文档根新建《…测试登记.md》⇒ 〈判据物〉 必须判红；随手新开一章「其他补记」⇒ 章节结构判据必须判红；把某条实现环节的条文塞进验证章 ⇒ 错位读数 +1，超过上限即判红；删掉一章却忘了划白名单 ⇒ 判红。
（七）**读数口径**：报「文档根 N 份 / 越界 M 份」+「章数 · 环节章数 · 错位条数 · 补记类章残留数」，不报「结构合理」这种话。 覆盖范围：只判文档根白名单、放置规则与「章 ↔ 归属环节」对不对得上，判不了「这本书该不该存在」「这条条文该不该存在」（都是决策），也判不了同一环节的条文该不该合并（人判）；错位读数上限是按重排前记下的，降到 0 才算结构归位（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：A2

第十六条【一条拍板只落一处结论】
（一）**是什么**：同一状态散在多本册子只改一处必留矛盾 ⇒ 状态唯一源 = 进度清单。
（二）**为什么**：同一状态散在多本册子里，只改一处必留矛盾；矛盾一旦出现，没人知道哪一处是对的。
（三）**不是什么**：不是「多写几处更保险」—— 同一状态写两处必然只改一处，留下矛盾。
（四）**判据**：【机判】〈判据物〉（跨册状态比对）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：在概设正文给已 ✅ 的编号 `需求条目` 紧贴一个 ⬜ 括注（编号与全角括号之间不留字、不加反引号）⇒ 〈判据物〉 判红「括注 ⬜，而进度清单为 ✅」（2026-11-10 实测）。
（七）**读数口径**：报「状态项 N / 矛盾 M」。 覆盖范围：只判跨册的状态字面一致，判不了这条拍板该不该存在、有没有被后来的决定取代（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：A3

第十七条【归约：没见过的东西先归到已有的格子里】
（一）**是什么**：把「无限的新场景」压成「有限的格子」的那一步。规范能跟着场景扩张，靠的不是写更多条，而是不认识的先归类。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「凡事都要新立环节」—— 能归进现有格子的一律不许新建；也不是「归约表填完就能开工」—— 表填完还要过该动作的必读与必跑。
（四）**判据**：【机判】〈判据物〉 每个环节必须有非空「出口」，缺一个即红；【人判】**归约演练**：拿一个从没做过的场景，只给这份规范，填下面的表；填不出来即为规范缺口。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：给某个环节删掉「出口」⇒ 必须判红（2026-11-18 实测：删掉 `B2` 的出口 ⇒ 点名「走到这一步怎么算做完没说」）；建一个没有出口的新环节 ⇒ 必须判红；没填归约表就开工 ⇒ 人判退回重填。
（七）**读数口径**：覆盖范围：判得了「每个环节都有出口」；判不了「这次归约归得对不对」，也判不了「某个新场景是否真的属于这一类」—— 那是人判。
（八）**归属环节**：A3

第十八条【进度清单只给正在开发的端建、每端一份活件】
（一）**是什么**：〈判据物〉（判据 A2）。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「每端都先建一份备着」—— 只给正在开发的端建，未开发端不建。
（四）**判据**：【机判】〈判据物〉（判据 A2）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：给不在允许端清单里的端建进度清单（`任务清单-Web端.md`）⇒ 端清单判据判红「不属于允许的端」（允许端清单见落点表；2026-11-10 实测）。
（七）**读数口径**：报「进度清单份数 / 对应端」。 覆盖范围：只判「进度清单的端白名单都是正在开发的端、每端恰一份」，判不了这个端是否真的在开发（端清单本身由需求书判） (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：A3

第十九条【进度清单永远只有一份活件，不做版本快照】
（一）**是什么**：进度清单是活件，任何时点只有一份，历史差异看 git，不拍快照。同上。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「每版留一份做对照」—— 历史看 git，快照只会漂移。
（四）**判据**：【机判】〈判据物〉（判据 A2）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：在 冻结区 留一份进度清单快照 ⇒ 必须判红（v1.3 起已删两份历史快照）。
（七）**读数口径**：报「活件份数（应 1）/ 快照份数（应 0）」。 覆盖范围：只判「同端没有第二份进度清单 / 没有版本快照文件」，判不了历史版本是否被藏到别的目录或别的文件名 (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：A3

第二十条【进度清单与详设同构、按端分册，只认同端详设活书】
（一）**是什么**：不许引别端详设、不许把 冻结区 冻结件当上游。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「可以引别端详设」；也不是「冻结件能当上游」。
（四）**判据**：【机判】〈判据物〉（判据 I）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：A 端进度清单引用 B 端详设的某一节作为落点 ⇒ 必须判红。
（七）**读数口径**：报「引别端 N 处 / 引冻结件 M 处（应 0）」。 覆盖范围：只判「章节结构与同端详设同构、引用的上游是活书」，判不了章节内容是否与详设实质一致（那由 〈判据物〉 报「碰了代码没碰文档」） (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：A3

第二十一条【进度清单是唯一进度源】
（一）**是什么**：日报 / 周报 / 进度表一律从它取，不许另开「里程碑清单」「按平台任务清单」当第二本。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「日报里另记一份进度」；也不许另开「里程碑清单」当第二本。
（四）**判据**：【机判】〈判据物〉 + 〈判据物〉；【人判】日报数字是否只从进度清单取。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：在进度活件（进度清单）里加一条需求书索引没有的编号（`需求条目`）⇒ 〈判据物〉 判红「进度清单多 1 条」（2026-11-10 实测）；另在别处另写一份进度（周报写「本版进度 80%」）⇒ 脚本判不了，接收方判错。
（七）**读数口径**：报「未闭条数（只从进度清单取）」。 覆盖范围：机判只判「进度清单与需求索引逐行对得上」，判不了别处（日报、聊天、提交信息）有没有另立一套状态口径 —— 那半只能人判 (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：A3

第二十二条【分册的需求书与概设不许按端拆】
（一）**是什么**：分册来自全量书、**只裁剪不增删**（`分册 ⊆ 全量`：分册出现的每个编号都必须能在全量书里找到）；一个产品各一本需求规格 + 一本概要设计，端差异不写进这两本；详设按端一本、从本族基准派生，只改落点与读数口径，不许另起契约正文。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「各端可以有自己的需求书」—— 需求与概设一个产品各一本，端差异只进详设；也不是「分册可以自己加条文」—— 只能裁，不能增。
（四）**判据**：【机判】〈判据物〉（分册 ⊆ 全量）、〈判据物〉（详设逐节表态）。

## 第四章 实现

第四十四条【第一刀是纵切，不是横切】
（一）**是什么**：从零起的功能，第一轮只许打通一条最小的端到端路径（存进去 → 拿出来 → 显示出来），哪怕只有一个按钮。
（二）**为什么**：先铺开做各层，最后没有一条路径能跑通，等于零；纵切能最早暴露集成问题。
（三）**不是什么**：不是「先做完数据库层再做后台再做页面」；也不是「每层都完成一点」—— 三层接不起来要等全部写完才暴露。
（四）**判据**：【人判】交接说明写清本轮走通的那条纵切 + 它的验证命令与原始输出，由接收方核对这份输出；只报「某层完成」= 判错。 **覆盖范围**：只看「本轮是否有一条端到端路径被真跑通」，看不到广度够不够（广度由需求条数与进度清单批次回答）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：【人判】交接写「数据库层已完成、后台待接入」而没有任何一条端到端命令输出 ⇒ 接收方必须退回。
（七）**读数口径**：报「本轮纵切：命令 + 输出行数」，不报各层完成度。
（八）**归属环节**：B1

第四十五条【开工先看工作区，提交只加本片文件】
（一）**是什么**：先 `git status --short`，判清归属再动手；提交只 `git add` 本片文件。
（二）**为什么**：一旦 `git add -A`，别人未提交的改动、本机记录、派生件、私物全被卷进提交，事后拆不干净；工作区脏着还会让出包判据误红。
（三）**不是什么**：不是「工作区干净才允许开工」；`git add -A` 一律禁止 —— 它会同时带上本机记录、派生件、私物、别人的未提交改动四类。
（四）**判据**：【机判】`git status --short` 逐字判归属 + 提交里出现 待办流水文件、构建产物目录、`dist/`、`.secrets/`、`_transfer_*`、`*.xcuserstate` 任一即红【脚本：〈判据物〉】；【人判】归属判断由本人在提交信息里写明（残余 / 另一助理 / 主人手改）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：改**对侧子树**（对侧端独有的目录）⇒ 路径归属判据判红「对侧子树」（2026-11-10 实测）；改共享面（文档目录 / 脚本目录）而新增行不注 `shared-surface：理由` ⇒ 判红「共享面未登记」。
（七）**读数口径**：报「本片文件数 / 未提交残余数」。 覆盖范围：机判只判「提交里出现了禁用路径」，判不了哪些算本片文件（归属由本人在提交信息里写明，属人判）（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：B2

第四十六条【提交信息中文写清三件】
（一）**是什么**：改了什么 + 派生出口 + 验证命令与结果，三件缺一即不合格。
（二）**为什么**：只写「修了点东西」的提交，一周后连作者自己都说不清改了什么、验证了什么；回滚时找不到边界。
（三）**不是什么**：不是「写了标题就算」；也不是「验证结果是『已跑』」—— 必须贴命令与输出行。
（四）**判据**：【人判】接收方读 `git log -1`，三件缺一即判错（提交信息是本条唯一被验对象）。 **覆盖范围**：只看 `git log -1` 的三件是否齐，不判三件内容是否正确（内容由对应判据判）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：【人判】提交信息只有「修 bug」四个字 ⇒ 判错退回。
（七）**读数口径**：报「三件：齐/缺哪件」。
（八）**归属环节**：B2

第四十七条【公开仓不留凭据 / 内网地址 / 个人内容】
（一）**是什么**：会随提交进入公开仓的文件里不许有密钥、内网地址、他人的个人内容。
（二）**为什么**：公开仓一旦推送就无法真正撤回；凭据泄露、内网地址暴露、他人个人内容都会被永久索引。
（三）**不是什么**：不是「删了提交历史就干净」（历史不重写，污染了就得换密钥）；也不是「私有仓可以放」—— 按每个仓自己的公开性判；**哪些仓是公开的属项目事实**，本册不写。
（四）**判据**：【机判】〈判据物〉（扫待推送文件的凭据/内网地址模式）；〈判据物〉 确认忽略规则命中。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把 `sk-` + 32 位随机串（示例值不写全，否则自己被判红） 写进**已跟踪**的 已跟踪的契约文档 ⇒ 〈判据物〉 必须判红（2026-11-10 实测）。内网地址在该脚本里只到**提示级**，不判红；是否脱敏由人判定夺。
（七）**读数口径**：报「扫描文件 N / 命中 0」。 覆盖范围：只判待推送文件里有没有凭据 / 内网地址模式，判不了没有固定模式的个人内容（那要读内容，人判）（2026-11-18 补：铁律 13 落地）
（八）**归属环节**：B4

第四十八条【代码写法：局部改动优先，一次只动与任务相关的最小范围】
（一）**是什么**：不顺手重排、不顺手改名、不顺手改格式；删除前确认范围（铁律 #7 的代码侧落点）；不许留「看起来能跑」的空实现（`TODO` 占位、假返回、`fatalError("not implemented")` 当交付）。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「代码不许重构」—— 重构要**单独提交**并写清动机；也不是「风格统一可以顺手改两百行」。
（四）**判据**：【机判】〈判据物〉 + 〈判据物〉（行为不许破）；〈判据物〉（改到别人负责的文件即红）。【人判】diff 里出现与任务无关的整段重排 ⇒ 退回。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：为了改一个按钮颜色重排整个文件 ⇒ 人判退回；提交里留 `fatalError("TODO")` 假实现 ⇒ 编译能过，但对应行为用例必须红。
（七）**读数口径**：报「本片改动文件数 / 其中与任务无关的文件数（应 0）/ 空实现残留数（应 0）」。 覆盖范围：只判「构建与测试不破」「改到别人负责的文件即红」，判不了 diff 是不是「与任务无关的整段重排」（那要读 diff，人判） (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：B1

第四十九条【代码评审与提交：一个提交只做一件事，且必须自证】
（一）**是什么**：提交信息写清「改了什么 / 派生出口 / 验证命令与结果」（铁律 #4）；改**契约或判据**的提交必须附自审清单 —— 改了哪条条文号、跑了哪条判据、反证做没做。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「提交越细越好」—— 一个提交里塞三个无关修复同样不合格；也不是「自审＝自己说没问题」。
（四）**判据**：【机判】〈判据物〉（动作对应判据必跑）；`git log -1 --format=%B` 必须能读到验证命令与结果。【人判】自审清单缺条文号或缺反证 ⇒ 退回。

（六）**负例**：提交信息只写「修 bug」、无任何验证输出 ⇒ 判错；改了一条判据却没跑它的负例 ⇒ 退回。

（一）**是什么**：三段式 `v主.次.补` 的含义必须写在该书的版本说明里 —— **主**：书的结构或契约面重写；**次**：契约面有增删（含破坏性变更，必须同时写迁移说明）；**补**：措辞、判据、数字修正。破坏性变更只升补位 = 判错。书版本与软件版本的对应关系按「冻结号 = 软件号」那条走。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「改了就加一」—— 加在哪一位必须与改动性质一致；也不是「破坏性变更靠口头通知」。
（四）**判据**：【人判】接收方核：本次改动的性质与所升的位是否匹配；破坏性变更有没有迁移说明。**机判兜底**：〈判据物〉 只兜三段式形状与「当前版本 = 版本表首行」，不判位与改动是否匹配。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：删掉一条契约条文却只升补位 ⇒ 判错；升中段但不写迁移说明 ⇒ 退回。
（七）**读数口径**：报「版本步进 N / 位与性质匹配 N / 破坏性有迁移说明 N」· **覆盖范围**：判不了「这次改动算不算破坏性」—— 那是判断，不是格式。
（八）**归属环节**：D1

第八十九条【解冻走「作废 + 重冻」：冻结件不许改，必须改就先作废】
（一）**是什么**：冻结件只能读。冻结之后发现必须改内容时，做法是：① 记录作废原因与影响面；② 把当前冻结标记为「已作废（被 vX 取代）」；③ 从活书重新冻结一次，产出**新的**冻结件与新的软件号。直接改冻结件的任何一个字，都按「伪造冻结件」处理。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「小改一下没事」—— 冻结件的价值就在于「事后可对账」，改一个字就废了；也不是「作废了旧的就不用留」，作废件必须留档。
（四）**判据**：【人判】接收方核：作废原因是否记、新冻结件是否为新文件、旧件是否仍在。**机判兜底**：〈判据物〉 与 〈判据物〉 兜冻结件与活书/软件号的一致。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：直接在冻结件里改一句 ⇒ 判错；覆盖写同一个冻结文件名 ⇒ 判「无留档」。
（七）**读数口径**：报「解冻 N 次 / 有作废记录 N / 旧件留存 N / 覆盖写 N（应 0）」· **覆盖范围**：判不了「这次改动是否值得解冻」。
（八）**归属环节**：D2

第九十条【三级投放：自己用 → 小范围 → 全量，每级都要能退回】
（一）**是什么**：任何新包不许一步全量投放。第一级只给自己用（至少一个完整工作日，覆盖一次真实任务）；第二级给指定的一两个人；第三级才全量。每一级必须写明「退回上一版」的动作（换回哪个包、数据是否需要回退），并确认退回动作真的能走通一次。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「自己是第一个用户就算灰度」—— 要跑过真实任务；也不是「退回就是重装」—— 数据格式变了重装也回不去。
（四）**判据**：【人判】接收方核：三级是否逐级走过、每级的退回动作是否写明并走过一次。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：新包直接全量替换 ⇒ 判错；写明「可回退」但从没走过 ⇒ 判「未验证」。
（七）**读数口径**：报「投放 N 次 / 分级走过 N / 退回动作验证过 N」· **覆盖范围**：判不了小范围用户是否真用了新功能。
（八）**归属环节**：D5

第九十一条【发布要有回执：谁、何时、能否正常启动】
（一）**是什么**：发布之后必须收到接收方的回执 —— 谁装的、什么时间、是否正常启动（能打开主界面并完成一次最小动作）。没有回执的发布只能记「已投递」，不许记「已发布」；回执缺失超过一轮，必须主动追一次。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「发了文件就算发布」—— 投递与可用是两件事；也不是「对方没说不就等于行」。
（四）**判据**：【人判】接收方核：发布记录里是否有回执三要素；没有的是否记成「已投递」。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把包放进共享目录就写「已发布」⇒ 判错；回执只写「收到了」而不说能否启动 ⇒ 判「不完整」。
（七）**读数口径**：报「发布 N / 有回执 N / 记为已投递 N / 回执缺三要素 N」· **覆盖范围**：判不了对方是否长期使用，只判「启动可用」这一件事。
（八）**归属环节**：D4

第九十二条【分发必须附第三方许可与声明，有义务的必须履行】
（一）**是什么**：包交给别人之前，必须能找到一份「本包内含哪些第三方件 / 各是什么许可 / 声明放在哪」；带署名或开源义务的许可（如 MIT 署名、Apache NOTICE、MPL 修改声明）必须履行，不许只留一行登记了事。声明位置写在交付说明里（包内文件或关于页二者其一）。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「登记表里记了许可就算合规」—— 登记表是给自己看的，声明是给用户看的；也不是「自己用就不用附」以外的自由，一旦分发就要附。
（四）**判据**：【人判】接收方核：包内 / 关于页能否找到第三方许可声明，登记表里的许可义务是否逐条履行。**机判兜底**：〈判据物〉 只兜「登记表里有许可行」，不判声明是否随包。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把含 MIT 第三方件的包直接发给别人而不附声明 ⇒ 判错；登记表写「MIT」但关于页没有任何第三方页 ⇒ 判「未履行」。
（七）**读数口径**：报「第三方件 N / 有许可声明 N / 有义务已履行 N / 声明位置写明 N」· **覆盖范围**：判不了许可义务的法律判断（例如「这样算不算衍生作品」），只能判声明在不在、义务有没有落到实物。
（八）**归属环节**：D3

第九十三条【备份必须演练过恢复：没恢复过的备份等于没有】
（一）**是什么**：任何声称「有备份」的数据面，必须至少演练过一次**完整恢复**，并记录三件：**恢复耗时、丢失范围（最多丢多少）、恢复后自检怎么证明是好的**。备份只写「已配置自动备份」不算——那只能证明文件存在，不能证明能回来。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「备份文件在就算安全」；也不是「演练一次永久有效」—— 数据面变了（换库、换机器、改格式）要重新演练。
（四）**判据**：【人判】接收方核：恢复演练的记录三件是否齐、数据面变化后是否重演。**覆盖范围**：本环节无机判脚本 —— 判不了「备份件里数据是否完整」，只能判「演练有没有做过、记录是否可核」。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：说「有每日备份」但从未恢复过 ⇒ 判错；演练记录只写「恢复成功」而不写耗时与丢失范围 ⇒ 判「不完整」。
（七）**读数口径**：报「数据面 N / 演练过 N / 三件齐 N / 数据面变化后未重演 N（应 0）」。
（八）**归属环节**：D5

（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：基线有红却直接开工做功能 ⇒ 判错。
（七）**读数口径**：报「四步：①②③④ 各绿/红」。

第九十八条【平台差异必须两侧登记并逐条对账】

（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：只在一侧加 `P-` 行 ⇒ 必须红；两侧条目内容不一致 ⇒ 必须红。

（八）**归属环节**：E1

第九十九条【入口页是索引不是副本，必须与规范同号】
（一）**是什么**：入口页（每个项目仓根那份给接手者看的索引文件）只许放**索引 + 触发条件 + 判据命令**；其中的铁律**条数与编号**必须与本册基本原则条逐条一致，不一致即红；副本一旦漂移就是两套规矩。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「多写一份更方便」—— 两份就等于两份会各自漂移。
（四）**判据**：【机判】〈判据物〉。 **覆盖范围**：只判条数与编号，判不了索引里写的判据命令是否还能跑（那由 〈判据物〉 自己判）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：在 入口页 的铁律目录里删一条 ⇒ 必须红；本册加一条基本原则而入口页没跟 ⇒ 必须红。
（七）**读数口径**：报「铁律 N / 入口页 N / 不一致 N（应 0）」
（八）**归属环节**：E3

第一百条【非显然的做法必须在 24 小时内沉淀成可复用件】
（一）**是什么**：一次做完、但下次还会遇到的做法（判据怎么设计、某类门禁怎么写、某个坑怎么绕），必须落成 **skill**（触发条件 + 步骤 + 判据 + 反例）或脚本 + 说明；没沉淀的，这件事算没做完。沉淀件要能被另一个助理在**新会话**里直接使用 —— 有触发条件、有步骤、有验证方式，不靠口头补充。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「记在对话里就行」—— 会话会丢；也不是「写成一篇长文」，没有触发条件的长文等于没有。
（四）**判据**：【人判】接收方核：本批有没有产生「下次还会遇到」的做法；有的话沉淀件在哪、能否按它独立复现。**覆盖范围**：本环节无机判脚本 —— 判不了「这个做法值不值得沉淀」，只能判「有没有产出可用的沉淀件」。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：同一个坑第二次出现仍靠现场回忆解决 ⇒ 判错（应已沉淀）；沉淀件只写结论不写触发条件 ⇒ 判「不可用」。
（七）**读数口径**：报「非显然做法 N / 已沉淀 N / 新会话可用 N / 重复踩坑 N（应 0）」。
（八）**归属环节**：E3

第一百零一条【一处在途改动一条分支；合并前 rebase 到最新并重跑门禁；冲突不许猜着解】
（一）**是什么**：每个在途改动占用一条分支（或一个明确的独占文件集），不许两个人同时改同一条分支；合并前必须 rebase 到最新基线并**重跑门禁**；合并冲突里涉及**别人的行**时必须问原主，不许「看起来能过就这样解」。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「本地能跑就能合」—— 冲突解决后的代码没人验过；也不是「谁的改动多听谁的」。
（四）**判据**：【人判】接收方核：分支是否独占、合并前是否 rebase 过且门禁重跑、冲突中别人的行是否问过。**覆盖范围**：判不了分支命名与团队习惯是否一致，只判这三件在不在。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把别人分支上的改动直接覆盖 ⇒ 判错；冲突解完不跑门禁就合并 ⇒ 退回；冲突行是自己改别人的代码且没问 ⇒ 判错。
（七）**读数口径**：报「在途分支 N / 独占 N / 合并前重跑门禁 N / 涉他冲突问过 N」。
（八）**归属环节**：E2

第一百零二条【外部协作者动工前先声明：动哪些文件、哪条分支、预期产出】
（一）**是什么**：另一个助理、另一个 AI、或任何自动化工具在**同一个仓**动手之前，必须先写一句声明（动哪些路径 / 哪条分支 / 预期产出 / 预计时长），并在产出后回执一句「实际改了哪些」。没有声明的，按双写风险处理 —— 先停，先问。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「反正每次提交会看到」—— 等看到时冲突已经发生了；也不是「同一个 AI 就不用声明」，换会话就是换人。
（四）**判据**：【人判】接收方核：动手前有没有声明、产出后有没有回执；`git status --short` 里是否出现了声明之外的文件。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：直接开干且改了三个文件，事后才说「顺手改的」⇒ 判错；两个助理同时改同一节 ⇒ 判错（应先声明再串行）。
（七）**读数口径**：报「外部协作者 N / 有前置声明 N / 有产出回执 N / 声明外改动 N（应 0）」· **覆盖范围**：判不了声明之后是否按声明执行，只能靠回执与 `git status` 对照。
（八）**归属环节**：E1


## 第八章 运行

第一百零三条【运行时与审计：每个自动动作留下「谁、何时、依据哪条」】
（一）**是什么**：一切自动或半自动动作必须留下可检索记录（触发者、时间、依据条文或判据号、结果）；审计记录**只追加不改写**；日志里不写凭据与用户原文。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「打个 print 就算审计」—— 无结构、不可检索、可被改写的日志不算审计。
（四）**判据**：【人判】接收方抽一条动作，要求当场在记录里找到这四项。**覆盖范围**：本环节无机判脚本。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：动作执行完只留一句「已处理」⇒ 判错；日志被覆盖写导致历史丢失 ⇒ 退回。
（七）**读数口径**：报「自动动作 N / 四项齐全 N / 可改写的记录 N（应 0）」。
（八）**归属环节**：F1

第一百零四条【可观测与告警：先能看见，再谈告警】
（一）**是什么**：运行态至少能回答三件事 —— 是否在跑、最近一次成功/失败在何时、失败原因是什么；告警要有阈值与去向，**没有去向的告警等于没有告警**。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「有日志就等于可观测」；也不是「告警越多越好」—— 无去处的告警会把人练成不看。
（四）**判据**：【人判】接收方现场问这三件事，看能否当场答出。**覆盖范围**：本环节无机判脚本。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：进程挂了三天没人知道 ⇒ 判错；告警发到一个没人看的分组 ⇒ 视为无告警。
（七）**读数口径**：报「三件事可答 N/3 / 有阈值与去向的告警 N」。
（八）**归属环节**：F2

第一百零五条【故障处置与复盘：先止血、再定性、后改规矩，三件事不许混在一轮做】
（一）**是什么**：出事时第一步是**止血**（回滚 / 关闸 / 只读），第二步定性（改了什么、影响面、为何判据没拦住），第三步才动规矩（补条文或补判据）。**同一条故障第二次出现，不许再靠新增脚本解决** —— 说明上次定性错了。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「写完复盘就结束」—— 复盘要落到**一条**具体改动（条文 / 判据 / 流程），不落就是故事。
（四）**判据**：【人判】复盘必须回答「为什么原有判据没拦住」；答不出即复盘无效。**覆盖范围**：本环节无机判脚本。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：同类问题第二次出现、处置仍是「再加一个脚本」⇒ 判错；复盘只写时间线不写判据缺口 ⇒ 退回。
（七）**读数口径**：报「故障 N / 有止血动作 N / 回答判据缺口 N / 同类二次出现 N（应 0）」。
（八）**归属环节**：F3

第一百零六条【用户支持与文案：文案是交付物，随功能同批验收，不留「敬请期待」】
（一）**是什么**：界面与提示文案随功能同批交付与验收；不许出现未实现功能的预告、占位文案、机器翻译腔；文案语言只许在册面上已声明的语言里，不许混入第三种。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「文案以后再补」—— 空文案与错文案同属缺陷；也不是「原文照搬英文就是国际化」。
（四）**判据**：【人判】接收方按语言清单逐项看：有无第三种语言、有无未实现预告、有无占位符残留。**覆盖范围**：本环节无机判脚本（本仓的语言清单口径见项目册）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：菜单里出现三种语言 ⇒ 判错；「即将上线」写在已发布版本里 ⇒ 退回。
（七）**读数口径**：报「新增文案 N / 与功能同批 N / 第三种语言 0 / 占位残留 0」。
（八）**归属环节**：F4

第一百零七条【审计记录必须有留存期与检索入口】
（一）**是什么**：审计记录写明保存多久、按什么维度能检索（动作 / 设备 / 条目号 / 时间窗）；过期删除本身要有记录，不许悄悄清空。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「日志文件在那就算有」—— 没人知道存多久、按什么查，等于查不到。
（四）**判据**：【人判】接收方随机给一个条目号，要求当场从审计里查出该条目最近三次动作及其时间。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：问「这条记录存到什么时候」答不出 ⇒ 判错；审计目录被清空且无删除记录 ⇒ 退回。
（七）**读数口径**：报「条目能查到 N / 留存期已写明 N / 删除有记录 N」。 覆盖范围：本仓无运行期审计留存判据物；只判「能不能按条目号查到」，判不了留存期是否合规、也判不了删除记录是否完整。
（八）**归属环节**：F1

第一百零八条【审计字段必须结构化落盘，不是拼一句话】
（一）**是什么**：触发者、时间、依据（条文号或判据号）、结果四件各自成字段；同一动作若被闸门跳过或强制，跳过与强制必须成对出现，不许只留一半。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「拼成一行中文就够了」—— 拼字符串无法按字段检索、也无法证明跳过与强制成对。
（四）**判据**：【机判】〈判据物〉（闸门跳过记成 notice、强制与跳过成对、通知双出口都落记录、静默决策不留记录，四条用例必须绿）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：只记「已跳过」而不记被谁强制 ⇒ `testGateForceIsPairedWithTheSkip` 判红。
（七）**读数口径**：报「审计面 N / 有结构化字段 N / 跳过强制成对 N」。 覆盖范围：只判 Agent 决策与通知这一面的审计字段；其它模块（笔记、连接、插件）的审计无判据。
（八）**归属环节**：F1

第一百零九条【敏感面必须进审计：出站请求、写外部状态、跨仓推送】
（一）**是什么**：这三类动作即使成功也要留记录；失败更要留，且要能看出「试过几次、最后一次错在哪」。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「只在失败时记」—— 成功但无人知的动作正是出事时最难查的那类。
（四）**判据**：【人判】接收方抽一次出站请求 / 一次外部写 / 一次推送，要求各自在审计里找到记录与重试次数。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：能证明某个写操作发生过，但审计里查不到 ⇒ 判错。
（七）**读数口径**：报「敏感面三类 / 有审计 N / 带重试次数 N」。 覆盖范围：本仓无运行期出站审计判据物（出口清单判据判的是**代码里的清单**，不判运行时有没有留记录）。
（八）**归属环节**：F1

第一百一十条【关键指标只许一个读数来源】
（一）**是什么**：每个指标（延迟、失败率、队列长度、花费）写清由谁算、在哪读；同一指标不许两处各算一套，两套必然吵架。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「多算几处取平均」—— 多来源不是冗余，是两套口径。
（四）**判据**：【人判】接收方指着任一指标问「这个数谁算的」，必须能答出唯一来源；答出两个即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：界面显示 12%、日志算出 30% ⇒ 判错。
（七）**读数口径**：报「指标 N / 有唯一来源 N / 两套口径 N（应 0）」。 覆盖范围：本仓无运行期指标采集判据物；只判「有没有唯一来源」，判不了这个来源算得对不对。
（八）**归属环节**：F2

第一百一十一条【告警三件套：阈值、责任人、静音与升级规则】
（一）**是什么**：每条告警写明阈值是多少、发给谁、什么条件下静音、多久没响应就升级；三件缺一即视为没有告警。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「告警越多越安全」—— 没有责任人和升级规则的告警，只会把人训练成不看。
（四）**判据**：【人判】接收方逐条问某条告警：阈值多少、谁收、静音条件、几小时升级；四问答不全即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：告警配了阈值但没写责任人 ⇒ 判错；静音没有期限 ⇒ 退回。
（七）**读数口径**：报「告警 N / 四问齐 N / 无责任人 N（应 0）」。 覆盖范围：本仓无运行期告警配置物（无告警服务、无通知渠道配置），只能人判；判不了告警是否真的送达。
（八）**归属环节**：F2

第一百一十二条【性能读数必须落读数表，阈值变化要留痕】
（一）**是什么**：每次测量的读数、机器、场景写进读数表；阈值只许按记录调，不许凭感觉改。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「测完贴聊天里就算记录」—— 读数表之外的口头读数下次没法比对。
（四）**判据**：【机判】〈判据物〉（读数条目带阈值与新鲜度，超期即红）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：把阈值从 800ms 改成 1200ms 却不写理由 ⇒ 读数表无留痕，判红。
（七）**读数口径**：报「读数条目 N / 带阈值 N / 超期 N（应 0）」。 覆盖范围：只判读数表形状与新鲜度；不判阈值定得合不合理（那是 F3 复盘时要回答的）。
（八）**归属环节**：F2

第一百一十三条【事故先分级：影响面决定时限，不许所有事故同优先级】
（一）**是什么**：按「影响多少使用者 / 是否丢数据 / 能否绕开」分三级，每级写明响应时限与谁拍板；分级动作在止血之前完成，一句话即可。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「事后再补分级」—— 分级决定先救谁，事后再定等于没定。
（四）**判据**：【人判】接收方看事故记录第一行：有没有级别、有没有影响面、有没有响应时限；三样缺一即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：两个事故一个丢数据一个只影响自己，处置顺序却按发生时间 ⇒ 判错。
（七）**读数口径**：报「事故 N / 有级别与时限 N / 分级在止血之前 N」。 覆盖范围：本仓无事故记录判据物；只判记录里有没有分级三样，判不了时限是否被遵守。
（八）**归属环节**：F3

第一百一十四条【复盘五项齐全：时间线、影响面、根因、为何判据没拦、改哪一条】
（一）**是什么**：五项缺一即复盘无效；「改哪一条」必须指到具体条文号或判据文件名，不许写「加强测试」。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「写清时间线就是复盘」—— 时间线只是第一项，缺后四项等于只讲发生了什么。
（四）**判据**：【人判】接收方按五项逐条核；第五项指不到具体条文号或判据文件即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：复盘写「今后加强测试」⇒ 第五项未指名，退回。
（七）**读数口径**：报「复盘 N / 五项齐 N / 第五项指名 N」。 覆盖范围：本仓无复盘模板判据物；只判五项在不在、第五项是否指名，判不了根因判断对不对。
（八）**归属环节**：F3

第一百一十五条【止血动作必须事前演练过，不许现场发明】
（一）**是什么**：每条回滚 / 关闸 / 只读路径，在出事之前至少走通一次并记下耗时；现场第一次执行的止损不算止血，算第二次事故。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「文档里写了回滚步骤就算演练过」—— 没跑过的步骤，真出事时总有一句命令是错的。
（四）**判据**：【人判】接收方要求指出该路径最近一次演练的时间与耗时；只有文档没有演练记录即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：回滚脚本第一次被执行是在事故现场 ⇒ 判错。
（七）**读数口径**：报「止血路径 N / 演练过 N / 有耗时记录 N」。 覆盖范围：本仓无演练记录判据物；只判演练是否发生过，判不了演练时数据量是否与真实一致。
（八）**归属环节**：F3

第一百一十六条【用户可见文案不许硬编码，只许比基线更少】
（一）**是什么**：核心层 里用户能看到的文字必须走语言资源；硬编码的数量记基线，只许降不许升。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「先写死以后再抽」—— 基线只降不升，写死一条就欠一条。
（四）**判据**：【机判】〈判据物〉（含汉字字面量的数量不得高于基线）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：新加一句中文提示没走资源 ⇒ 棘轮数 +1，判红。
（七）**读数口径**：报「硬编码 N / 基线 M（N ≤ M）」。 覆盖范围：只判 核心层 里含汉字的字面量；界面层/ 层、界面快照、以及英文硬编码都不在其内（后者由〈判据物〉另判）。
（八）**归属环节**：F4

第一百一十七条【报错文案必须说下一步：是什么 + 能做什么】
（一）**是什么**：每条面向用户的失败文案写清两件事 —— 发生了什么、用户可以做什么；只说「出错了」「操作失败」不算文案。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「把技术异常原样抛给用户」—— 栈信息既不是「是什么」，也不是「能做什么」。
（四）**判据**：【人判】接收方逐条读新增失败文案：有没有可执行下一步；只有结论没有动作即判错。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：弹窗只写「操作失败」⇒ 判错。
（七）**读数口径**：报「新增失败文案 N / 带可执行下一步 N」。 覆盖范围：本仓有「失败文案覆盖面」判据但只判**命令行**输出，界面弹窗与 Agent 回话的文案无判据。
（八）**归属环节**：F4

第一百一十八条【语言清单只有已登记的那几门，菜单层也要判】
（一）**是什么**：界面只许出现册面上声明的语言（**具体哪几门归项目册**，本册不写死）；菜单标题即使由系统本地化，也必须落在同一清单内。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「正文干净就行」—— 菜单标题由系统菜单层另行本地化，最容易漏出第三种语言。
（四）**判据**：【机判】〈判据物〉（需真应用运行，打包后跑：菜单标题只许已登记语言）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：菜单出现第三种语言 ⇒ `MenuLanguageGateTests` 判红。
（七）**读数口径**：报「菜单语言落在清单内 N/N / 清单外 0」。 覆盖范围：只判菜单标题这一层；正文与提示文案的语言正确性靠 R-037 棘轮与人判，不在此判据。
（八）**归属环节**：F4


## 第九章 附则

> **术语（本册的固定含义，不是某个仓的文件名）**：
> **入口页** = 每个项目仓根那份给接手者看的索引文件（只放索引 + 触发条件 + 判据命令，不放规则正文）；
> **文档根** = 活书所在的那层目录（只放活件，过程件进归档区）；
> **归档区** = 过程件与历史记录的存放处；**冻结区** = 版本冻结快照的存放处；
> **派生件区** = 从真源生成的矩阵 / 清单 / 索引的存放处（不进文档根）；
> **单测收尾行** = 跑完单测后那句统计（项数 / 跳过 / 失败）；**判据物** = 落实本册某条判据的那个可执行检查（叫什么名字、放在哪、怎么跑，全属项目事实，本册不写也不指向 —— 项目册反向登记「本条落点在哪」）。
> **另外两个代词**：**本册** = 你手里这份规范；**本仓** = 采用本规范的仓库（换项目时含义跟着换，所以「本仓有没有某样东西」这类话换仓必须重判）。
>
> 这些名字**每个项目各自不同**：本册只写术语，具体叫什么、放在哪，写进项目册的落点表。

> 本章管版本、废止、术语与过渡；过渡条款是真条文，版本与术语是元数据（不判七问）。

第一百一十九条【存量条文允许暂缺字段】
（一）**是什么**：数量记 〈判据物〉，**只许降不许升**；新条文一律不许裸奔。
（二）**为什么**：出处未记（待补：能从该条的提交信息 / 事故记录查到再填，不编）
（三）**不是什么**：不是「新条文也可以先裸奔」—— 只许降不许升。
（四）**判据**：【机判】〈判据物〉（棘轮：缺字段数不得升、完整数不得降；**单向引用**：本册条文正文出现项目规范的书名或节号即红 —— 只许项目规范引用本册，不许本册指回去）。
（五）**能力前提**：出处未记（待补：写清守这条要什么工具 / 权限 / 环境）
（六）**负例**：新写一条只有「判据：评审」的条文 ⇒ 缺字段数 +1，必须判红。
（七）**读数口径**：报「条文 N / 完整 M / 缺字段 K」。 覆盖范围：只判棘轮方向（缺字段不许升、完整不许降），判不了缺的字段什么时候补上 (2026-11-18 补：铁律 13 落地)
（八）**归属环节**：全局

第一百二十条【版本与生效】
（一）**是什么**：版本写在书首版本表里（最新在最前）；条文的生效版本记在该条的版本行。版本号只增不减，跳段必须写明原因。
（二）**为什么**：此前版本头与版本表并存，两处都能改，于是两处都不可信。
（三）**不是什么**：不是每改一字就升大版本：口径变更升小版本，措辞与错字不动版本。
（四）**判据**：【机判】版本表首条必须是最新版本；同一版本号不许出现两次（判据物：check-doc-versions）。
（五）**能力前提**：版本表与书首版本头必须同源，不能各写一份。
（六）**负例**：版本表首条写 v1.0.49 而最新是 v1.0.51 ⇒ 必须判红。
（七）**读数口径**：报「当前版本 / 版本表条数」。覆盖范围：判不了版本号与实际改动量是否相称。
（八）**归属环节**：全局

第一百二十一条【废止与修订】
（一）**是什么**：条文只增不删。要取消一条，标「已废止（被第N条替代）」并保留原文；条号永不复用。修订 = 新增一条 + 旧条标废止。
（二）**为什么**：就地改写旧条会让历史决策无从追溯，残留就是这么来的：改了半句、留了半句，两代口径并存，谁也说不清哪句有效。
（三）**不是什么**：不是「旧条一律留着占地方」：废止条只进附则废止表，正文不再列。
（四）**判据**：【机判】废止条必须指向存在的替代条；活条文不许引用已废止条；条号不许复用。
（五）**能力前提**：废止需要有稳定的条号 —— 所以条号制度必须先立（见第三条）。
（六）**负例**：把第 40 条整段删掉、把第 41 条改成第 40 条 ⇒ 必须判红。
（七）**读数口径**：报「废止条数 / 活条数」。覆盖范围：判不了「废止是否该发生」。
（八）**归属环节**：全局

第一百二十二条【术语】
（一）**是什么**：本册术语只定义通用册内部用到的词：条文、款、判据、负例、读数口径、覆盖范围、归属环节、阶段、环节、形态、事实、派生件区。项目专有名词一律不进本册。
（二）**为什么**：同一个词在两册里各有一个意思，是「同一件事两种写法」的根源。
（三）**不是什么**：不是词典：只收本册正文真的用了、且容易读错的词。
（四）**判据**：【人判】正文用了未定义的词、或定义与用法不一致。
（五）**能力前提**：术语与本册正文同批维护，否则定义会落后于用法。
（六）**负例**：正文用「落点」而术语表里没有，只出现在项目册 ⇒ 不合格。
（七）**读数口径**：报「术语条数 / 正文自造词疑似数」。覆盖范围：自造词不可枚举，只报人判。
（八）**归属环节**：全局
