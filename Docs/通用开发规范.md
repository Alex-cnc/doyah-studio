# 通用开发规范

## 1 铁律（违反就是返工）
1. **第一刀是纵切，不是横切**：从零起的功能，第一轮只许打通一条最小的端到端路径（存进去 → 拿出来 → 显示出来），哪怕只有一个按钮。
- **不是什么**：不是「先做完数据库层再做后台再做页面」；也不是「每层都完成一点」—— 三层接不起来要等全部写完才暴露。
- **判据**：【人判】交接说明写清本轮走通的那条纵切 + 它的验证命令与原始输出，由接收方核对这份输出；只报「某层完成」= 判错。
- **负例**：【人判】交接写「数据库层已完成、后台待接入」而没有任何一条端到端命令输出 ⇒ 接收方必须退回。
- **读数口径**：报「本轮纵切：命令 + 输出行数」，不报各层完成度。
- **归属**：本节；判据形态（人判）改机判需另立脚本。

2. **状态只在验证之后改**：代码写完不算完成，跑过脚本/单测拿到 `exit 0` 才算，宣称「已完成」必须附那行输出。判据：`./Scripts/verify-all.sh` 或 `./Scripts/verify-core.sh` 的收尾行。
3. **开工先看工作区，提交只加本片文件**：先 `git status --short`，判清归属再动手；提交只 `git add` 本片文件。
- **不是什么**：不是「工作区干净才允许开工」；`git add -A` 一律禁止 —— 它会同时带上本机台账、派生件、私物、别人的未提交改动四类。
- **判据**：【机判】`git status --short` 逐字判归属 + 提交里出现 `.agent/`、`.build/`、`dist/`、`.secrets/`、`_transfer_*`、`*.xcuserstate` 任一即红【脚本：`Scripts/check-path-ownership.py`】；【人判】归属判断由本人在提交信息里写明（残余 / 另一助理 / 主人手改）。
- **负例**：`git add -A` 后提交带上 `.build/derived/x.md` ⇒ `check-path-ownership` 必须判红。
- **读数口径**：报「本片文件数 / 未提交残余数」。
- **归属**：本节；白名单另见 `.gitignore` 与《项目管理规范》。

4. **提交信息中文写清三件**：改了什么 + 派生出口 + 验证命令与结果，三件缺一即不合格。
- **不是什么**：不是「写了标题就算」；也不是「验证结果是『已跑』」—— 必须贴命令与输出行。
- **判据**：【人判】接收方读 `git log -1`，三件缺一即判错（提交信息是本条唯一被验对象）。
- **负例**：【人判】提交信息只有「修 bug」四个字 ⇒ 判错退回。
- **读数口径**：报「三件：齐/缺哪件」。
- **归属**：本节。

5. **不弹窗要授权**：需要授权或拍板的进队列，能做的一律先做，不许因等确认停工。
- **不是什么**：不是「等主人回话才继续」；也不是「把要授权的事自己做了」—— 前者停工，后者越权。
- **判据**：【机判】`python3 Scripts/check-queue-needs-user.py`（待拍板项必须在队列里且状态词合法）；【人判】队列条目是否真属「需授权」由本人判断。
- **负例**：需要主人授权的动作没进队列而直接在提交里做了 ⇒ `check-queue-needs-user` 必须判红。
- **读数口径**：报「队列新增 N 条 / 已自行完成 M 条」。
- **归属**：本节 + 《项目管理规范》§4 队列。

6. **不擅自改外部状态**：不在别人的库上建库、不改 `pg_hba.conf`、不为跑测试在本机装服务 —— 只给命令，不执行。
- **不是什么**：不是「只读操作也要问」；也不是「本地环境随便装」—— 装服务同样算改外部状态。
- **判据**：【人判】执行记录里有没有对他人库/系统配置的写操作，由本人自查 + 交接说明注明；口径真值源 = 《产品需求规格说明书》§0.9。
- **负例**：【人判】为跑测试在自己机器上 `brew install mysql@8.0` 并写进交接当「已就绪」⇒ 判错。
- **读数口径**：报「给出命令 N 条 / 已执行 0 条」。
- **归属**：本节。

7. **删除前确认范围**：「清理掉」先确认是部分文件还是整个目录，范围写进命令再执行。
- **不是什么**：不是「先删再问」；也不是「备份了就能删」—— 备份不是授权。
- **判据**：【人判】删除命令必须带明确路径通配并在此前贴出 `ls` 结果，由本人核对。
- **负例**：【人判】收到「清理掉旧包」直接 `rm -rf dist/` ⇒ 判错（只该删过期的单个文件）。
- **读数口径**：报「待删 N 个 / 实删 N 个 / 保留 N 个」。
- **归属**：本节。

8. **Studio 仓是 PUBLIC**：凭据、内网地址、个人内容不进会被推送的文件。
- **不是什么**：不是「删了提交历史就干净」（历史不重写）；也不是「私有仓可以放」—— 本仓 PUBLIC，别的仓按各自口径。
- **判据**：【机判】`python3 Scripts/check-no-user-data.py`（扫待推送文件的凭据/内网地址模式）；`git check-ignore -v <文件>` 确认忽略规则命中。
- **负例**：把 `192.168.5.26` 写进 `Docs/` 受检文件 ⇒ `check-no-user-data` 必须判红。
- **读数口径**：报「扫描文件 N / 命中 0」。
- **归属**：本节（铁律 #8）。

9. **文档改动必过门禁**（清单见 §4）。判据：`./Scripts/verify-all.sh`。
10. **不擅自扩大文档体系**：只认 §2 的三书一单，不许新建第六本书 / 索引 / 台账 / 清单，门禁要的中间产物落 `.build/`。判据：`Scripts/check-doc-invariants.py`、`Scripts/check-end-sheets.py`。
11. **报数报「还剩多少」**：报数报「还剩多少 / 缺在哪」，不报「扫了多少」。
- **不是什么**：不是「已登记 = 已修完」；也不是「覆盖率 96% 可以当结论」。
- **判据**：【机判】`python3 Scripts/check-doc-numbers.py`（写死数字必须与实测一致）；【人判】结论句里有没有「还剩/缺在哪」，由接收方读。
- **负例**：报告写「已完成 391 条中的 379 条」而不说剩 6 条未闭 ⇒ `check-doc-numbers` 判不出，接收方判错（故本条保留人判）。
- **读数口径**：报「总数 / 已闭 / **未闭**」三值，未闭必须点名。
- **归属**：本节（铁律 #11）。

12. **一条拍板只落一处结论**：同一状态散在多本册子只改一处必留矛盾 ⇒ 状态唯一源 = 一单。判据：`Scripts/check-status-consistency.py`。

13. **判据必须声明覆盖范围**：任何「报缺失/报异常」的判据，先说清扫了哪些目标源、哪些没扫。
- **不是什么**：不是「加了 `--json` 就算声明」；覆盖不全时**只许报「未知」，不许报「发现」**。
- **判据**：【机判】脚本 `--json` 输出必须含 `sources` / `uncovered` 两段，`uncovered` 非空而结论报「发现」即红；【人判】交接说明写没写这两段。
- **负例**：悬空引用检测扫了 48 个源报「23 处异常」，实际漏扫分仓 ⇒ 必须报「未知」而不是「23 处」。
- **读数口径**：报「覆盖 N 源 / 未覆盖 M 源 / 结论：发现｜未知」。
- **归属**：本节（铁律 #13）。

14. **每条判据配一条「必须判红」的负例**：正例只证明能通过，负例才证明真会拦；新写或改写的门禁必须同时交一个故意违规的样本。
- **不是什么**：不是「有单测就算」—— 必须有一条**故意违规**的用例，且它必须判红。
- **判据**：【机判】`python3 Scripts/check-self-test-counts.py`（各门禁自测计数与登记一致）+ `python3 Scripts/test-verify-all-gate.py`；新增门禁无负例用例即红。
- **负例**：新门禁只写了「合规输入 ⇒ 绿」，被 `check-self-test-counts` 发现负例数 0 ⇒ 必须判红。
- **读数口径**：报「负例数 / 断言数」两个数，不报「自检通过」。
- **归属**：本节（铁律 #14）。

15. **独立验收层：判「对」的依据不许由被判方提供**：判「对」只认三样：人类主人原话 / 契约条文（三书判据行）/ 外部权威系统（编译器、测试框架、真机）。
- **不是什么**：不是「自己跑通了就算对」；生成 spec/代码/测试的同一个模型不能同时判定它对。
- **判据**：【人判】交接说明里每条「已完成」必须指名依据属于哪一类（口径编号 / 主人原话 / 命令输出）；只写「我验过了」= 判错。
- **负例**：【人判】交接写「已按我最新的理解实现并自测通过」而不指名契约条文号 ⇒ 判错。
- **读数口径**：报「已完成条目数 / 其中指明依据的条数」。
- **归属**：本节（铁律 #15）。

## 2 三书一单（唯一文档体系，产品无关）
| 位置 | 书 | 写什么 |
|---|---|---|
| ② | 《X产品需求规格说明书》 | 需求条目（编号 / 需求 / 判据 / 优先级 / 状态 / 来源）、验收判据 |
| ③ | 《X产品概要设计说明书》 | 组件表、契约 `P-xx`、ADR、跨端约束；不写实现细节 |
| ④ | 《X产品详细设计说明书-<端>》 | 七件套契约、追溯矩阵、用例定义、实现约束 |
| 单 | 《X产品开发计划任务清单-<端>》 | 该端需求状态台账 + 版本计划 + 批次；日报从这里取数 |

- **PC 一体化：Agent / Studio / Notes / Retro 四个功能写在**同一份**全量三书里**（人类主人 2026-11-01 重申）：PC 三端是同一产品的四个功能面，不是四个产品 ⇒ 能力 / 需求 / 概设 / 详设各只有一本全量书，不许按功能各立一套。判据：`Docs/` 根只认这四个功能合写的书（`check-doc-invariants.py` 白名单）。
- **Notes / Retro / Tuner 是独立产品，独立仓里的书是「分册」**：分册**来自全量三书，只裁剪不增删** ⇒ 分册出现的每个编号都必须能在全量三书里找到（`分册 ⊆ 全量`）；
- **分册书数 = 本仓实际承载的端数（2026-11-09 人类主人令三次修订）**：Notes 仓只放移动端（需求 + 概设 + 移动端详设 + 移动端一单），**PC 端 Notes 的代码与端册归主力仓**（`Plugins/Notes/` + macOS 详设 §4.5 + macOS 一单）；Retro 纯 PC、Tuner 纯移动，各一套；
- **分册只有需求与概设是「截取」（2026-11-09 人类主人令二次修订）**：**需求规格**（平台无关）＋ **概要设计**（平台无关）这两本从 L0 截取，其余**按端各成一套「详设 + 任务清单」、由该端自己负责**；原话「Notes 分仓（Retro 同理）仅有需求规格说明书和概要设计说明书需要从全量版本中截取，其他就是移动端和 PC 端各自的详设和任务清单各自负责」；
- **分册的需求书与概设不许按端拆**：一个产品各一本，端差异不写进这两本；**详设按端一本**（PC 族基准 macOS / 移动族基准 Android，同族其余端从本族基准派生），只改落点与读数口径，不许另起契约正文。判据：每端详设头部写「端族 / 基准端 / 契约来源（L0 版本 + 概设章节）」，缺一判红；**唯一例外是任务清单** —— Notes / Retro 各记各的，全量 Studio 仓也有自己那份（`-macOS`）。违规分两种：分册有、全量无 ⇒ **全量漏登**；分册改条文 ⇒ 越权。判据：`Scripts/check-book-subset.py`（负例：分册塞一条全量没有的编号 ⇒ 必须判红）。
- **三书由大河马统一输出**，端不各写一套；详设按端分册，端名只出现在详设文件名里（2026-10-26 定）。判据：评审（谁落笔看 git 作者）。
- **一单只给正在开发的端建、每端一份活件**（现 = `-macOS` / `-Android`）；其他端有详设、不建单，真开工时再加；**不设产品级总单**；旧写法 `-安卓端` 不许复活。判据：`Scripts/check-end-sheets.py`（判据 A2）。
- **一单永远只有一份活件，不做版本快照**；只有三书有版本。判据：同上。
- **一单与详设同构、按端分册，只认同端详设活书**：不许引别端详设、不许把 `Docs/frozen/` 冻结件当上游。判据：同上（判据 I）。
- **一单是唯一进度源**：日报 / 周报 / 进度表一律从它取，不许另开「里程碑清单」「按平台任务清单」当第二本。判据：`Scripts/check-plan-coverage.py` + 评审。
- **`Docs/` 根只许三书 + 一单**（+3 工程件：`README.md`、本件与《项目管理规范》、详设模板）；发布说明 / 点验清单 / 功能清单 / 调研书 / 各类记录等过程件一律进 `Docs/archive/`。判据：同上（判据 H）+ `Scripts/check-doc-invariants.py`（17 份白名单）。
- **跨端视图不是书**：平台矩阵 / 按平台清单 / 需求索引 / 追溯表 / 各种台账都是派生件 ⇒ 落 `.build/derived/`，不得与三书并排。判据：同上（判据 H）。
- **平台详设以 macOS 为基准派生，不各写一本**（2026-11-05 人类主人定法：「有了 macOS 的详细设计并验证通过了绝大多数条目，其他平台端的详细设计就好做了 —— 参考 macOS 版本的设计，根据平台差异进行调整即可」）：每本《X产品详细设计说明书-<端>》(macOS 除外) 必须 ① 头部写「派生自 `Docs/Doyah产品详细设计说明书-macOS.md` vX」；② 有一节差异登记，对着**本族基准**详设 §3 的每一节表态 —— 基准按族定：**PC 族（Windows / Linux）= macOS；移动族（iOS / 鸿蒙）= Android**（安卓已开发完，是移动族基准本体，不再回头补它自己的详设；iOS 按主人 2026-11-05 令「参考安卓来做详设」）； —— `沿用` / `差异` / `不适用`，后两者必须给依据或本端落点；③ 每有 macOS 详设新增一节（如 §3.29 / §3.30 这类真机缺陷补登记），各端差异登记同批补行，不是等排期。本条判的是「有没有逐节表态」，判不了「表得对不对」——后半由各端测试与骨架判据负责。判据：`Scripts/check-platform-derivation.py`（红=还有端没表过态）。
- **编号形制五段式**：`<FR|NFR|AC>-<产品码>-<面>-<域>-<三位序号>`（例 `FR-STD-DB-DRV-005`），`DATA` / `IFACE` 是合法域码。判据：`Scripts/check-req-ids.py`。
- **风险不是需求**：风险用 `R-001` 形制，`NFR-*-RISK-*` 不许再出现；状态符号不许进需求定义行。判据：`Scripts/check-req-ids.py` + `Scripts/check-plan-coverage.py`。
- **新需求登记一次性落齐派生出口**：正文定义行 → 需求索引 → 追溯表 → 平台等价矩阵 → 能力地图，漏一个门禁红。判据：`Scripts/check-req-index.py`、`Scripts/check-req-ids.py`、`Scripts/gen-platform-parity.py --check`、`Scripts/check-plan-coverage.py`。

## 4 门禁

**条文写作格式（本节总则，2026-11-10 人类主人：「规范本身其实不规范，没写人判还是机判，没写负例判红」）**

规范是行为规格书，条文不写清验收方式就不算规则。每条条文必须带六字段，缺一即不合规：

| 字段 | 写什么 | 省掉的后果 |
|---|---|---|
| **是什么** | 要求一句话，可引用 | 判据无处挂靠 |
| **不是什么** | 边界与常见误读 | 同一句话被两种解读执行 |
| **判据** | 【机判】命令 + `exit 0` ／【人判】谁判 + 判错的表现 | 条文变口号，或人判伪装成机判 |
| **负例** | 故意违规时哪条必须变红 | 判据假绿而无人知 |
| **读数口径** | 报什么、什么算通过 | 报「全绿」而书里三个版本号 |
| **归属** | 规则正文落在哪本哪节、谁有权改 | 两本规范各写一套 |

- **判据两种，必须点名**：【机判】给命令；【人判】写清「谁判 + 判错时他说什么」。只写「评审」不算判据 —— 它既不说谁判，也不说判错什么样。
- **模板的元规范在代码里，不在文档里**：`Scripts/rule-schema.json`（六字段定义）+ `Scripts/check-rule-schema.py`（执行者）。**不另立《模板规范》文档** —— 再套一层就会丢（人类主人：「随着项目深入推进，这些模板的模板也会丢失」）。
- **存量条文允许暂缺字段**：数量记 `Scripts/rule-schema-baseline.json`，**只许降不许升**；新条文一律不许裸奔。判据：【机判】`python3 Scripts/check-rule-schema.py`。
- **负例（本条自己也要有）**：新写一条缺 **负例** 字段的条文 ⇒ `check-rule-schema.py` 必须判红（该例已固化在 `--self-test`）。

**示例（改造前后，取自 §4 交接三件）**

改前 —— 看着能遵守，实则三个号可以各写一个：
> **每轮交接三件**：`check-doc-numbers.py` + `check-release-version.py` + `check-self-test-counts.py`，三条都跑（各 `exit 0`）才算交接。判据：这三条本身。

改后 —— 缺字段即红，判错长什么样写死了：
> **是什么**：交接前三条判据各自 `exit 0`，缺一条即未交接。**不是什么**：不是「跑过就算」，不是「两条绿也能交接」。
> **判据**：【机判】三条并联，任一红即整体红。**负例**：`doc-numbers.json` 的 `core-tests` 改成 5000（实测 5572）⇒ `check-doc-numbers` 必红。
> **读数口径**：报「三件：绿/红」三项，不报合并结论。**归属**：本条只管交接动作，版本纪律见《项目管理规范》§5。
- **唯一入口**：Studio `./Scripts/verify-all.sh`（只验 Core 用 `./Scripts/verify-core.sh`）｜ Notes `bash tools/logic-check/run.sh` ｜ Retro `bash tools/verify-all.sh`。判据：跑它本身，`exit 0` 才叫门禁绿。
- **首红即退** ⇒「只剩一处红」是伪读数；要一次跑完用 `--keep-going`。判据：`Scripts/test-verify-all-gate.py`。
- **每轮交接三件**：`check-doc-numbers.py` + `check-release-version.py` + `check-self-test-counts.py`，三条都跑（各 `exit 0`）才算交接。判据：这三条本身。
- **文档体系相关**（清单与每项口径的唯一来源 = 《产品概要设计说明书》§8.3）：`check-frozen-sync` · `check-doc-versions` · `check-doc-tables` · `check-doc-invariants` · `check-end-sheets` · `check-plan-coverage` · `check-req-index` · `check-req-ids` · `check-p-parity` · `check-exclusive-sections`。判据：`./Scripts/verify-all.sh`（已接线）。
- **契约层锁定**：无 `[独占:*]` 标记的节 = 契约层，只有大河马可改；他侧走提案或注 `contract-change：理由`；台账类节标 `[开放]`。判据：`Scripts/check-exclusive-sections.py`。
- **提案通道**：动契约层先提 `Docs/proposals/NNNN-短标题.md`（状态 / 提出方 / 影响面 / 关联提交 SHA），采纳后由 macOS 侧落笔。判据：`Scripts/check-exclusive-sections.py` + 评审。

## 5 交接
- **接手第一天四步**：① 读 §1 → ② 跑门禁确认基线绿（不绿先修基线，别做功能）→ ③ 从一单挑「不需用户到场」的直接做 → ④ 做完更新文档并提交。判据：评审。
- **换环境 / 换助理**：本件 + 《项目管理规范》整份贴过去即可接手；拍板原话与逐笔记录在 `Docs/archive/过程记录-20261026/`，只在追溯时查。判据：评审。
- **日报三段**：做了什么（对应一单条目号）· 门禁/读数 · 阻塞；数字只从一单取；一单状态词只许 `todo / doing / blocked / done`。判据：评审。
- **引用他的话与数字必须逐字**，不许润色；每条结论都要能指到出处（三书条文 / 派单单号 / 提交）。判据：评审。
