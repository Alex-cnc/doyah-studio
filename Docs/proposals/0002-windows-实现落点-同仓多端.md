## 背景

Windows 端已由需求提出者 2026-09-27 拍板动工（「Windows 版本的 Doyah Studio 也可以动工了」），
并且**本侧已在 §8.5 `[独占:windows]` 落位设计层**（v2.35：技术栈 / 适配点 / 本节闸门 / 差异条目 `P-17`~`P-24`）。

但**落点本身未定**，而它是契约层事实 —— §8.2「仓库结构（按平台分节）」里只写了：

- `DoyahStudio/`（macOS 侧，现有）
- `doyah-linux/`（Linux 侧，待建：建议独立仓库或同仓子目录）

**没有 Windows 侧那一条**。§8.5.6-1 记着「本侧建议同仓 `windows/`，待契约侧与需求提出者确认」。
**在该条确认前，本侧不建目录、不写代码** —— 否则等于用既成事实替契约侧决定 §8.2。

## 提案

**Windows 实现进 Studio 主仓，同仓多端**：在 §8.2 的代码块里补一段（与 macOS 侧并列）：

```
windows/                         # Windows 侧（本仓内，与 macOS 侧并列）
├── Core/          # 领域层（§3 契约的实现；不得引用任何 GUI / 平台包）
├── App/           # 表示层（WPF）
├── Platform/Windows/             # 平台适配层（唯一允许 P/Invoke / Windows 专有 API）
├── Cli/           # 无界面验证入口
├── Tests/         # 单测（xUnit）+ 平台层测试
└── Tools/         # 本节闸门（verify-all.ps1 / 令牌棘轮 / 文档与中立性校验）
```

配套条文（建议一并落进 §8.2 的说明文字）：

1. **三书单一来源不变**：`windows/` **不得另写一份契约**（数据模型 / SQL / 导入导出 / 笔记存储分层 = §3 与三书）；
2. **契约层锁定不变**：无标记节只由 macOS 侧改，本侧走提案或带 `contract-change：理由` 痕迹；
3. **平台实现层各归其主**：`windows/` 与 §8.5 由 Windows 侧落笔，另一端只读；
4. **构建与门禁入口放 `windows/Tools/`**：不要求在 macOS 上可跑（与 Notes 仓 `windows/` 同口径）；
5. **设计令牌共享取值**：`Docs/design/terminal-palette.json` 那类跨端交接物**只有一份**（§8.5.3 已写）。

## 代价与替代方案

- **代价**：单仓变大、两套构建工具链共存（SwiftPM / Xcode 与 .NET / MSBuild），`verify-all.sh` 需按平台分流；
  仓库根目录多一层平台目录，克隆体积与检出时间上升。这些都是**可接受**的。
- **被排除：另开 `doyah-studio-windows` 独立仓** —— 把「契约单一事实源」拆成两份（正是契约层锁定要防的事），
  且三书会出现第四份副本或严重的跨仓版本滞后；Linux 侧那条「独立仓库或同仓子目录」是**单端自用**的形态，
  与 Windows 端「与 macOS 完全一致」的目标不同。
- **先例（同口径已采纳）**：Doyah Notes 的 `0001`「Notes 的 Windows 端形态：同仓多端」——**已采纳**
  （需求提出者拍板，采纳大河马侧建议）；Doyah Retro 的 `windows/` 目录亦为同形态。

## 结论与落笔

- 采纳方：**待契约侧（macOS 侧 / 大河马）与需求提出者确认**；本侧建议采纳。
- 若采纳，落笔拆两步：① **契约侧**在 §8.2 补 `windows/` 段落（契约层，本侧不改），提交信息写
  `contract-change：理由（proposal 0002）`，并在 §10 台账行保留本提案号；② **本侧**随后建 `windows/`
  目录、跑通 8.5.3 的闸门（先有闸门再有功能），并把 §8.5.7 的「⬜ 未开工」按实际推进改写。
- 若驳回（改为独立仓）：本侧按新落点重写 §8.5.1 的工程结构与 §8.5.3 的路径，届时再请契约侧改 §8.2。
