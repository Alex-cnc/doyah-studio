## 6. 版本节奏与里程碑（v1.2 提速：一天多版）

**节奏口径（2026-10-23 二次提速：人类主人令「一个小时放一个 beta 版本不行吗？我明天就要第一个 rc1」）**：

- **一小时一包**：每包一个功能批次，构建 4 分钟 + 闸门 3 分钟，其余时间全给功能；
- **rc1 = 2026-10-24（明天）**，为此 1.0 之前只做「能在一天内做完且不回退」的项；
- **为赶 rc1 的取舍（A 案，默认执行）**：rc1 只含 ①云同步闭环 ②笔记 UI 收口 ③外部反馈修复；**笔记本族（NOTE-29~35）与账号全流程（AUTH-03~07）顺延到 1.1**——它们是新数据模型/云端协议，硬塞进 rc1 会带病出厂；
- 破坏性改动（表结构、同步协议）**今天全部落地**（rc 期只允许向后兼容修补）。

**（历史）一天 2~3 版口径**：

- **一天 2~3 个包**，每包 = 一个可感知的功能批次（不是修一行字）；
- 每包必跑：`gate.py` 26 项 + 纯逻辑 409 例 + 真机/模拟器抽验；
- **仪式降级**：截图集重出 + 说明书跟版 + 派单登记**只在对外发的那一包**做（约省 15~20 分钟/包），内部包只跑闸门；
- 一包做完立即出包、立即报读数，不等攒批；
- 单批次上限 90 分钟，超时就切小再发。

**RC 阶段规则（2026-10-23 人类主人补：「beta 之后是 rc 版本」）**：

- **beta → rc → release** 三段：beta 加功能，rc 只修缺陷，release 定版；rc 阶段**不接受新需求**（进来的一律排到 1.1）；
- rc 每包都必须**对外发**（这是拿真实反馈的最后窗口），且要跑全量回归（闸门 26 项 + 409 例 + 两态四屏截图）；
- 进 release 的门槛：**连续一个 rc 包零崩溃 / 零 ANR / 零阻断级缺陷**，且外部用户测试满 24 小时无新阻断问题；
- 破坏性改动（表结构、同步协议）**必须在 rc1 之前全部落地**，rc 阶段只允许加列这种向后兼容的修补。

**为什么能提这么快**：批次 A/B 都是「加列 + 加界面 + 加判据」，每包 60~90 分钟可完成；真正的瓶颈是每次出包的构建（约 4 分钟）与闸门（约 3 分钟），不是功能本身。
