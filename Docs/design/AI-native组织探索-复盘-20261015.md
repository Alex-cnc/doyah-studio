# AI-native 组织探索 · 复盘（2026-10-01 ~ 2026-10-15）

> **出处**：人类主人 2026-10-15 令 —— 梳理 AI native 组织的探索过程，「既要记录做过什么，也要总结失败原因和经验教训，以及成功案例，供后续参考」。
> **取材**：本会话全部历史 · `DoyahDispatch` 全部派单（**973 张**）与台账 · 三书 · 基本法与沿革（v2.0→v6.4）· `AGENT-SPEC.md`。
> **一句话结论**：**这套组织的「治理能力」是成功的，「编制规模」是失败的** —— 机制越建越精密，节点越加越多，而**协调开销吃掉了增益**；最终被迫从 **9 agent / 三层** 砍到 **2 名开发主力 + 轻度协同**。

## 一、演化编年（五个阶段）

| 阶段 | 时间 | 形态 | 关键发明 | 为什么这么走 |
|---|---|---|---|---|
| **① 一人盯一机** | 10-01 ~ 10-02 | 1 人类 + 1 agent | 三书（功能/需求/概设）立起来；平台实现层与契约层分离 | 先要有「契约」，才能让别的 agent 照做而不跑偏 |
| **② 循环自主开发协议** | 10-03 ~ 10-05 | 1 人类 + 1 总管 + 2~3 助理 | **信箱派单协议**（`PROTOCOL.md` + `queue.py` 状态机）· **零 token 门控**（launchd 写 pending，有变才唤起）· 基本法 v2.x | 人类不可能时刻盯着 ⇒ 把「指令」变成**可留痕的卡片**，把「轮询」变成**有变化才唤醒** |
| **③ 组队与基本法** | 10-05 ~ 10-10 | 9 agent / 三层（1 总管 + 2 组长 + 5 dev） | **机组制**（组长 + dev，组内预审）· **基本法**（宪法级职责/程序）· **kanban** 分片 · **12 道机械门禁** | 想用「人多」换「并行度」；用「法条」换「一致性」 |
| **④ 被迫扁平化** | 10-10 ~ 10-13 | 1 总管 + 2 组长（dev 全砍） | 停 kanban、**组长亲自开发**；小河马停用、只开大河马 | **实测发现：组内协调开销 ≥ 增益** —— 人类主人原话「大小河马下属的 agent 太多实际上无法、至少目前无法带来效率倍增」 |
| **⑤ 移交与极简** | 10-14 ~ 10-15 | **2 名开发主力 + 轻度协同** | 禁隔夜单 · 未清完不派开发单 · **唯一记录原则** · **撤总管**（基本法 v6.0/v6.1）· 大肥鲨解除开发（v6.3/v6.4） | 总管侧**大量积压且怎么推进都无法清零** ⇒ **撤掉总管这个节点**；三书守护与信箱轮询并入开发主力 |

## 三、失败原因（按根因，不按现象）

| # | 根因 | 证据 | 影响 |
|---|---|---|---|
| **1** | **协调开销随节点数超线性增长** | 9 agent 三层时卡量 157/日（峰值）；人类主人实测「**40% 以上开销在团队间沟通协调**」 | 加人 ≠ 加速，**反而更慢** |
| **2** | **总管是单点** | 52% 的卡由总管发出；他积压 ⇒ 全队停摆 | 「怎么推进都无法清零派单」的直接原因 |
| **3** | **多真值 / 记录分散** | 一度有 12 处「源」（卡片 + 6 份台账 + 看板 + 缓存 + 第二盘面…） | **数字反复变、无法确定性** ⇒ 人类主人裁定「**唯一记录原则：信箱仓就是唯一记录**」 |
| **4** | **判据与真实工作的覆盖面不匹配** | ① `T-062` 无 `due` ⇒ 巡检抓不到（挂 9 天）② 待落笔总账 58 条的**行号全部失效**（文档已改写）③ 悬空引用机检**四轮全因判据覆盖不足而假阳性**（48→29→作废→23） | **坏判据比没有判据更危险**：它制造「假发现」与「假清零」 |
| **5** | **边界靠人记，不靠机制** | 越界改 `[独占:*]` 节、`.idea` 混入提交致推送静默失败、按行前缀批量改表误伤原表 | 反复返工（单日 4 次） |
| **6** | **没有终止条件** | dev 可无限拆片；卡可无限挂；「立项」曾被当成「放行」 | 必须靠**人类主人的禁令**兜底（10-14 冻结、10-15 继续冻结） |
| **7** | **把可靠性寄托在模型注意力上** | 前门多次「漏单」：只查当下想到的窗口就宣布「清零」 | 同一类错误一天犯三次，**信任受损** |
| **8** | **变更成本被低估** | 10-15 单日 5 次组织变更 + 机制改挂 + 三书跟版 | 交接本身消耗了当天主要产能 |

**一句话**：**失败的不是「机制」，是「编制」与「判据覆盖面」。** 机制（卡片流、门禁、法条、门控）都成立；**但节点加多了、判据做窄了、真值分散了。**

## 四、成功案例（值得保留并复用）

| # | 做法 | 为什么有效 | 证据 |
|---|---|---|---|
| **1** | **契约层 / 实现层分离**（三书 + 平台实现层归各侧） | 多端并行**互不阻塞**；端只需照契约做，不必等对方 | 平台等价矩阵 §10.10 **204 → 278 行**可机核；Windows 端独立达到 **52%** |
| **2** | **信箱 + 卡片协议**（`PROTOCOL.md` + `queue.py` 状态机 + 归档冻结） | **异步**、**可留痕**、**可复算**；不靠"当面说" | 973 张卡全生命周期可追；归档 957 张 |
| **3** | **零 token 门控**（launchd 每 120 秒写 pending；有变才唤起模型） | **无变化不烧钱**；轮询成本≈0 | 门控脚本 rc0 静默 / rc10 写 pending |
| **4** | **机械判据 + 成对读数 + 反例判红** | 「**未跑 ≠ 通过**」；**放宽不会变成放水** | 例：`check-doc-numbers` 抓出实测/台账不一致；判据自测 45/45；反例 15/15、30/30 |
| **5** | **失败留痕文化**（沿革 / 台账 / 自记缺口） | 事后能复盘，避免重复踩 | 沿革 v2.0→v6.4 逐条可查；`T-20261010-172`「小河马停用」等原话入档 |
| **6** | **人类主人直接点名的机制修补** | 一次修一类，不复犯 | 「派单不许跨天」→ 第四十六条；「未清完不派单」→ 第四十七条；「唯一记录」→ 协议第一条 |
| **7** | **收敛后的极小结构当天见效** | 撤总管后**当天**完成机制改挂并留成对读数 | v6.2：三仓 `path-ownership` / 门禁 / 归属 actor 三处 `bluewhale`→`hugehippo`，自测 45/45 全绿 |

## 五、经验教训（可直接当规矩用）

1. **组织规模 ≤ 协调容限** —— 先砍节点，再加机制；**9 → 2 的收缩比任何流程优化都有效**。
2. **唯一真值** —— 一件事只允许有一处记录（本族 = 卡片）；**其余只能是派生视图**；**没有卡 = 没有活**。
3. **判据先于流程，且必须声明覆盖范围** —— 报「缺失/悬空」前先列齐**所有合法目标源**；否则**只许报「未知」，不许报「发现」**。
4. **别让单点承担唯一职责** —— 总管占 52% 出单量 = 结构性瓶颈；**跨侧接口要么并行化，要么下沉**。
5. **每条活都要当天到期** —— **没有期限 = 没有机制看得见**（`T-062` 9 天案）。
6. **可靠性靠不变量，不靠注意力** —— 每发现一类漏，就把它变成一条**机械判据**；判据改动要留痕并标注「**口径校正 ≠ 进度**」。
7. **变更要记沿革** —— 尤其**组织变更**；本次做得好（v6.0~v6.4 全在案），但**变更频率本身要控制**。
8. **越界与例外必须机器判** —— 独占节、白名单、归属 actor 都应可机核；**靠人记必错**。
9. **失败要当场留痕** —— 我自己的 4 次返工、3 次假阳性都写进了台账；**这是唯一能让后人少踩的方式**。
10. **人要能一眼看清状态** —— 汇报只给一张表（源 × 未结 + 合计）；**合计不为 0，不许说「清完」**。

## 六、现状与后续探索建议

**现状（2026-10-15 08:xx）**：**2 名开发主力**（大河马 = macOS + 鸿蒙 + 三书守护 + 信箱轮询 + 项目管理；小河马 = Windows + Notes）+ 1 名写作/地缘角色（鲸鱼娘）+ 大肥鲨（解除开发，另有任用）。**保留了轻度 agent 协同能力**（卡片流、门禁、成对读数）。

**建议的下一步（极简结构的探索方向）**

| # | 建议 | 理由 |
|---|---|---|
| 1 | **保持 2 名开发主力为上限**，需要扩编时先用「外部工具/脚本」替代第三个人 | 协调开销的临界点已经被撞过一次 |
| 2 | **把「三书守护 + 信箱轮询」并入开发主力**（已完成）| 治理动作与开发动作同源，**少一层转达** |
| 3 | **全面贯彻唯一记录**：所有台账降为派生视图，日报只数卡 | 消除「数字反复变」的根源 |
| 4 | **建立「目标源全集」清单**，任何机检必须声明覆盖 | 消除假阳性（本次四轮教训） |
| 5 | **把「当天到期 + 未清完不派单」写进工具**（`queue.py` 已开始拒跨天 due） | 把纪律变成**不能违反**而非**不该违反** |
| 6 | **每两周一次组织复盘**（像本件），只保留**仍在产生价值**的机制 | 机制会腐化（如恒红告警、失效行号） |
