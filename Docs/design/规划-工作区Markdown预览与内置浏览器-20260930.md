## 一、Markdown 预览

### 1.1 现状（实测）

| 项 | 事实 |
|---|---|
| 编辑器已有 | `Core/CodeLexer.swift` 已含 **Markdown 语言**（高亮）、行号列（`L-111`/`L-64`）、格式化（`FR-EDIT-39` 形态③）、文件树/多页签 |
| 编辑器没有 | **任何预览**（`grep -rn 'Markdown' Core/*.swift App/Views/*.swift` 只命中 Lexer 的语言清单） |
| 仓里已有的 Markdown 能力 | **笔记侧**：Markdown 是**权威源**（2026-09-30 `Q8` 拍板：Markdown 权威源 + 样式旁挂 JSON），`Core/NoteBody.swift` 已有「Markdown → 文档模型」的解析与投影（`NoteBodyProjection.toSpans(_:language:)` / `exportMarkdown(...)`） |
| 家规（不可违反） | ① 不引第三方 Swift 封装（笔记存储引擎当年就是这么定的）② 契约层可单测、平台层只做渲染 ③ 能本机算的不走模型（`FR-EDIT-40` 第 5 条同族）④ 本地文件与预览**不许联网**（预览若联网，出网必须进外发日志） |

### 1.2 三条路线对比

| 路线 | 能做到什么 | 代价 / 为什么不动手 |
|---|---|---|
| ① SwiftUI 原生 `AttributedString(markdown:)` / `Text` | 只有**行内标记**（粗体 / 斜体 / 行内代码 / 链接）；**标题、列表、表格、代码块、图片、引用都不支持**（Apple 走的是 CommonMark/cmark 子集） | 达不到「预览」的基本盘（看不了表格与代码块）⇒ **否** |
| ② 第三方渲染库（如 MarkdownUI 一类） | 开箱即用、GFM 全量 | 新增第三方依赖 + **仓里变成两套 Markdown 解析**（笔记侧一套、编辑器一套）⇒ 同一份文档两处口径不一致的风险 ⇒ **否**（与「不引第三方」家规冲突） |
| ③ **复用笔记侧解析 + 平台渲染**（**推荐**） | 契约层已有「Markdown → 文档模型」，编辑器预览只是**第二个消费者**：模型 → macOS 渲染（`NSAttributedString` / SwiftUI 视图树）；Windows 侧由 Tauri 前端渲染同一模型 | 需要在笔记侧解析上补 GFM 缺口（表格 / 任务列表 / 代码块围栏），但**只补一处**，笔记与工作区同时受益；可单测 |

**为什么 ③ 明显更省**：笔记侧已经是 Markdown 权威源，`Q8` 拍板时不接受「再来一套」。预览不是新产品，是**同一份解析的第二个视图**。

### 1.3 范围（建议冻结）

- **Alpha 2（10-04）必保**：分屏（左源码 / 右预览）或切换式只读预览 · **跟随滚动**（编辑与预览同一位置）· GFM：标题 / 列表 / **表格** / **任务列表** / 围栏代码块（带语言高亮，复用 `CodeLexer`）· 链接可点（**默认在已内嵌的浏览器页签里打开**，见 §二；不弹系统浏览器）· 大文件与二进制**如实截断并报数**
- **Beta 1**：图片渲染（含本地相对路径，走授权目录读）· 数学式 · 导出（Markdown → HTML/PDF，与 `FR-EDIT-16` 导出族同批）
- **不做**：所见即所得双向编辑（Markdown 是权威源，WYSIWYG 会引入第二真相）

### 1.4 判据（每条都要能机器判）

1. **解析层单测**：固定样例 md（含表格 / 任务列表 / 围栏 / 嵌套列表）→ 文档模型逐节点断言（笔记侧同一批样例，**两处消费者同源**）
2. **预览不联网**：预览全过程外发日志（`NFR-SEC-08` 同一份）**零写入**；断言失败即红
3. **跟随滚动**：编辑光标行 ↔ 预览锚点行的映射单测（不靠肉眼）
4. **如实跳过**：> N MB 或二进制 ⇒ 预览区显示「已跳过（原因）」，测试断言文案与计数
5. **不写第二套解析**：门禁断言「编辑器侧不得出现独立的 Markdown 解析实现」（只许引用契约层）

## 二、内置 Web 浏览器：现状核查（**不需要调研「怎么内置」**）

### 2.1 已经在产品里（`FR-EDIT-34`，2026-09-23 落地）

| 层 | 落点 |
|---|---|
| 契约层 | `Core/BrowserPage.swift`（地址 / 标题 / 加载态 / 错误 / **有界历史** + 前进后退）、`Core/BrowserNavigationPolicy`（**默认不加载远程内容**，导航一律显式发起）；下载 = `Core/BrowserDownload.swift`（文件名净化 + 不覆盖已有文件） |
| 平台层（macOS） | `Platform/macOS/WebKitBrowserEngine.swift` —— `WKWebView` + `WKNavigationDelegate`，**每次导航裁决先过 Core 策略并写进统一外发日志**（放行与拦截都记）；不注册任何 `WKScriptMessageHandler`（不给页面一条到原生代码的通道） |
| 界面层 | `App/Views/BrowserTabView.swift` —— **工作区**的可关闭浏览器页签（与 **Home / 文件页签同类**；页签条 = `App/Views/WorkspaceTabStrip.swift`，内容区在 `WorkspaceAreaView.swift`）—— **归属订正 2026-10-01**，原文「编辑器区……与 SQL 页签同级」已作废 |

已具备的行为：① 空白页起步、不预载远程内容 ② 每条出网（文档 / 子资源 / 下载）进**同一份外发日志**、可按页签过滤 ③ **独立数据存储**（不与数据库连接的凭据共用 Cookie / 缓存）④ 下载走**授权目录**模型、不静默写盘 ⑤ 页签状态随会话持久化 ⑥ 平台差异登记在 **§10.9 `P-14`**（允许渲染引擎 / Cookie 存储 / 权限提示不同，行为契约必须一致）。

### 2.2 现在还欠什么

1. **人工点验**（`FR-EDIT-34` 的 🟡 残项）：GUI 点击、下载观感 —— **只能你看** ⇒ 已并入内测清单（`L-138`）
2. **Windows 侧实现**：Tauri 2 壳**本身就是 WebView2**（系统组件，Win11 预装、Win10 需 Evergreen Runtime）⇒ 小河马侧不需要「引入浏览器」，只需要按其宿主约定接**同一套 Core 契约**（`BrowserPage` / `BrowserNavigationPolicy` / 外发日志）—— 合同已登记 `P-14`，归小河马
3. **Linux 自用第三端**：本侧不实现（口径不变）

### 2.3 如果你要的是「更强的浏览器」（增强候选，**别全做**）

| 候选 | 价值 | 版本建议 |
|---|---|---|
| 页面内查找（⌘F） | 高（配合「网页里找一段话」的日常） | Beta 1 |
| 书签 + 最近访问 | 中 | Beta 1（可选） |
| 开发者工具 / 检查器开关 | 低（自用产品，除非你要调页面） | 不做，除非你要 |

> 三者都会动 `BrowserPage` 契约与数据隔离口径（书签要落盘位置、DevTools 要暴露调试面）⇒ 要做先登记再排期，**不顺手加**。
