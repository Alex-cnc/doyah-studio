# 存储选型（待迁概要设计）

> 从能力书 2.5「存储分层」整节迁出（2026-10-18）。能力书只留「数据归属」三条能力级表述；
> 以下全部是**选型与实现**，能力书定稿后并入 `Doyah产品概要设计说明书.md`。

**人类主人原话**：「统一到 SQLite，主存进库、原始数据与附件留在文件系统确认」

| 项 | 决定 |
|---|---|
| 引擎 | 桌面各端统一本地 SQLite，WAL + 事务 |
| **进库** | 笔记元数据 / 正文 / 标签 / 时间线 / 附件索引（只存路径）；将来复盘侧的成交明细、周报索引同引擎 |
| **不进库** | 原始行情快照仍 CSV/JSON（可读、可 diff、喂脚本与 AI 零摩擦）；附件二进制留文件系统；导出产物照旧落盘 |
| 接入方式 | vendored `sqlite3.c`（公有领域）+ 本工程薄封装，沿用 `Vendor/` 纪律；不引第三方 Swift 封装 |
| 判据 | 四条 4/4 命中：数据持续增长 / 有并发写与多进程读 / 要按条件查与全文检索（FTS5）/ 要崩溃不坏数据的硬保证 |
| 迁移成本 | 换引擎成本最低点：实测 `notes.json` 仅 395 字节；L-03 已演练一次性迁移 + 原子写 + 坏文件回退 |
| 排除 | GRDB（官方仅 Apple + Linux，Windows 社区探索中）、SwiftData / Core Data（Apple 独占）、JSONL（查询要自建索引）、DuckDB（分析型，不适合作事务主存，可作日后分析层） |

**与移动侧的关系**：移动端 `relationalStore` 底层同为 SQLite ⇒ 各端将来可共用一种数据契约。
