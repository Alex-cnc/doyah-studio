# 能力规划说明书 → 需求分析说明书：派生规程

> 这份规程解决一件事：需求书不许「另起一套」，也不许把能力书原文搬进来。每一条需求都要能回答「对应哪个能力点、它的边界从哪来、怎么算做到了」。

## 一、两本书各管什么（先定，不然派生会跑偏）

能力书回答「是什么」：一个能力点一节，只写三段 —— 是什么 / 不是什么 / 边界。
需求书回答「要什么」：一个能力点一节（同名同序），节下是若干条可独立验收的需求。

搬运方向单向：能力 → 需求。需求书里不许出现只有它自己知道的口径；反过来，能力书也不许引用需求编号。

## 二、十步派生

**第一步 骨架照抄。** 能力书的每个三级标题原样成为需求书的三级标题：同一个名字、同一个顺序。章按产品面分组（共性 + 各产品面），节号前缀不同，但三级名一字不改。

判据：两侧三级名集合双向差集为空，顺序一致。多出一节或名字改一个字，都算派生失败 —— 名字一改，下游的索引、台账、平台矩阵就对不上了。

**第二步 一条能力点至少一条需求。** 「是什么」决定这条需求干什么；一条需求只承载一个可独立判红判绿的行为。判断粒度的方法很笨但有效：能不能单独写出一条会失败的断言？不能，就是还没拆开。

**第三步 「不是什么」变负例。** 能力书写「不许 X」，需求书在验收里写「X 的时候应当报错 / 拒绝 / 不落盘，并说明原因」。能力书里最值钱的就是这一句，漏掉负例，这条需求就只剩半条。

**第四步 「边界」变硬指标。** 步数、上限、退出码、超时、体积、行数 —— 全部落进验收要点，且要有具体数值。能力书写「有上限」、需求书必须写「上限是多少、触顶时说什么」。

**第五步 写验收，且必须落进四类方法之一**（见需求书 §7.3）：Test（可跑断言，带负例）/ Inspection（结构可点名）/ Analysis（先定测量方法与阈值）/ Demonstration（人工点验，步骤进清单）。落不进去的，说明还没写成可验证形式。

**第六步 层次从能力位置推，不从排期推。** 拆掉就不能用的 → 基线必备；少一种本事仍能用 → 常用增强；可有可无 → 进阶可选。排期属于计划书，不进需求书。

**第七步 编号按五段式，域码跟着面走。** 一个能力点落在哪个产品面，编号的产品码与面码就跟着它；域码必须已在 §1.5 登记。编号不承载语义顺序，只在同域内递增。

**第八步 宿主侧 / 工程侧的能力落共性节。** 构建、命令行出口、授权、插件装配这类是 Studio 自己的东西，落 §3.1 用 `FR-STD-ALL-*`；不要因为「看起来所有产品都用」就编成产品码 `ALL` —— `ALL` 只配面 `GATE`。

**第九步 跑四条回溯判据。** 名称 1:1；每节至少一条；每条有验收且能落四类；编号与引用都能解析。这四条是可复跑的，不靠人读。

**第十步 反向也要查。** 需求书里有、能力书里没有的 §3 条目，只有两种合法解释：能力书漏了一个点（报给作者补，别自己编），或者这条其实属于工程 / 质量域（那就该是 NFR / 验收条目，不该混在 §3）。

## 三、五种常见走偏（都踩过）

1. **把实现史当验收**：写「已实现（某日）：…」。验收只回答「怎么算做到了」，做过什么属于台账。
2. **按编号前缀切节**：`FR-META-*` 一簇一节，读起来整齐，但和读者的「我要这个能力」对不上。节要按能力切。
3. **一个能力点铺三条重复需求**：总览一条、新建一条、重命名一条，三条讲同一件事且互相矛盾（一条说悬浮菜单、一条说右键）。一个能力点可以有多条需求，但每条要有互不重叠的判据面。
4. **同名两套机制合成一条**：Agent 能力层的插件（可装卸扩展点）和宿主侧的插件（装一个子产品）不是一回事，派生时必须分开写，机制不许互相借用。
5. **在需求书里写版本与状态**：「本版不做」「M2 候选」属于计划书；需求书只写要不要、怎么算做到。
