> **为什么有这份清单**：需求提出者 **2026-10-02** 原话「要在三书的概要设计出来后，按平台输出自己的任务清单，这样版本完成度就比较清晰了」（Notes 侧照此建了 `IC-BOARD-001`）；**2026-10-14** 追问「怎么到现在你还没有 macOS 的任务清单？那你之前给我的 204 个任务是怎么搞出来的？」⇒ 本文件按同一形态，建 Studio 侧那一份。

> **三条划界（先读这三条，再看表）**：
> ① **「项数」= §10.10 的矩阵行数（= 功能需求条数 204 · 逐端同一个分母）—— 它不是「任务数」**，更不是本机 Hermes 看板的卡数（看板卡 = 工作项台账，是另一套面）。2026-10-14 那句「204 个任务」正是两种数被混起来的现场：**204 只说明「有几条需求要在这一端落实」，不说明「有几件活在办」**。
> ② **移动端（iOS / 安卓 / 鸿蒙）不设行**：移动端 = Doyah Notes（只有笔记），不是 Doyah Studio 的平台版本（台账 `notPlatforms.mobile`）⇒ 本表按**矩阵的列**排 = **macOS / Windows / Linux / watchOS**。派单原文写的是「macOS / Windows / Linux / iOS」，其中 **iOS 与真值源冲突**（台账原话：「移动端…不在本矩阵设列，免得造出一列永远 ⬜ 的假进度」），故本文件取 watchOS —— 这是**如实订正**，不是漏排。
> ③ 表里的 ✅ / 🟡 / ⬜ **逐格就是 §10.10 的读数**（`⬜ ⚠️` 里那个 `⚠️` = 与 macOS 基线不一致，**不是第四种状态**）；本文件不做二次判定、不自己判断「算不算完成」。

## 4. 判据与维护

- **判据** = `python3 Scripts/check-board-parity.py`（rc=0 = 全绿）：从 §10.10 **逐列重算** §1 / §2 / §3 的每一格；`--self-test` = 它自己的 15 例负例证据。挂 `Scripts/verify-all.sh` **第 7 项**（与「§10.10 ↔ 台账」那几条同一项）。
- **改法（只此一条）**：**本文件一个字都不手改计数** —— 先动真值源（各端 = `Docs/平台实现状态.json` 的 `overrides`；macOS = §10.1 索引）⇒ 跑 `python3 Scripts/gen-platform-parity.py` 重写 §10.10 ⇒ 再按 §10.10 的读数改本文件（判据会把每一处不一致逐格点名）。
