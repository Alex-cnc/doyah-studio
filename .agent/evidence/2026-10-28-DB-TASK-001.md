# `FR-STD-DB-TASK-001` 任务定义可保存复用 · 第四十四批（2026-10-28）

## 1. 由头与范围

需求书原文（`Docs/Doyah产品需求规格说明书.md:1618`）：**一句话 → 一条可执行任务**：任务定义落在连接上
（目标库、只读 / 可写、影响行数上限、是否需审批），保存后可复用；定义与实际执行参数不一致时拒绝执行。
验收要点：① 任务可保存并在下次复用；② 目标库与定义不符时拒绝并说明；③ 只读任务里出现写语句被拦下。
概设 §5.3 的「任务定义」实体给了五个字段与两条禁令（禁止定义与执行参数不一致仍执行 / 禁止绕过上限）。

台账状态：实现 `⬜` / 判据 `⬜`（本批之前盘上零代码）。

## 3. 落法（三处收口 + 接线）

1. **定义实体** `SQLTaskDefinition`：连接 / 目标库 / 读写模式（缺省**只读**）/ 影响行数上限（选填、> 0）/
   是否需审批（缺省**真**）+ 名称与语句；`issues()` 一次列全（空名 / 空语句 / 空库 / 上限非正）。
   缺省值照概设 §5.3，不自己发明「更安全」的默认（默认值本身就是 §5.3 的一行）。
2. **`SQLTaskStore`**（`sql-tasks.json`，与连接、保存查询分开存）：**唯一写入口** `save` 里做两条拒 ——
   ① 定义不完整（把 `issues()` 逐条拼进理由）② **同名不同 id**。同名同 id = 原地改（复用一条定义时改目标库 / 上限
   就是这条路径），创建时刻跟第一次保存走。
3. **`SQLTaskGuard.check`**：判定顺序 = 定义完整性 → 连接不符 → **目标库不符** → **只读任务里的写语句** →
   可写任务遇只读连接 → **上限**（没带 / 放宽）→ 审批。拒绝档不进确认流程（能点「仍然执行」就等于没拦）。
   `rowVerdict` 管执行之后：`exceeded` 与 `unmeasured` 分开，**没读数不许当「动了 0 行」**。

接线：`AppState.sqlTasks` / `boundSQLTaskIDs`（tabID → 任务 id）、启动 `loadSQLTasks()`、存盘即绑定、
`loadSQLTask` 载入时**一并切连接与库**、关页签解绑；`executeQuery` 在 `let targetDatabase = queryDatabase(...)`
之后、`updateTab(isExecuting = true)` 之前过判定；工具栏「任务」菜单（存 / 取 / 删 / 解绑）+ `SQLTaskSaveSheet`；
语言键 20 个中英齐。

## 6. 口径取舍（写下来，免得下一轮当缺陷改掉）

1. **收紧放行、放宽拒绝**：定义上限 100 而这次要 10 行 —— 更严的要求不是绕过，放行；
   定义 100 而这次不带上限或要 500 —— 拒。依据：概设 §5.3「禁止绕过上限」。
2. **审批只给「真会改东西」的执行**：纯读任务即使定义写着「需审批」也不弹（弹只会训练用户闭眼点），
   与 `ExecutionSafety` 的「默认只确认高危」同一条理由。
3. **上限在执行之后判**：影响行数只有服务端回执才有；客户端不事前预估（预估错了要么放走一次超限、要么挡住合法执行）。
   超限**不撤销已执行的部分**（做不到，也不该假装做到），只当场说清。
4. **界面上「只读 / 可写」走语言表**（`sqlTaskModeReadOnly` / `sqlTaskModeWritable`），
   Core 的 `AccessMode.displayName` 只服务日志与拒绝理由（与 `DataTask` 一族同形）。
5. **`SavedQuery` 不改造**：两个类型两个文件。把可执行属性塞进书签，等于让「贴回来的片段」也带着一份执行授权。
