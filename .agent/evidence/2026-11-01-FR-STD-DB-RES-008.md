## 3) 量法（为什么这六条不是「看着对」）

挂**真** `ResultTableView`（生产里自己持有 `ResultGridState` 的那个视图）进离屏真窗口 →
从视图树里取真 `NSTableView` 与条上的真控件 →

- 按钮：`NSButton.performClick(nil)`（与手点同一条 action 路径）；
- 列 / 运算符：`NSPopUpButton.selectItem(withTitle:) + sendAction(action, to: target)`（与手选同一条）；
- 打字：`makeFirstResponder(field)` → `currentEditor().insertText(...)`（与手打同一条，字段编辑器那条路）。

判据读的是**表格里真的显示成哪几行**（逐行 `NSTableCellView.textField.stringValue`），不是「回调被调用了」。

合成数据（5 行）：`note` 同时有 `beta` 与 `BETA`（大小写才量得出差）、一个 NULL（第 3 行）、一个空串（第 5 行）、
`gamma`；`id` 是 1…5（任何「包含 a」在 id 列上都命中 0 行 —— 换列才量得出差）。

| 用例 | 读数 |
|---|---|
| ① 死路回归钉 | 没有排序 / 筛选时条也在场；点「+」后表格仍是 `1..5`（待填条件不参与筛选），且多出列 / 运算符 / 值三样控件 |
| ② 换列 | `note 含 a` ⇒ `1,2,4`；换到 `id` ⇒ 空；换回 `note` ⇒ `1,2,4` |
| ③ 换运算符 | `不包含 a` ⇒ `5`（NULL 不算命中）；`为空` ⇒ `3,5`（NULL + 空串）且值输入框消失；换回「包含」输入框回来 |
| ④ 打字 | 空值 ⇒ 5 行；逐字打 `gam` ⇒ 只剩 `4`，每敲一字 `currentEditor()` 都在 |
| ⑤ 大小写 | 不分大小写 `A` ⇒ `1,2,4`；按下开关 ⇒ `2`（只剩 `BETA`）；再按回 `1,2,4` |
| ⑥ 多条件 / 删 | note 含 a + id 含 1（AND）⇒ `1`；删第一条 ⇒ 仍 `1`；删光 ⇒ 回服务端顺序 `1..5`，条还在、还能再加 |

## 5) 这一跳修掉的两个真缺陷（不只是补判据）

1. **「+ 加条件」入口是死路**：`ResultTableView` 原先只在 `gridState.isClientViewActive` 为真时渲染客户端视图条，
   而**唯一的「+ 加筛选条件」按钮就在条里** ⇒ 没排过序的用户永远加不了第一个筛选条件
   （排序之后条才冒出来、才有加号）。这与 2026-09-23 那次分页条（选「全部」后分页条消失、再也切不回分页）同一个形状：
   入口藏在一个「只有用了入口才会出现」的地方。
   修法：只要结果有列就渲染条；R-21 那句「仅对已加载的 N 行生效」改成**按状态出现**（条默认在场之后，
   一进来就喊等于每次查询都提醒用户一件没发生的事）。
2. **点「+」当场清空整张表**：新条件默认 `contains ""`，而 Foundation 里 `"abc".contains("") == false`、
   `"abc".range(of: "") == nil`（本机实测，见 §3 的合成数据注） ⇒ 一条**还没填值**的条件把每一行都筛掉了。
   修法：`ResultFilter.isPending`（要值但还没值）不参与筛选，也不进 `whereClause`（否则会生成 `LIKE '%%'` 这种假条件）。

顺带的结构换法：列 / 运算符从 SwiftUI `Menu` 换成真 `NSPopUpButton`（`ResultFilterPopup`）。
`Menu` 落到 `SwiftUIPopupButton`，但**菜单项要到弹出那一刻才建**（实测 `itemTitles == []`，
`menu.update()` 与 `menuNeedsUpdate` 都不填）⇒ 换列 / 换运算符在离屏探针里根本量不到。
